## 拆分规则

- 一个 Feature 始终只生成一个平台级 IR。
- 按 **R1→R2→R3→R4** 顺序逐条判定，前一条触发即拆分：
  1. **R1 仓库隔离**：涉及 ≥2 个仓库且各仓可独立编译验证 → 按仓库拆
  2. **R2 子系统隔离**：单仓库内涉及 ≥2 个子系统且由不同 Owner/SIG → 按子系统拆
  3. **R3 工作量约束**：单 proposal 超过复杂度上限 → 按功能点细分至上限以内
  4. **R4 默认不拆**：不触发 R1-R3 → 单一 proposal
- **工作量分级约束**（按端到端总人月推导复杂度）：
  - 简单（<5 人月）：单 proposal ≤5 人月
  - 标准（5-10 人月）：单 proposal ≤8 人月
  - 复杂（>10 人月）：单 proposal ≤15 人月，但必须有独立验收边界和 AC
- 每个 proposal 必须有独立的 AC、工作量估算和代码范围边界。
- proposal 间依赖必须显式声明。
- **§5 必须填写总工作量汇总表**：总工作量（各 proposal 工作量之和）、复杂度分级（<5=简单/5-10=标准/>10=复杂）、proposal 数量。复杂度分级决定单 proposal 工作量上限。
