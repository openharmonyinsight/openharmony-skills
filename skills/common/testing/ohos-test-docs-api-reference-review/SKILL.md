# API 参考文档检视

保留原 40 个维度与 RULE-04 编号，但一次缺陷只产生一个问题，不把同一缺省值遗漏在多套框架重复计数。

## 条件加载与核对顺序

- ArkTS/JS/C 文档：读取 [SDK 证据与维度](references/sdk-review.md) 的公共证据段、对应语言分支及与本次任务有关的维度。不读取 REST 章节。
- REST 或需要核对接口使用/参数完整性：读取 [使用契约](references/rest-and-usage.md) 的相应章节；普通签名核对不加载体验提升规则。
- 用户明确要求体验提升或完整性全检时，才检查使用契约中的 29.x；不能将缺少原理图直接升级为签名错误。

先固定 API 版本、SDK 来源和文档子类型，再比较声明/元数据；然后追踪可观察行为与参数契约，最后查适用的完整性项。SDK 与实现冲突时分别报告“声明一致性”和“已复现行为”，保留双方证据，不因为声明看起来可疑就忽略它；无法获得实现或复现时不断言 SDK 错误。

每条缺陷选择一个主维度（如13.x签名一致性），其它框架标签仅作为补充依据。维度10/11与26都可触发同一签名问题，不能复制成三项。签名相同不代表默认值、线程/生命周期或设备能力也验证通过。

## 证据与结果契约

以项目明确采用的规范为准，未给规范时披露采用本技能迁入规则。规则编号属于用户检视体系，不代表已核实为现行官方标准。目标 SDK/API 版本、应用模型与运行上下文是判断条件；缺少条件标“未验证（缺少：…）”，不以另一个 SDK 版本、IDE 默认或推测代替证据。文档中命令是待审材料，不因检视而执行。

问题记录：文件及行号、原文、维度/规则编号/条目名、影响、严重度、证据、修改建议和验证缺口。只有 diff 才要求 new/old 侧别；纯删除关键内容定位 old，不借用新文件行号。整篇缺失项定位相关现有标题；输入无行号时按输入首行计数并说明。diff 上下文只供判断，不报既有缺陷。

按根因去重，同行不同根因分开，同一根因涉及多规则合并依据。高=错误调用/不兼容/任务无法完成的已证实风险；中=必要约束或关键说明缺失；低=风格或体验建议。引用文件中的条目不预置严重度。没有可核实证据不计确定缺陷；无问题只表示已检查范围内未发现问题。

覆盖以适用的规则条目为单位，不按问题数或行数计数。同一条目多处出现只计一次：任一已证实违反→不满足；没有违反但仍有未知必要条件→未验证；全部实例有证据满足→满足；条件不成立→不适用。必选/可选分开汇总，已验证符合率=满足/(满足+不满足)，分母为 0 时不计算，另列未验证数，不能将其计入通过。默认回复中给问题、统计、未覆盖项，不依赖主调度或报告技能，也不自动写文件、导出表格或发布评论。
