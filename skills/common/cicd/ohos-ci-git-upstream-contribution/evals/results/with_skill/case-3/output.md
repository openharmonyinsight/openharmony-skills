依据指定的 `ohos-ci-git-upstream-contribution` 技能，本次应准备可审阅草稿。GitCode 工具未连接，无法核对已有 Issue/PR 或创建远端记录；没有 CI 结果，不能声明检查通过。

题面仅给出模板路径，`materials/` 中未提供模板正文，因此以下为内容提纲。实际填写时须保留原模板的必填字段，不能假定其字段或勾选项。

**1. 准备性能修复 Issue**

使用 `.gitcode/ISSUE_TEMPLATE/task.yaml`，按实际字段填入：

- **标题**：`[性能] <场景> 下 <性能指标> 异常`
- **问题与影响**：受影响版本、分支、模块、使用场景及影响范围。
- **复现条件**：硬件、系统、构建配置、数据规模和复现步骤。
- **预期与实际行为**：目标性能与当前表现；尚无测量数据时明确标为待测。
- **分析与修复方向**：已确认的瓶颈、证据及拟修改范围，区分事实与推测。
- **验收标准**：在相同环境、负载和测量方法下比较修复前后指标，并确认功能正确性及相关回归情况。

工具连接后，先搜索已有 Issue/PR，避免重复；若需选择 Issue 类型，以 GitCode 实际支持的类型为准，不猜测枚举。

**2. 准备 PR**

使用 `.github/PULL_REQUEST_TEMPLATE.zh-CN.md`，保留必填内容，可组织为：

> **标题**：优化 `<模块>` 在 `<场景>` 下的 `<性能问题>`
> **关联 Issue**：`<确认后的本分支 Issue URL>`
> **问题原因**：`<瓶颈及证据>`
> **改动说明**：`<最终实现、作用及必要的取舍>`
> **性能对比**：`<测量环境、方法、次数和修复前后数据；未测则写待验证>`
> **验证情况**：`<实际执行的命令和结果>`
> **CI 状态**：尚无 CI 结果，相关检查项保持未勾选。
> **风险与未验证项**：`<兼容性、资源占用、边界场景等实际待核验事项>`

本地测试只有在实际运行并取得结果后才能填写“通过”；性能提升比例也必须来自可复现测量。

**3. 提交前核对**

确认真实 upstream、fork 和目标分支，不默认 `origin` 是 fork 或目标为 `master`。检查提交范围、diff 和暂存区，排除无关改动；使用现有真实 Git 身份签署提交，遵守仓库的提交数量及消息规范。

以下仅为审阅用命令，替换占位符并核对索引后再执行：

```sh
git add -- <本次修复文件>
git commit --signoff -m '<符合仓库规范的标题>' \
  -m 'Issue: <本分支 Issue URL>'
git push -u <fork-remote> <feature-branch>
```

GitCode 连接恢复后，再完成去重、Issue 创建或复用、PR 创建，并回读核对 head/base、Issue 关联和提交范围。当前没有创建 Issue/PR，也没有可报告的远端链接或 CI 通过结论。
