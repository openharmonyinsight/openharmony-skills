# OpenHarmony 指南任务链与 G 规则

## 先用失败链路决定必要信息

| 读者遇到的断点 | 核对证据与反例 | 规则 |
|---|---|---|
| 同名API在目标工程无法使用 | 绑定SDK/API版本、Stage/其它应用模型及上下文，核对声明或项目约束；不能用另一版本IDE补全判当前示例错。 | SDK来源检查 + G-18 |
| import/资源引用在片段外 | 追踪模块来源、路径/句柄/资源的取得方式以及宿主与示例的边界。已注明宿主提供不是“确定未定义”；完整工程遗漏必需资源才是操作断点。 | G-10/G-16/G-18/G-20 |
| 声明权限后仍不能操作 | 对照给定SDK的权限等级、声明位置及是否需要运行时授权；声明不等于已获授权，也不能要求所有权限一律弹窗。不要把Linux chmod/sudo作为鸿蒙权限通用恢复方法。 | 权限来源检查 + G-17/G-20 |
| 调用顺序正确但运行环境不符 | 核对UIAbility/Worker等适用环境、生命周期、设备syscap及目标模型；只有SDK/规格明确禁止才报确定错误，不能按经验猜线程限制。 | 约束来源检查 + G-15/G-17 |
| 展示代码但永远拿不到结果 | 从结果使用位置逆追Promise/callback成功路径，查初始化、状态更新和失败恢复；变量预先声明不证明异步结果已获得。 | G-10/G-17/G-20 |
| 按步骤完成却无法判断成功 | 寻找可观察结果与独立验证入口；若无需独立调测可在原步骤给成功状态，不机械追加无意义验证章节。 | G-19 |

## 保留的任务链 G 编号与证据

| 编号 | 检视对象与判定 |
|---|---|
| G-10（28.5） | 从输入到结果的操作链闭合，工程/依赖/资源取得方式可追踪；依据上表定位实际断点。 |
| G-15（28.8.1） | 步骤主体、触发条件、位置与结果能落到目标工程和生命周期。 |
| G-16（28.8.2） | 示例不依赖未声明输入或真实私人信息；规格/API名不是任意改写的“敏感内容”。 |
| G-17（28.8.3） | 分支选择、关键前提及不可恢复操作的提醒必须在使用点可见，避免只在结尾解释。 |
| G-18（28.8.4） | 片段放入声明的宿主上下文可用；没有宿主工程时编译记未验证，不能推断失败。 |
| G-19（28.8.4） | 完整示例有可复现环境与预期结果；截图属于提供的证据，不代替实际运行。 |
| G-20（28.8.4） | 自包含示例核对：匹配SDK签名/版本、依赖与变量来源、资源/权限/上下文、异步成功后使用结果、失败处理与资源释放、展示效果一致（如适用）。不依赖外部“完整代码质量清单”。 |

本地只统计下表保留的 G-10、G-15–G-20 任务链专项。其它 G 编号不再作为本地检查单：大纲/清晰度/完整性/约束/场景/调试指导复用既有质量技能，API 模板与声明检查复用 chinese-docs；未执行的委派范围不得计作通过。部分实例缺证据仍记未验证。

示例：`guide.md:30`直接调用`save(targetPath,payload)`，已给规格要求先取得路径并授权，而文档均未交代→G-10与来源权限规则指向同一前置链路断点，按根因合并并列证据；建议补输入来源、授权与失败出口。只有“宿主提供readConfig”的片段且没有工程→G-18未验证，G-19不适用，不能报编译失败。
