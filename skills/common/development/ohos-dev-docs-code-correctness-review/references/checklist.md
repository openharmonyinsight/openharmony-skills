# 编码、版本与图文的专项判定

## 证据矩阵

| 目标结论 | 最小证据 | 不足时如何处理 |
|---|---|---|
| 名称/签名/参数/属性合法 | 匹配项目SDK的声明、C头文件或明确schema，绑定版本/模型 | 无匹配声明仅查文内矛盾，外部合法性未验证 |
| 默认值/生命周期/线程限制/设备效果 | 匹配实现/规格，必要时给定环境复现 | IDE默认值及其它版本只是线索，不作最终依据 |
| 可编译 | 工程/宿主上下文、工具版本及实际编译输出 | 片段静态核对不能写“编译通过”，缺截图不证明失败 |
| 运行和图文一致 | 设备/环境、实际结果及可读图片 | 无图标未验证，非UI示例不强制截图 |

## 1.1 ArkTS / ArkUI

按“导入路径及对象 → 签名/装饰器/属性 → 调用环境 → 成功结果消费”追踪。

- @kit/@ohos 名称、成员继承、参数可选性/顺序及返回方式对照目标SDK；IDE补全可能来自另一SDK，不按默认自动导入判当前代码错。
- UI DSL片段、普通逻辑代码及宿主组件上下文分开；装饰器/状态模型差异需匹配项目规则。不能把TypeScript允许的用法直接当作该ArkTS版本允许。
- 组件width/height等是否允许字符串依声明，不因为参考偏好数字就报语法错；枚举大小写和事件回调参数则可逐字段对照。
- Promise/callback结果须沿成功路径再消费，外层变量预声明或加日志不能证明值已取得；错误字段类型未知时不建议盲读code/message。

## 1.2 C API

证据路径：头文件版本→完整声明→调用实参→返回值/所有权。

- 区分返回类型、参数类型/顺序、指针层级、const位置、函数指针；宏名称相似不能证明数值一致。
- const是类型修饰，不独立证明参数非空、对象生命周期或资源归属。缺少这些契约可指出说明缺口，但不能猜释放函数。
- 示例：`open_data(1,"x")`对`int open_data(const char *path,unsigned int flags)`→参数类型/顺序确定错误，改为`open_data("x",1)`；标志值1是否允许仍需规格，不因通过类型检查宣称可运行。

## 1.3 JSON5

依给定schema核对module/app的层级、类型、权限与资源引用，不把资源值字符串当普通文件路径。仅给一个局部schema时不凭空补全所有必填字段。

JSON5允许注释、单引号和尾随逗号。`{module:{name:'entry',},}`不能因严格JSON解析器拒绝而报错；若schema要求name为string而值为123，则报告字段类型，不报告逗号。权限是否需运行时授权另依目标SDK契约，不能从manifest声明推断已获授权。

## 1.4 Bash / 构建和设备命令

区分主机/设备路径、可执行工具版本、子命令、选项、路径引用及变量来源。hvigorw、hdc、hilog等用法从给定版本帮助或项目脚本核对，不用记忆构造新选项。

`rm -rf "$OUTPUT_DIR"`中变量未定义时，指出缺少非空/允许目录边界约束，绝不试跑删除命令；空变量被引用不等于一定会删根目录，也不能据此夸大已发生的数据损失。文档审查不执行设备命令或权限修改来验证“可能有效”。

## 2 版本一致性

接口/成员起始版本、废弃版本、能力和设备条件分开；模块since不能无条件覆盖后来新增成员。文档声称API12支持而给定匹配声明since13→可确认矛盾；只有API13签名与API12文档不同→不能确认API12有错。

## 3 图文一致性

只比较实际可读图片中的文字、组件类型、布局和可观察结果；代码在某一分支产生的效果要与同场景截图对应。图片缺失不推断其内容，不要求所有图片达到某分辨率，非UI功能不要求效果图。

## 4 基础质量（仅用户指定）

4.1用于可定位低错和文内矛盾，4.2用于项目渲染后损坏的标题/代码块/表格/链接；代码标识符和项目认可的`<sup>`版本角标不作为普通中文或非法HTML自动修改。精细写作约定可选用写作技能，未安装不声称覆盖其完整规则。

无条件验证反例：SDK签名匹配但缺工程→“签名满足，编译未验证”；代码文字写Button但图片不可读→“图文未验证”，不是“截图与代码不符”。
