# 文档示例风格（5.x）

先判断示例角色，而不是套用“所有代码必须一样”的规则。

| 示例角色 | 异常处理与上下文要求 |
|---|---|
| API 查阅片段 | 可以省略业务错误处理；模板允许 try/catch 或 .catch 时不报它们存在。省略的上下文需要说明来源。 |
| 开发指南 | 关键失败路径须有可操作指导，片段可用注释指向宿主逻辑；是否需要捕获按调用契约，不因简单 try/catch 包裹就认定已处理业务失败。 |
| 最佳实践/完整工程 | 验收真实恢复、资源释放与失败传播；不能用只打印日志证明错误已恢复。 |

| 规则 | 迁入约定与误判边界 |
|---|---|
| 5.1 代码规范 | import 来源、状态/应用模型与匹配 SDK 对照；组件属性是否允许单位字符串由声明决定，数值写法只是风格偏好。API 是否每项独立给例子以模板决定，关联调用可共享场景示例。 |
| 5.2 代码展示 | 一个代码块对应一个文件，混合宿主与片段需明确文件边界；省略统一 `// ...` 或说明，不把省略标记作为真实可执行语句。格式化是否运行须有证据。 |
| 5.3 异常日志 | 指南默认建议操作描述+code/message，如 `Failed to load. Code: ..., message: ...`；先确认异常类型确有这些字段，不能给 unknown 强加属性访问。API 片段遵循上表例外。 |
| 5.4 正常/成功日志 | 默认正常日志用 console.info，成功句式用 Succeeded；与项目不同时按项目约定。属于低级风格，不影响代码合法性，不能把 console.log 说成编译错误。 |
| 5.5 回调和废弃 API | 依赖词法 this 的示例优先箭头回调；需要动态 this 的回调不能机械改箭头。废弃接口以匹配版本标记核对，解释旧 API 的迁移示例可以保留旧调用并明确用途。 |

报告例：`sample.md:8` 的 console.log 与默认 5.4 不符→低，建议 console.info；“某模块在 API 12 不存在”若只有 API 13 SDK→未验证，不把猜测与风格问题一起计高。
