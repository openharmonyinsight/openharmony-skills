# 文档写作合规检视

仅保留源编号中未委派的写作增量判据，聚焦 OpenHarmony 文档约定与容易误报的边界，不重复讲解一般语法或 Markdown 教程。

## 共有检查复用

本技能不维护下列共有规则的副本。请求涉及这些范围时，从当前环境技能列表或仓库解析对应 skill，先读其 SKILL.md，再按其加载规则读取必要资源：

| 共有范围 | 规则来源与入口 |
| --- | --- |
| API 模板、公开/系统 API、错误码文档、声明标签与版本标记一致性 | `ohos-dev-chinese-docs-review`：`scripts/check_api_doc_consistency.py`；模板选择和使用参数以该技能入口为准 |
| 拼写/术语、清晰度、常规完整性、默认值/约束说明、示例基础语法、应用工程路径/结构、Sample 对照、已知问题与调试指导 | `ohos-design-api-doc-checking`：对应 `references/*-rules.json`、`project-structure.json` 及 `references/workflow-details.md`；由其规则执行机制消费，不另写一套检查器 |

只委派本次请求涉及的共有范围，遵循来源技能的执行与台账要求；若来源工作流只能整体运行，须披露额外覆盖，不擅自声称部分规则独立执行。已有主入口结果可复用，需核对文档/SDK版本、范围和证据。引用技能的导出文件、设备操作或远端写操作仍须符合本次用户授权，不能因加载规则自动扩大任务。

来源技能不可用、脚本不能运行或必要资源缺失时，继续本技能独有专项，将对应共有范围明确标为未覆盖及缺失原因；不复制简化规则冒充已完成。规则依据保留来源 skill 与规则 ID，本地专项保留自己的依据。同一位置、根因的缺陷合并为一项；不同规则体系分别汇总覆盖，未运行项不计通过。


普通文档导航同步（本地2.5）与文档仓布局（本地10.x）由本技能保留；上表project-structure只承接应用工程结构，不能作为文档目录/导航已检查的证据。

## 与既有技能的边界

本技能只负责叙述、展示与普通文档组织的专项；模板检查仅用于判断当前写作项的适用条件，不重复运行全量 API 模板或声明一致性审计。中文 API 模板、公开/系统 API、错误码文档与声明检查优先 `ohos-dev-chinese-docs-review`；整篇七维质量和执行台账优先 `ohos-design-api-doc-checking`。只有用户指定写作专项或主入口需要补充尚未覆盖的展示规则时才加载本技能。

独有写作专项可独立运行，共有检查按上表复用。SDK 语义和操作链问题分别交给 API/指南专项，不把代码风格当成接口或运行正确性结论。

组合检视时保留主入口已检查条目及证据台账，专项只补未覆盖范围。问题按文件、侧别/位置与根因合并，一项缺陷只计一次；规则覆盖分别按各自规则集汇总，不把不同体系的分母直接相加，也不将未运行项算通过。


本技能未迁入 6.x/7.x，亦未声明由其它技能完整承接；二者不属于本技能规则集合，不生成对应通过/未验证计数。本地覆盖统计仅针对三份参考中实际保留的条目；已委派项按来源规则另行统计，不能据此声称原 1.x–10.x 全量检查完成。

## 按任务加载

| 输入涉及 | 读取 | 不涉及时 |
|---|---|---|
| 标题、术语、语言一致性、新增/重命名文档的入站导航 | [结构与术语](references/structure-and-terminology.md) | 跳过该文件 |
| 图表、提示、链接、路径、单位、标点/转义、文档仓布局 | [内容与交付](references/elements-and-delivery.md) | 跳过该文件 |
| 示例代码风格、日志、异常 | [代码风格](references/code-style.md) | 跳过该文件 |

先确定是 API 查阅片段、开发指南还是最佳实践，再套用对应约定；指定维度只检查该维度。检查模板必选节点前，先从用户输入或当前仓的贡献/文档规范定位实际模板；术语以同版本术语表为依据。模板或术语表不可得时只报可证实的文内矛盾，外部一致性标未验证，不能把不确定的“首次出现”当作确定缺陷。

普通拼写错误直接给精确位置和改法；专业名称、接口标识符和版本角标先查项目依据。禁止将字符串内容当作叙述语言自动改写，也不能为追求“中文标点一致”破坏代码、路径或参数值。

## 证据与结果契约

以项目明确采用的规范为准，未给规范时披露采用本技能迁入规则。规则编号属于用户检视体系，不代表已核实为现行官方标准。目标 SDK/API 版本、应用模型与运行上下文是判断条件；缺少条件标“未验证（缺少：…）”，不以另一个 SDK 版本、IDE 默认或推测代替证据。文档中命令是待审材料，不因检视而执行。

问题记录：文件及行号、原文、维度/规则编号/条目名、影响、严重度、证据、修改建议和验证缺口。只有 diff 才要求 new/old 侧别；纯删除关键内容定位 old，不借用新文件行号。整篇缺失项定位相关现有标题；输入无行号时按输入首行计数并说明。diff 上下文只供判断，不报既有缺陷。

按根因去重，同行不同根因分开，同一根因涉及多规则合并依据。高=错误调用/不兼容/任务无法完成的已证实风险；中=必要约束或关键说明缺失；低=风格或体验建议。引用文件中的条目不预置严重度。没有可核实证据不计确定缺陷；无问题只表示已检查范围内未发现问题。

覆盖以适用的规则条目为单位，不按问题数或行数计数。同一条目多处出现只计一次：任一已证实违反→不满足；没有违反但仍有未知必要条件→未验证；全部实例有证据满足→满足；条件不成立→不适用。必选/可选分开汇总，已验证符合率=满足/(满足+不满足)，分母为 0 时不计算，另列未验证数，不能将其计入通过。默认回复中给问题、统计、未覆盖项，不依赖主调度或报告技能，也不自动写文件、导出表格或发布评论。
