## Step 6：生成报告

> 📖 **详细报告生成说明**: [ReportStructure.md](./ReportStructure.md)

**改进要点**：
1. 报告为 2 章节结构（一·hilog日志用例详情 + 二·总结）
2. 每个用例包含完整时间窗提取信息（所在日志文件、起始/结束行号）

**AI操作**：生成2章节标准报告

**章节结构（2章节）**：
- 一、hilog日志用例详情（每个失败/异常用例：基本信息 + 时间窗提取 + 源码→领域证据链 + 关键日志 + 源码分析 + 问题定界 + BLOCKED级联阻塞汇总）
- 二、总结（问题分类汇总 + 定界结论表格 + 建议流转）

**⚠️ 崩溃为根因时的报告结构**：

当检测到崩溃日志（cppcrash/appfreeze）且崩溃是FAILED和BLOCKED的根因时：
1. 在"一、hilog日志用例详情"最前面增加**崩溃分析节（1.1）**
2. 崩溃分析节包含：崩溃基本信息 + 崩溃时间线 + 崩溃调用栈 + 崩溃根因分析
3. 后续FAILED用例（1.2~1.N）引用崩溃分析节，标注"同根因"
4. 最后增加**级联阻塞汇总节（1.N+1）**，说明多少条用例因崩溃阻塞未执行
5. "二、总结"中所有问题归属标注为**系统侧**

**识别方法**：
```bash
# 检测崩溃日志（判断是否需要崩溃分析节）
ls <日志目录>/crash_log_*/ | grep -c "cppcrash"  # 崩溃次数>0则需要
ls <日志目录>/crash_log_*/ | grep "appfreeze"     # appfreeze=级联阻塞原因
grep -n "missed" <日志目录>/module_run.log         # missed=套件中断标志
```

> 详细报告结构见下方「崩溃作为根因时的报告结构」

**形态④（流程B）报告标注**：
- "二、总结"标注："形态④（hilog目录），缺少 module_run.log，无法确认执行状态"
- "一、hilog日志用例详情"标注（无源码时）："未提供源码，domain 推断自 testsuite 名"

**报告命名**：`XTS_Analysis_Report_YYYYMMDD.md`

**保存路径**：日志目录

## 报告生成前置门槛

> 生成报告前，AI必须自检以下条件，不通过则补执行对应步骤。规则详见 [constraints.md](../../references/constraints.md)。

| 检查项 | 通过条件 | 不通过时的处理 |
|--------|---------|--------------|
| 源码定位 | Step 2.5 已执行且有源码路径 | 必须提示用户提供；用户拒绝后降级为L1报告，标题标注"⚠️ 无源码分析（L1 降级）" |
| import提取 | Step 2.5.6 已执行 extract_imports.py | 如有源码但未执行，必须补执行 |
| domain查询 | map_domain.py 已查询 | 如有源码但未查询，必须补查询；无源码时用testsuite名推断 |
| 崩溃/冻结检测 | Step 2.7 已执行 | 必须补执行（检测cppcrash/appfreeze/missed） |
| appfreeze分析节 | 检测到appfreeze → 报告含BLOCKED类型A分析节（完整6段） | 补充appfreeze分析（读 [CrashAnalysis.md](../L0_PreAnalysis/CrashAnalysis.md) 冻屏分析） |
| BLOCKED计数交叉校验 | FAILED + BLOCKED + PASSED = Collected test count | 重新 grep "missed" + "BLOCKED" 核对，禁止漏算套件内missed |
| 分层统计完整性 | 每个FAILED用例含 主:N行\|P1:X\|P2:Y\|P3:Z | 用 filter_hilog.py --stats-only 补取 |
| 崩溃时间线完整性 | cppcrash文件数 = 时间线条目数 | 逐条补列（ls crash_log_*/cppcrash-*.log \| wc -l 核对） |

**禁止**：未执行源码定位 + 未标注L1降级就直接生成报告；未通过崩溃/冻结检测 + BLOCKED计数校验就直接生成报告

## 改进要点（20260714）

### 1. 报告为 2 章节结构

**说明**: 报告仅含"一、hilog日志用例详情"+"二、总结"两个章节，不生成执行概况/失败用例清单/数据库查询记录等多余章节。

**替代**: 执行状态判定（Step 3）作为内部分析步骤，用于决定是否进行hilog切片，不在报告中体现。

### 2. 失败用例直接在"一、hilog日志用例详情"中展示

**说明**: 失败用例详情直接在"一、hilog日志用例详情"中逐条展示（含同根因标记），不再单独列表。

### 3. 调整章节编号

**改进**: 从4章节简化为2章节：
- 一、hilog日志用例详情（原三）
- 二、总结（原四）

### 4. 总结改为问题分类视角

**原因**: 便于用户快速了解问题归属，区分测试侧和系统侧。

**新增内容**:
- 问题分类汇总（测试侧问题、系统侧问题）
- 定界结论表格增加"问题归属"列
- 流转建议区分测试侧和系统侧

### 5. 问题归属字段

**新增字段**: 定界结论表格增加"问题归属"列（测试侧/系统侧）。

**目的**: 明确问题责任归属，便于流转决策。

### 6. BLOCKED分类处理（2026-07-14新增）

**改进**: 将BLOCKED用例分为两类分别处理：
- **类型A（异常触发用例）**：引发阻塞的异常用例，按正常工作流完整6段落分析
- **类型B（级联阻塞用例）**：因异常未执行的用例，汇总说明

**原因**: BLOCKED通常是异常事件（崩溃/冻结）的级联影响，无需逐条分析被阻塞的用例。优先定位并分析异常触发点，修复根因后重跑即可。

**新增内容**:
- BLOCKED类型识别方法（时间分布、missed标记、崩溃日志）
- 级联阻塞汇总模板（阻塞概况 + 分布表格 + 阻塞链分析）
- 有FAILED+BLOCKED时的报告格式

## 报告生成流程

### AI 主动生成

AI 应按照以下步骤主动生成报告：

1. ✅ 阅读本文件（报告格式规范）
2. ✅ 根据 FailureAndSource.md 等各 Step 的输出产物组装报告内容
3. ✅ 确认报告为 2 章节结构（一·hilog日志用例详情 + 二·总结），不生成执行概况/失败用例清单等多余章节
4. ✅ 在"一、hilog日志用例详情"中展示所有失败用例（同根因标记）
5. ✅ 每个用例包含完整时间窗提取信息（日志文件、行号）
6. ✅ 在"二、总结"中区分测试侧问题和系统侧问题
7. ✅ 定界结论表格增加"问题归属"列
8. ✅ 保存到日志目录（`XTS_Analysis_Report_YYYYMMDD.md`）

### 禁止行为

- ❌ 不要生成多个报告文件
- ❌ 不要生成补充报告、最终报告等额外文件
- ❌ 不要在用例详情添加"问题根因汇总"、"定界结论"等冗余内容
- ❌ 不要遗漏失败用例（除非同根因已标记）
- ❌ 总结中不区分测试侧/系统侧问题

## 标准段落结构（每个失败用例）

每个失败用例详情节**必须包含以下6个标准段落**（按顺序排列）：

1. **基本信息** - 用例名、testsuite、执行序号、执行结果、消耗时间、所在日志（hilog）
2. **时间窗提取** - 所在日志文件、起始时间、起始行号、结束时间、结束行号、时间来源
3. ⚠️ **源码→领域证据链** - **独立段落**，必须包含：
   - 证据链表格（API | 子系统 | domain | 日志行 | 时间）
   - 证据链追溯图（源码→@ohos模块→子系统→domain→日志过滤）
4. **关键日志片段** - 带分层来源标记 `[主]`/`[P1]`/`[P2]`/`[P3]`
5. **源码定位与分析** - 源码位置（绝对路径）、源码片段、源码分析
6. **问题定界** - 问题类型、**问题归属（测试侧/系统侧）**、影响范围、定界依据、归属判定

**同根因用例特殊处理**：
- 标题追加 `[同根因用例]` 标签
- 包含：基本信息 + 时间窗提取 + 根因继承 + 问题定界
- 根因继承章节说明差异点（如有）
