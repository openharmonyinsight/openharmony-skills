## 一、设计原则：总分结构

知识库采用**三层总分结构**，每层的职责和约束边界如下：

```
Layer 0: references/subsystems/_common.md        ← 全局总（跨子系统通用规则）
         ├── Layer 1: Camera/_common.md           ← 子系统总（Camera 子系统整体约束）
         │   ├── Layer 2: cameraManager.md        ← 模块分（cameraManager 模块特有约束）
         │   ├── Layer 2: cameraInput.md          ← 模块分（cameraInput 模块特有约束）
         │   ├── Layer 2: Flash.md                ← 模块分（Flash 模块特有约束）
         │   └── ... (共 20 个模块文件)
         ├── Layer 1: image/_common.md            ← 子系统总（image 子系统整体约束）
         │   ├── Layer 2: imageSource.md          ← 模块分
         │   └── ...
         └── Layer 1: mediaLibrary/_common.md     ← 子系统总（mediaLibrary 子系统整体约束）
             └── Layer 2: PhotoAccessHelper.md    ← 模块分
```

### 各层职责定义

| 层级 | 文件 | 应包含 | 不应包含 |
|------|------|--------|----------|
| **全局总** | `subsystems/_common.md` | 跨子系统通用规则（测试框架、通用断言、@tc 注释规范等） | 特定子系统的 API、流程、权限等 |
| **子系统总** | `{Subsystem}/_common.md` | 该子系统下所有模块共享的规则（Kit 映射、语法模式、权限约束、通用测试流程、索引、**开发阶段定义**） | 特定模块的 API 测试规则 |
| **模块分** | `{Subsystem}/{Module}.md` | **仅**该模块特有的规则（API 测试场景、错误码、模块特有约束） | 已在 `_common.md` 中定义的通用规则 |

### 开发阶段定义（推荐）

各子系统应在 `_common.md` 中定义该领域的开发阶段，用于标注模块在流程中的位置：

| 子系统 | 阶段定义示例 |
|--------|--------------|
| **Camera** | 获取管理器 → 创建输入 → 打开相机 → 创建会话 → 创建输出 → 配置 → 测试 → 释放 |
| **image** | 创建 ImageSource → 创建 UnPacker/Packer → 编解码 → 释放 |
| **mediaLibrary** | 获取 PhotoAccessHelper → 查询资源 → 增删改 → 释放 |

### 总分之间的索引关系（设计要求）

```
                    ┌─────────────────────┐
                    │  subsystems/_common  │  Layer 0
                    └──────────┬──────────┘
                               │ 引用
              ┌────────────────┼────────────────┐
              ▼                ▼                 ▼
     ┌────────────┐   ┌────────────┐    ┌──────────────┐
     │Camera/_common│  │image/_common│   │mediaLib/_common│  Layer 1
     └──────┬─────┘   └──────┬─────┘   └──────┬───────┘
            │                 │                 │
     ┌──────┴──────┐         │                 │
     │ 模块索引表   │         │                 │
     │ (父→子索引)  │         │                 │
     └──────┬──────┘         │                 │
            │                 │                 │
     ┌──────┼──────┐         │                 │
     ▼      ▼      ▼         ▼                 ▼
   camMgr  camIn  Flash   imgSrc  ...    PhotoAccess  Layer 2
     │      │      │        │                │
     └──────┴──────┴────────┴────────────────┘
              │
              │ 父引用（子→父回链）
              ▼
     "通用规则见 ../_common.md §X.X"
```

| 索引方向 | 作用 | 当前状态 |
|----------|------|----------|
| **父→子索引** | `_common.md` 列出所有子模块文件清单及说明 | ❌ 全部缺失 |
| **子→父回链** | 模块文件引用 `_common.md` 获取通用规则，不重复内容 | ❌ 模块文件大量复制父级内容 |
| **子→子关联** | 模块文件标注依赖的其他模块 | ❌ 全部缺失 |
| **API→文件映射** | `_common.md` 提供 API 名称到模块文件的查找表 | ❌ 全部缺失 |

### 外部源文件与知识库文件的对应关系

每个模块文件对应三类外部源文件，需在模块头部正确声明：

```
.d.ts（API 声明文件）          ← 接口定义，参数类型、返回值、错误码的唯一权威
  ↓ 对应关系（由 _common.md 索引）
API 参考文档（.md）            ← OpenHarmony 官方文档，说明用法和示例
  ↓ 对应关系（由模块文件头部声明）
知识库模块文件（.md）          ← 本 skill 的测试规则文件
```

**三类文件正确命名**：

| 文件类型 | 示例 | 作用 |
|----------|------|------|
| **API 声明文件**（`.d.ts`） | `@ohos.multimedia.camera.d.ts` | 接口定义，参数/返回值类型，错误码声明 |
| **API 参考文档**（`.md`） | `arkts-apis-camera-Flash.md` | 官方文档，接口说明、用法示例 |
| **知识库模块文件**（`.md`） | `Camera/Flash.md` | 本 skill 的测试规则 |

**当前错误**：20 个模块文件头部将 API 参考文档错误标注为"API声明文件"：

```markdown
# 当前（错误）
> - API声明文件: arkts-apis-camera-Flash.md    ← 这是参考文档，不是声明文件

# 应改为
> - API声明文件: @ohos.multimedia.camera.d.ts  ← .d.ts 才是声明文件
> - API参考文档: arkts-apis-camera-Flash.md    ← 参考文档单独标注
```

## 二、现状与设计原则的偏差分析

### 2.1 偏差总览

| 设计原则 | 设计要求 | 实际状态 | 偏差程度 |
|----------|----------|----------|----------|
| **模块分只含特有规则** | 模块文件仅包含该模块特有的 API 测试规则 | 每个模块文件完整复制 `_common.md` 的通用规则（语法规范、try-catch、@tc 模板等） | 🔴 严重违反 |
| **子→父回链** | 模块文件通过引用声明继承父级规则 | 模块文件直接复制内容，无引用声明 | 🔴 严重违反 |
| **父→子索引** | `_common.md` 包含模块文件索引表 | 无任何索引 | 🔴 严重违反 |
| **全局总提取** | 跨子系统通用规则在 `subsystems/_common.md` 定义一次 | 三个子系统各自复制通用规则 | 🟡 部分违反 |
| **子系统总准确性** | `_common.md` 内容准确、引用有效 | 语法模式标注与内容矛盾、引用文件不存在 | 🔴 严重违反 |
| **模块分独立性** | 各模块文件只描述自身特有约束 | 模块间大量内容逐字复制 | 🟡 部分违反 |

### 2.2 偏差详解

#### 偏差 1：模块文件复制父级内容（最严重）

**设计要求**：模块文件（分）只包含该模块特有的规则，通用规则通过引用父级 `_common.md` 继承。

**实际情况**：以 Camera 子系统为例，20 个模块文件均完整复制了以下 `_common.md` 内容：

| 被复制的 `_common.md` 章节 | 每份行数 | 复制次数 | 冗余行数 |
|---------------------------|----------|----------|----------|
| §1.6 ArkTS 语法规范要求（6 条规则详细内容） | ~30 行 | 20 次 | ~600 行 |
| try-catch 结构要求 | ~15 行 | 20 次 | ~300 行 |
| @tc 注释模板 | ~10 行 | 20 次 | ~200 行 |
| 通用配置继承声明块 | ~8 行 | 24 次 | ~192 行 |
| **合计** | | | **~1,292 行** |

**应改为**：每个模块文件用一行引用替代：

```markdown
> 通用规则（语法规范、try-catch、@tc 注释等）继承自 [Camera/_common.md](./_common.md)，以下为 {Module} 模块特有约束。
```

#### 偏差 2：父→子索引缺失

**设计要求**：`_common.md` 作为子系统总文件，应在头部或尾部提供所有子模块的文件索引。

**实际情况**：Camera `_common.md`（551 行）未列出任何子模块文件清单，使用者无法从父文件发现子文件。

#### 偏差 3：子系统总内容准确性问题

**设计要求**：`_common.md` 作为父级权威来源，内容必须准确。

**实际情况**：

| 子系统 | 问题 | 详情 |
|--------|------|------|
| Camera | 语法模式标注与内容矛盾 | `_common.md:448` 写"静态语言语法规范"，但列举的 6 条规则（isEmpty()、`| undefined`、`!` 非空断言等）均为动态语法特征；引用文件 `modules/L1_Framework/arkts_standards.md` 不存在 |
| image | Kit 包名错误 | `_common.md:5` 写 `@ohos.multimedia.image`，应为 `@kit.ImageKit` |
| mediaLibrary | Kit 包名含后缀 | `_common.md:5` 写 `@ohos.file.photoAccessHelper.d.ts`，不应含 `.d.ts` |

**连锁影响**：9 个核心模块照抄了 `_common.md` 的错误标注，导致 10 个文件标注错误。而 11 个特性模块独立编写，标注为"动态"反而正确。

#### 偏差 4：外部源文件命名混淆

**设计要求**：模块文件头部应正确区分三类外部源文件（`.d.ts` 声明文件、API 参考文档、知识库文件）。

**实际情况**：20 个模块文件头部将 API 参考文档（`arkts-apis-camera-Flash.md`）错误标注为"API声明文件"，与真正的 API 声明文件（`.d.ts`）混淆。

```markdown
# 当前（错误）
> - API声明文件: arkts-apis-camera-Flash.md    ← 参考文档被误标为"声明文件"

# 正确写法
> - API声明文件: @ohos.multimedia.camera.d.ts  ← .d.ts 才是声明文件
> - API参考文档: arkts-apis-camera-Flash.md    ← 参考文档单独标注
```

**影响**：Agent 生成测试用例时可能找不到真正的 `.d.ts` 声明文件，导致参数校验、错误码断言等缺乏权威依据。

## 八、动静态语法差异支撑分析

### 8.1 工作流背景

参考 skill 的工作流采用**"先动态后转写"**模式：
1. **Phase 5 生成阶段**：先生成动态语法（ArkTS-Dyn, ets1.1）测试用例
2. **转写阶段**：将动态语法用例转写为静态语法（ArkTS-Sta, ets1.2）

### 8.2 子系统知识库应提供的支撑

**基础静态语法规范已在 skill 中**（不需要子系统知识库重复说明）：
- `references/conventions/arkts_standards.md` - 通用静态语法规范
- `modules/L2_Generation/generator/arkts_static_constraints.md` - 静态语法约束摘要
- `prompts/phase-5-generation.md` - 动态与静态模板关键差异

**子系统知识库应说明的内容**（如有差异）：
| 应说明项 | 说明 | 示例 |
|----------|------|------|
| **接口动静态差异** | 某些 API 在动态和静态语法下是否有不同的使用方式 | 例如：某些回调在静态语法下需要显式类型标注 |
| **场景差异** | 某些测试场景在静态语法下是否需要特殊处理 | 例如：ERROR_401 测试在静态语法下不生成 |
| **类型映射** | 动态语法中的类型在静态语法下的对应写法 | 例如：`number` → `int`/`double`，`any` → 具体类型 |
