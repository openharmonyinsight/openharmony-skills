# 阶段2：测试点生成规则

本文档包含Phase2测试点生成的详细执行规则，供AI Agent参考使用。

## NEVER（执行约束）

### 内容规范类
- NEVER 内部接口相关测试点——内部接口在phase1已拦截，phase2仅做自检处理
- NEVER 无数据持久化描述时生成数据存储测试点——仅当主单元场景或非功能需求明确出现持久化描述时才生成
- NEVER 在测试点描述中使用模糊量词（如"多个"、"部分"、"一些"）——必须明确具体数值或枚举
- NEVER 生成与需求不相关或冗余重复的测试点——测试点必须来源于Phase1输出，同一场景只允许一条测试点
- NEVER 对前置条件、测试手段、内部信息生成测试点——仅对Phase1输出的被测对象(功能特性)生成测试点，前置条件仅用于设置测试状态，测试手段仅用于触发被测行为，内部信息不可外部观测
- NEVER 滥用等价类或边界值分析的测试方法——仅对测试对象合理的使用测试方法，生成有价值/有意义的测试点（比如边界值仅当需求有明确范围约束时才生成）
- NEVER 非功能需求生成同一测试类型的多条测试点（性能、兼容性、稳定性、安全）——仅允许非功能需求的每种类型合并为一条测试点，无需用测试方法分析非功能需求，资料用例无需生成（phase4处理）

### ID与格式类
- NEVER 在面向执行者的内容列中使用内部追溯ID——内部ID仅出现在"来源"列，内容列使用自然语言描述
- NEVER 拆分策略声明缺失或与 phase1 不一致——必须从 phase1 输出继承并保持一致

### 覆盖与执行类
- NEVER 跳过低风险参数覆盖——所有有约束参数都必须覆盖，低风险标记为P3
- NEVER 将异常流程测试点标记为手工执行——异常流程是自动化的高价值目标，优先黑盒自动化
- NEVER 为已标注"适用说明"的异常场景重复生成测试点——跳过这些异常场景，来源标注"适用US-X异常场景"

### 执行模式类
- NEVER 中途出错或失败静默跳过——任一批次失败必须明确告警并记录后继续执行其他批次

## 执行规则

### 多轮并行处理机制（协调器执行）

协调器根据批次总数执行多轮并行spawn，每轮≤parallel_limit（4）个Agent。

**并行上限**：parallel_limit = 4（SKILL.md约束），每轮最多spawn 4个执行Agent

**轮次计算**：
```
轮次数 = ceil(batch_count / parallel_limit)
例：batch_count=10，parallel_limit=4 → 轮次数=3（第1轮4个，第2轮4个，第3轮2个）
```

**轮次执行流程**：每轮spawn≤4个Agent（注入knowledge_match.md路径+主单元ID），等待全部完成后启动下一轮，所有轮次完成后调用merge_batch_mds合并输出test_point_design.md（分配规则见下表）。

**每轮Agent分配规则**：

| 分配项 | 说明 |
|--------|------|
| **批次数量** | 每轮≤parallel_limit（4）个Agent |
| **注入文件** | knowledge_match.md路径（已更新，含§1.1交付推断结果和§2测试经验匹配结果） |
| **分配参数** | 测试对象主单元ID（从batches数组提取，仅为测试对象主单元生成batch） |
| **等待机制** | 当前轮次所有Agent完成后再启动下一轮 |
| **批次文件收集** | 协调器收集所有轮次的批次文件后统一合并 |

**规划Agent返回格式**：
```
批次规划完成：
| batch_id | unit_id | estimated_tps |
|----------|---------|---------------|
| batch_US_1  | US-01   | 15         |
| batch_US_2  | US-02   | 12         |
批次总数：X个
预计测试点总数：X个
经验库匹配完成：已追加到knowledge_match.md
```

**注意**：
- 规划Agent不再声明执行方式，协调器统一按多轮并行处理
- 执行Agent不关心轮次逻辑，仅负责生成测试点

### 执行Agent编号规则（强制执行）

**测试点ID格式**：
- 测试点ID格式：`TP-{主单元ID}-{序号}`
- 主单元ID转换：去掉连字符，如 US-01 → US01, US-02 → US02
- 示例：US-01的测试点 → TP-US01-001, TP-US01-002, ...
- 序号格式：3位数字，每个主单元独立编号，从001开始
- 合并后脚本统一重编号为 `TP-001~TP-N`
- **禁止使用不一致格式**（如 TP-batch1, TP-batch3, TP-batch_US_02）

**核心要点**：
- 每批次生成临时编号，合并时统一重编号
- 不输出汇总统计（脚本统一生成）

### 测试技术数据读取规则

**触发条件**：testing_technology.json存在。

**测试技术JSON格式**（`testing_technology.json`）：
```json
{
  "status": "success",
  "technique": "generate_all",
  "units": [{"unit_id": "US-01", "risk_level": "P1", "orthogonal_type": "非正交", "has_cond": true, "has_br": true}],
  "techniques": {
    "boundary_value": {"US-01": {"testpoints": [...], "total": 10}},
    "equivalence_class": {"US-01": {"testpoints": [...], "total": 8}},
    "decision_table": {"US-01": {"testpoints": [...], "total": 5}},
    "factor_combination": {"US-01": {"combinations": [...], "strength": 2, "total": 12}}
  },
  "trigger_rules": {
    "boundary_value": "has_cond",
    "equivalence_class": "has_cond",
    "decision_table": "has_br",
    "factor_combination": "orthogonal_type=非正交"
  }
}
```

**Agent 执行规则**：
1. Read testing_technology.json → 解析当前unit_id对应的技术数据
2. 按技术类别整合测试点：
   - **boundary_value**：边界值测试点（输入条件边界极值）
     - 来源标注：`边界值分析/BV-001`
   - **equivalence_class**：等价类测试点（有效/无效代表值）
     - 来源标注：`等价类划分/EQ-001`
   - **decision_table**：判定表测试点（规则覆盖）
     - 来源标注：`判定表/DT-001`
   - **factor_combination**：因子组合测试点（非正交组合）
     - 编号：使用脚本生成的COMB-XXX ID
     - 输入条件：组合值（如 `platform=OHOS5.0, mode=normal`）
     - 来源标注：`因子组合/COMB-001`
     - 测试类型：环境因子→兼容性测试，参数因子→功能测试
     - 风险评级映射：P0→3-way, P1/P2→2-way, P3→1-way
     - 覆盖率阈值：≥95%
3. 整合到测试点表格，按优先级排序
4. 若testing_technology.json缺失 → Agent自行按场景风险定向生成

## 核心理念与规则（AI必读）

### 生成理念：场景风险驱动

Phase2 不从参数出发穷举组合，而是从场景出发定向生成：
```
Phase1场景+耦合路径 → 风险识别 → 定向生成 → 覆盖率检查 → 定向补充
```

与穷举式生成对比：

| 维度 | 穷举式 | 场景风险驱动 |
|------|--------|-----------|
| 起点 | 参数→值构造→组合 | 场景→风险→定向测试点 |
| 覆盖保证 | 均匀穷举每个参数 | 高风险深覆盖、低风险浅覆盖、P3保留不丢 |
| 冗余 | 低风险参数同样2-3异常值 | 低风险1类异常值(P3)，不浪费执行资源 |
| 覆盖率角色 | 生成驱动 | 检查手段（生成后检查缺口，定向补充） |

### 风险分级规则（核心）

所有参数和场景都保留覆盖，不丢项，但深度按风险分级：

| 风险等级 | 优先级 | 适用对象 | 异常值覆盖深度 |
|---------|--------|---------|--------------|
| 高风险 | P0 | 安全/权限/核心业务逻辑/数据持久化 | 4-5类 |
| 中风险 | P1 | 重要功能/状态转换/组合约束 | 2-3类 |
| 低风险 | P2 | 辅助功能/默认值行为 | 1-2类 |
| 防御性 | P3 | 参数校验/格式检查 | 1类 |

**风险分级判定依据**（直接使用Phase1数据）：

| 判定维度 | 高风险信号 | 低风险信号 |
|---------|----------|----------|
| 业务规则(BR) | 涉及安全/权限/数据完整性 | 仅涉及UI展示/辅助信息 |
| 异常规则(EX) | 涉及数据丢失/系统崩溃 | 仅返回错误码/提示信息 |
| 字段关联(ASSOC) | 涉及条件互斥/状态依赖 | 仅涉及条件依赖 |
| 场景类型 | 异常场景/竞态场景/特殊场景 | 功能场景/展示场景 |
| 非功能需求 | 性能/稳定性/安全 | 无明确指标 |

### 可测试手段处理规则

Phase1 §2.4中的手段是可测试手段（外部入口/观测窗），US章节中的内容是被测对象。

**处理策略**：

| 信息来源位置 | Phase2处理策略 |
|------------|-------------|
| §2.4且被US引用的手段 | 正常测试设计策略（风险分析+场景定向），且该手段触发的功能生效效果必须作为预期输出的一部分验证 |
| §2.4且未被任何US引用的手段 | 补充到相关US或单独生成测试点 |
| US/TR章节中的被测对象 | 正常测试设计策略（风险分析+场景定向） |

### 测试对象测试策略（强制执行）

Phase1已在knowledge_match.md§1.1标注测试对象主单元，Phase2仅对测试对象生成测试点。采纳策略（语义匹配涉及特征→无标记/必测/选测二次判定）详见 `rules/knowledge_usage_guide.md` §2.2。

**Phase2执行要点**：
- 规划Agent仅匹配测试对象主单元的测试经验，knowledge_match.md表格保留完整内容
- 执行Agent生成测试点时：测试对象P0-P3全量覆盖
- 采纳策略：详见§知识库/经验库匹配规则及 `rules/knowledge_usage_guide.md` §2.2
- 测试对象判定来源：Read knowledge_match.md§1.1交付推断结果表

### 验证完整性原则（强制执行）

所有测试点的预期输出概要必须验证到外部可观测效果。若被测行为存在可外观测生效效果（配置生效、状态变更、数据持久化等），预期输出概要必须包含生效验证；若被测行为的逻辑终点即为可观测输出（如错误码返回），验证该输出即为充分。不得仅依赖"接口返回成功"等手段层反馈作为唯一预期结果。

### 知识库/经验库匹配规则（三层知识层级目录架构）

#### 阶段继承与层级隔离

**Phase2 Read knowledge_match.md → 读"测试经验匹配结果"表格 → 测试点补充**。

knowledge_match.md由Phase1生成（领域知识）+ Phase2规划Agent追加（测试经验），包含三段独立表格。Phase2仅读取"测试经验匹配结果"表格中的test-experience目录条目，禁止读取"领域知识匹配结果"或"用例细化匹配结果"表格。

**详细规则**：详见 `rules/knowledge_usage_guide.md`。

#### Phase2规划Agent匹配执行步骤

**核心原则**：基于Phase1分析的测试对象进行经验库匹配，而非关键词语义匹配。

> 统一流程（层级发现glob、沿层级从深到浅Read、语义匹配涉及特征score≥0.6、采纳策略、MCP/本地模式工具调用语法）详见 `rules/knowledge_usage_guide.md` §2-3。以下仅描述Phase2专属逻辑。

```
步骤1：Read knowledge_match.md §1.1交付推断结果表 → 提取测试对象主单元列表
步骤2：针对测试对象主单元匹配测试经验
       - 提取每个测试对象主单元ID（US-1, US-2等）
       - 按统一流程匹配test-experience目录（知识层级=test-experience，匹配字段=涉及特征）
       - 记录完整内容 + 关联US字段标注主单元ID
步骤3：输出匹配结果追加到knowledge_match.md §2（表格形式汇总，格式见knowledge_usage_guide.md §6）
步骤4：生成分批计划（仅以下主单元生成batch_id：写入类主单元 + 独立查询类主单元）

**查询类主单元判定**：
- 识别方式：主单元名称/API名称含 get/query/read/is/can/has 等查询类关键词
- 有前置依赖 → 不生成独立batch，合并到前置US验证
- 无前置依赖 → 生成独立batch，覆盖默认值/空状态
- 有独立异常逻辑 → 异常部分独立生成测试点（无论是否有前置依赖）

**分批计划排除**：有前置依赖的查询类主单元不生成batch_id，其验证合并到前置US的前置摘要中（混合校验拆分处理见§前后场景合并与聚合规则）。
```

- 补充测试点时遵循经验库的推荐测试技术、历史频率映射优先级
- 避免遗漏：确保经验库中的"需要测试"验证点全部覆盖
- 采纳前参照系检查（强制执行）：采纳经验"需要测试"验证点前，先提取当前US已生成AC/BR测试点的预期输出验证点集合作为参照系，对每条待采纳验证点做验证逻辑等价/子集检测。等价或子集则跳过采纳，来源标注"经验库/{条目ID}已由{TP-ID}覆盖"；父集则补充差异部分到已有TP，不新建

### 防重复规则

- 当输入条件和预期输出概要完全相同，仅测试技术/来源不同时，合并为一条测试点，测试技术选择风险分级版本，来源标注合并
- 测试点必须整合对应场景的所有规则约束，输入条件使用自然语言描述值类型（如"包名=256字符(边界极值)"），规则约束ID仅在"来源"列标注
- 基于风险分级生成的测试点与原场景测试点重合时，保留风险分级版本（含更完整的风险标注），删除原场景的简单版本
- 跨US重叠处理（强制执行）：区分"共享操作"与"共享验证"。多个US共享同一API/操作入口但验证不同副作用（如状态变更、事件发布、回调通知等不同观测目标）时**不可合并**，各US必须独立生成测试点。仅在验证目标完全相同且相似度≥85%时才可合并到最早出现的US，来源标注"合并到US-X处理（验证侧重点相同：XXX）"
- 跨US语义重叠检测（强制执行）：Agent必须主动扫描Phase1输出及已生成的其他US批次，检测语义重叠测试点。仅当满足全部条件才可合并：①相似度≥85%（非70%）②验证侧重点完全相同③共享验证而非共享操作。验证侧重点不同时独立生成，来源标注"独立生成（共享操作但验证不同：XXX vs YYY）"
- NF与AC/EX跨类型去重（强制执行）：非功能测试点（安全/性能/稳定性/兼容性）生成时，必须扫描同US已生成的AC/EX功能测试点，检测验证逻辑重叠。验证逻辑等价时删除NF测试点（仅保留AC未覆盖的独立量化指标部分，如性能阈值、持续时长），来源标注"合并到{TP-ID}（验证逻辑等价：{验证点描述}）"
- 验证逻辑等价/子集检测（强制执行）：两测试点文本相似度低但验证逻辑等价（验证目标语义一致，仅措辞/参数值/测试类型不同）或子集包含（验证点集合A⊆B）时，合并为一条，由AI语义判断，不依赖文本相似度。验证逻辑等价判定标准：①验证目标（预期输出中外部可观测效果的验证意图）语义等价 ②仅参数值/措辞不同 ③测试类型不同不影响判定

#### 前后场景合并与聚合规则

**前后场景合并**：同一主单元内存在前后场景关系时（如"开启→关闭→开启"），取并集合并为最完整流程，删除子集测试点，来源列标注合并来源（如"US1-AC1+AC2"）。

**场景聚合**：操作对象相同、验证链路连续、无环境切换的测试点可聚合为一条（避免测试跳跃），输入条件顺序排列，预期输出顺序验证，删除已聚合子集，来源列标注聚合来源（如"TP-001+002"）。

**不可聚合**：跨页面/跨API/需环境切换/需重新初始化的场景。

**跨US查询类操作合并**：当前主单元为查询/读取类操作（API名称含get/query/read/is/can/has等）且存在前置依赖时，查询验证合并到前置US的测试点预期输出中，不独立生成batch。前置US本身仍独立生成其测试点，预期输出概要中包含查询验证。

**混合校验拆分处理（强制执行）**：查询类操作同时包含查询验证和权限/安全等独立校验时，拆分处理：
- 查询验证部分 → 合并到前置US的测试点预期输出中
- 权限/安全校验部分 → 在执行Agent生成前置US测试点时，追加权限/安全校验测试点
- 来源标注："US-X-ACYz/权限校验"或"US-X-ACYz/安全校验"

**合并格式**：前置US测试点预期输出概要增加查询验证，如"状态设置成功，getXxx返回预期值"。

**来源标注**：
- 合并到前置US的查询验证："US-X-ACYz + 查询验证(US-Y)"
- 独立查询类默认值测试点："US-X-ACYz/默认值规则"
- 独立异常逻辑测试点："US-X-ACYz/异常逻辑"

### 测试类型判定规则

**核心原则（强制执行）**：测试类型由**影响后果**（failure consequence，即"如果该条件/行为失败，会导致什么后果"）决定，而非由测试动作本身决定。

**判定逻辑**：对每个测试点，问"如果被测行为失败/不满足，最严重的影响后果是什么？"，然后按后果归类：

| 影响后果 | 测试类型 | 说明 |
|---------|---------|------|
| 系统崩溃/进程挂死/内存持续增长/ANR | 稳定性测试 | 非功能故障导致系统不可用 |
| 安全机制被绕过/权限越权/数据泄露/隔离突破 | 安全测试 | 安全属性被破坏 |
| 量化指标不达标（延迟、吞吐、帧率等） | 性能测试 | 有明确量化性能指标 |
| 版本/设备/平台不适配 | 兼容性测试 | 跨环境适配问题 |
| 功能逻辑错误/数据错误/状态不一致 | 功能测试 | 默认类型，逻辑层面故障 |

**判定优先级**：稳定性测试 > 安全测试 > 性能测试 > 兼容性测试 > 功能测试

### 执行方式判定规则

| 执行方式 | 判定依据 | 示例 |
|---------|---------|------|
| 手工 | 黑盒自动化难以实现 | 功耗测试、后台待机、人工观察验证 |
| API性能自动化 | 性能测试含IPC/内存/写入速度指标 | IPC延迟、内存开销、写入速度测试 |
| XTS | OpenHarmony接口/组件白盒测试 | 接口参数校验、组件属性测试、事件回调验证 |
| 黑盒自动化 | 默认执行方式 | 功能测试、安全测试、并发测试、兼容性测试 |

**判定优先级**：性能测试含IPC/内存/写入速度指标 → API性能自动化; 接口/组件白盒测试 → XTS; 黑盒自动化难以实现 → 手工; 其他 → 黑盒自动化

**XTS判定标准**：
- 测试场景涉及OpenHarmony SDK接口直接调用（如@ohos模块API）
- 测试场景涉及组件属性设置、事件触发（如ArkUI组件属性、事件回调）
- 测试场景涉及白盒验证（如返回值校验、属性值校验、回调参数校验）

**黑盒自动化难以实现判断**：需人工观察验证（功耗、发热、视觉体验）、需环境切换（后台状态、设备切换）、需主观判断（文档准确性、用户体验）

## AI生成流程

### Step 1：场景风险识别

对每个主单元：

1. 读取 §X.2 资源关联，确定涉及的输入条件(COND)、字段关联(ASSOC)、业务规则(BR)、异常规则(EX)、SDK API、可测试手段(TM)
2. 检查是否存在"适用说明"标注：
   - 若标注"适用XX的全部异常场景"或"行为与XX一致" → 跳过这些异常场景的测试点生成
   - 记录跳过清单：`跳过场景=[异常场景ID列表]，原因="适用US-X异常场景"`
   - 异常场景应区分'新增逻辑的异常处理'与'已有功能的异常触发'，已有功能的异常触发不生成测试点
3. 读取 §X.3 被测场景（仅原文档明确描述，已跳过的异常场景不读取）
4. 读取 §2.2 耦合分析（正交/非正交判定 + 条件分表/组合真值表）
5. 对每个未跳过的场景和参数执行风险分级（按§风险分级规则表判定）
6. 对§2.4中被本主单元引用的手段，按§可测试手段处理规则纳入生效验证

### Step 2：定向测试点生成

对每个主单元，按§风险分级规则表生成测试点（深度遵循异常值覆盖深度列）：
- **P0**：覆盖全风险维度（输入/状态/交互/环境），每维度≥1条
- **P1**：覆盖核心异常路径+非正交耦合关键分支
- **P2**：覆盖常见错误模式，辅助功能边界值/默认值缺失
- **P3**：每个有约束参数1条代表性异常值

**链路覆盖（§2.4手段）**：手段生效验证已纳入相关测试点（见§可测试手段处理规则），不再单独生成"链路覆盖测试点"

**知识库匹配**：仅补充当前测试点未覆盖的风险模式

**资料测试点**（如有public API）：phase4会生成一条public接口资料测试用例（phase2无需处理）

**非功能测试点**（如有本US相关的非功能需求）：每个非功能需求合并为1条测试点（稳定性、兼容性、性能、安全）

## 输出格式规范（强制执行）

**表格列（必填）**：测试点ID | 测试场景 | 输入条件 | 预期输出概要 | 测试类型 | 测试技术 | 优先级 | 执行方式 | 来源

**格式要点**：
- 文件必须是 `.md` Markdown表格格式
- 表格行以 `|` 开头，测试点ID格式：`TP-{主单元ID}-{序号}`
- 输入条件/预期输出概要：自然语言描述，禁止内部追溯ID（COND-/TM-/VM-/BR-/EX-/ASSOC-等）
- 测试技术列：填写具体测试技术名称，若来源于testing_technology.json则标注完整ID（如"边界值分析/BV-001"）
- 来源列：结构化 `spec: {US/COND/API/TM 等内部追溯ID} ｜ 经验库: TE-..`（对抗补旧时追加 `｜ 对抗: {说明}` 段）；spec 段是内部ID唯一合法位置；用到经验库 TE 条目时填经验库段（仅编号），对抗补旧时填对抗段；无则整段省略
- 不输出汇总统计（脚本统一生成）
- 组合测试点融入标准表格，禁止与非组合测试点分表输出
