# 阶段2对抗：测试点对抗评估规则

## NEVER（执行约束）

### 数据真实性类
- NEVER 脱离脚本校验结果虚构覆盖率数据——必须调用脚本获取准确数据
- NEVER 脱离脚本初步识别结果虚构深度覆盖——脚本已基于关键词识别，AI需校验补充
- NEVER 脱离需求分析虚构关键场景深度权重——深度权重需基于实际测试点判断
- NEVER 脱离需求分析虚构变异语义相似——语义相似需基于实际测试意图判断
- NEVER 脱离test_point_design.md虚构重复检测结果——必须基于脚本输出的duplicate字段

### 循环对抗类
- NEVER 任一指标不达标时跳过循环对抗——必须循环补充（最多3轮）
- NEVER 超过3轮对抗循环——最多3轮，不达标则强制终止

### 补充生成类
- NEVER 脱离需求分析生成补充测试点——补充测试点必须基于遗漏项
- NEVER 补充测试点不追加到test_point_design.md——补充测试点必须追加写入test_point_design.md

### 重复检测类
- NEVER 跳过重复测试点检测——对抗评估后必须执行重复检测
- NEVER 跳过脚本校验——对抗评估必须先调用脚本获取基础数据

## 执行规则

### 基础数据（由脚本提供）

脚本自动计算：
- 测试点总数、被测场景总数、API接口总数、验证映射总数
- 需求覆盖率（被测场景+API覆盖）
- 关键场景分类统计（基础覆盖）
- 深度覆盖初步识别（脚本基于关键词，可能遗漏或误判）
- 变异体生成（含固定值过滤：权限2750、属组3823不生成±1变异）
- 变异杀死判断（精确覆盖+范围覆盖）
- 重复测试点检测（相似度≥95%精确检测 + ≥80%潜在检测）

### AI语义校验（混合模式）

#### 深度覆盖AI语义校验

脚本已基于关键词初步识别深度覆盖，但可能存在遗漏或误判。AI需进行语义校验：

| 校验类型 | AI判断标准 | 处理方式 |
|---------|-----------|---------|
| 遗漏补充 | 测试意图满足深度条件但无关键词匹配 | 增加深度分（+5分） |
| 误判移除 | 有关键词匹配但测试意图不满足深度条件 | 移除深度分 |

**深度覆盖语义判断标准**：
- 边界场景深度：测试意图是验证边界值附近的系统行为（如"验证参数刚好超出边界时的处理"）
- 异常场景深度：测试意图是验证异常发生后系统的恢复能力（如"验证失败后系统如何恢复"）
- 竞态场景深度：测试意图是验证并发场景的边界条件（如"验证多个操作同时发生时的边界行为"）
- 特殊场景深度：测试意图是验证安全/权限的深度隔离（如"验证跨用户访问被拒绝后的处理"）
- 数据持久化深度：测试意图是验证数据写入后的读取一致性（如"验证写入数据能否正确读取"）

#### 变异杀死语义相似判断

- 测试对象测试点测试意图 ≈ 测试对象变异体测试目标 → 语义判定=杀死
- 语义判定杀死 → 直接计入AI语义杀死数

> 说明：alive变异体已未被精确覆盖(60%)和范围覆盖(30%)杀死，AI语义判定为独立的第三杀死维度，确认语义相似即直接杀死，无需再叠加不可达的加权得分阈值。

## 风险加权计算规则

**覆盖率风险加权**：P0×4, P1×3, P2×1, P3×0.5
- 测试对象覆盖率 = Σ(已覆盖场景权重)/Σ(全部场景权重) × 0.7 + Σ(已覆盖API权重)/Σ(全部API权重) × 0.3

**关键场景基础分差异化**：
- 测试对象：P0(基础8+深度8), P1(基础6+深度6), P2(基础4), P3(基础2)

**变异杀死率风险加权**：P0×4, P1×3, P2×1, P3×0.5
- 测试对象变异杀死率 = Σ(已杀死变异体权重)/Σ(全部变异体权重)

## 测试经验覆盖验证规则（§2验证点纳入覆盖率维度）

Read knowledge_match.md §2测试经验匹配结果 → 提取TE条目的验证点(需要测试字段) → 按采纳规则判定是否为必覆盖项 → 检查测试点是否覆盖 → 计算经验覆盖率 → 作为覆盖率维度修正因子。

**采纳规则**（[必测]/[选测]为附加标注，无标注≠可跳过）：

| 采纳层级 | 标注 | 测试对象 | 说明 |
|---------|------|---------|------|
| 最深层级 | 无标注 | 直接采纳(视为必测) | 无标注时全部验证点视为必测 |
| 最深层级 | [必测] | 直接采纳 | 明确标注必测 |
| 最深层级 | [选测] | 语义匹配 | 仅测试对象按需采纳 |
| 父层级 | 无标注 | 语义匹配(选测逻辑) | 无标注按选测逻辑 |
| 父层级 | [必测] | 直接采纳 | 明确标注必测 |
| 父层级 | [选测] | 语义匹配 | 仅测试对象按需采纳 |

**历史频率→风险等级**：高→P0, 中→P1, 低→P2

**覆盖率修正公式**：
- modifier = max(0.7, 1 - 0.3 × (1 - 经验覆盖率/100))
- 覆盖率得分 × modifier → 最终覆盖率得分

## 三维度评分

| 维度 | 权重 | 计算方式 |
|------|------|---------|
| 需求覆盖率 | 40分 | 风险加权覆盖率×权重 |
| 关键场景评分 | 45分 | 风险等级差异化基础分+深度权重 |
| 变异杀死率 | 15分 | 风险加权杀死率×权重 |

**达标阈值**：总分≥80分（三维度加权求和）

### 需求覆盖率AI语义校验

脚本已基于关键词初步计算覆盖率，但可能存在遗漏或误判。AI需进行语义校验：

**对象类型区分**：
- 测试对象遗漏→必须补充（P0-P3全量）
- 经验[必测]或无标注(最深层级)遗漏→视为必测，必须补充
- 经验[选测]或无标注(父层级)遗漏→测试对象语义匹配补充

| 校验类型 | AI判断标准 | 处理方式 |
|---------|-----------|---------|
| 遗漏补充 | 测试点实际覆盖但脚本未识别（语义覆盖） | 增加覆盖率得分 |
| 误判移除 | 脚本识别为覆盖但测试意图未真正覆盖 | 移除覆盖率得分 |

**语义覆盖判断标准**：
- 被测场景覆盖：测试点测试意图与AC描述语义一致（如"验证目录创建"覆盖AC-1）
- API覆盖：测试点触发了API调用路径（如"创建目录"调用CreatePrintServiceDir）
- 规则覆盖：测试点验证了业务规则约束（如"仅驱动应用创建"验证BR-1）

**循环规则**：
- 最多3轮对抗
- 编号规则：TP-ADD-{NNN}
- 每轮重新调用脚本计算

## 重复检测处理机制（对抗达标后执行）

若脚本输出的duplicate字段存在exact_count或potential_count或cross_type_count或logic_equivalent_count > 0：

**步骤1：展示重复检测结果**

从phase2_adversary.json读取duplicate字段，展示：
- 精确重复（相似度≥95%）：X个，自动删除候选
- 潜在重复（相似度≥80%）：X个，需AI语义判断
- 跨类型候选（NF↔AC/经验↔AC）：X个，需AI验证逻辑等价判定
- 逻辑等价候选（相似度60-80%）：X个，需AI语义判断

**步骤2：AI语义判断与自动处理**

对potential_duplicates、cross_type_candidates、logic_equivalent_candidates进行语义判断，自动合并删除：

| 重复类型 | 判断标准 | 处理方式 |
|---------|---------|---------|
| 完全相同 | 执行方式相同 + 测试场景相似度≥95% + 输入条件相同 | 自动删除被合并测试点 |
| 逻辑等价 | 验证目标语义一致（预期输出中验证意图等价）+ 仅参数值/措辞/测试类型不同 | 自动删除被合并测试点 |
| 子集包含 | 验证点集合A⊆B（语义判定，A验证的所有内容B都验证了） | 合并为完整测试点，删除子集测试点 |
| NF↔AC跨类型 | NF测试点验证逻辑⊆或≡AC/EX测试点 | 删除NF测试点（保留独立量化指标部分），来源标注合并来源 |
| 跨来源（经验/对抗↔spec） | 来源不同（经验库/对抗 vs 当前需求规格）+ 测试意图相同 + 验证逻辑等价 | 合并为一（保留 spec 来源测试点），来源取并集（spec+经验库+对抗 段）；删除被合并测试点 |

**步骤3：自动合并删除执行**

- 完全相同/逻辑等价：直接删除重复测试点，来源列标注合并来源（如"合并自TP-XXX,TP-YYY"）
- 子集包含：将子集测试点的输入条件、预期输出概要合并到父集测试点，删除子集测试点，来源列标注合并来源
- NF↔AC跨类型：删除NF测试点（保留独立量化指标部分合并到AC测试点），来源标注"合并到{TP-ID}（验证逻辑等价）"
- 跨来源（经验/对抗↔spec）：合并为一（保留 spec 来源测试点），来源取并集（spec+经验库+对抗 段），删除被合并测试点

## 补充测试点生成规则

**生成原则**：
- 仅生成遗漏项对应的补充测试点
- 补充测试点明确标注依据（遗漏项来源）
- 编号规则：TP-ADD-{NNN}（顺延）
- 精简不冗余
- **补充优先级**：P0遗漏优先→P1→P2(≤3条)→P3(≤2条)
- 测试对象遗漏→P0-P3全量补充

**变异存活补充规则**：
- 仅补充phase1 §2.1明确定义的边界对应的测试点
- 明确标注变异体值（如"边界-1变异：timeout=59999"）
- 来源标注：在测试点来源末尾追加 `对抗: 变异存活（边界-1变异）` 段（保留原 spec+经验库 段）
- 禁止补充phase1未明确定义的边界扰动
- 禁止补充固定值参数的±1变异（已过滤）

**补充格式**：
```markdown
### 补充测试点（对抗评估第X轮）

| 测试点ID | 测试场景 | 输入条件 | 预期输出概要 | 测试类型 | 优先级 | 执行方式 | 来源 |
|---------|---------|---------|------------|---------|--------|---------|------|
| TP-ADD-001 | [内容] | [值类型] | [预期] | [测试类型] | [P0/P1/P2/P3] | [执行方式] | spec: {遗漏项来源} ｜ 对抗: 需求遗漏(测试对象-{US-ID})/关键场景遗漏(测试对象)/变异存活(测试对象) |
```

**补充提示**：
 * 使用`## 补充测试点（对抗评估第X轮）`标题
 * 来源标注遗漏原因（如"需求遗漏：缺少XX验证"、"关键场景遗漏：缺少XX边界"、"变异存活：边界-1变异"）
 * **NEVER 生成"对抗模型"来源的测试点，除非是以下情况**：
   - 需求遗漏：phase1未识别的测试场景
   - 关键场景遗漏：phase2已识别但未覆盖的边界/异常/竞态场景
   - 变异存活：phase2定义的变异体未被杀死
 * 标注"合并来源"后，必须删除原测试点（避免重复）
 * 棏查补充测试点编号是否冲突（与现有TP-XXX不重复）
 * 补充测试点后更新test_point_design.md的统计信息
 * 每轮对抗后更新对抗轮次
