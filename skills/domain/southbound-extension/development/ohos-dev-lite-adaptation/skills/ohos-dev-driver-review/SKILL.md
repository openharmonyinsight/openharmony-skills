## Trigger Signals

出现以下信号时应触发本 skill：

| 信号类型 | 典型表达 |
|---------|---------|
| 审查任务 | "审查这份驱动代码"、"深度审查（含 MISRA）"、"生成 review-report"、"合入前把把关" |
| 症状词（隐性需求） | "ISR 里调 printf 行不行"、"memcpy_s 这么写安全吗"、"会不会栈溢出"、"这个锁用对了吗"、"有没有硬编码密钥/越界风险" |
| 链式调用 | ohos-dev-rtos-migrate 迁移产出件质量把关、ohos-dev-hal-skeleton-gen 生成代码复查、适配工作流各阶段产出代码的门禁审查 |
| 同义表达 | 代码评审 / 静态审查 / 驱动代码 review / quality gate |

**不触发**（明确排除）：只修编译错误不改质量（走构建/诊断类 skill）；只需 lint 级风格微调不需结构化报告的编辑任务；审查非 C 驱动代码（规则集面向 C/MCU-L1 驱动）。

## Scope

本 SKILL 是 OpenHarmony Lite（L0 轻量系统 / L1 小型系统）芯片适配的**代码审查层**：读取驱动源码（.c/.h），对照 `references/review-rules.md` 中 FUNC（功能正确性）/ SEC（安全）/ EMB（嵌入式优化）/ MAINT（可维护性）/ STYLE（编码风格）/ MISRA（MISRA-C 合规）六大类规则逐条检查，识别 ISR 安全违规、栈溢出风险、缓冲区越界、DMA 对齐、CMSIS 合规等 MCU 特有问题，输出带严重度分级（CRITICAL / HIGH / MEDIUM / LOW / INFO）和修复建议的结构化审查报告。

**本 SKILL 做规则匹配 + 问题分级 + 修复建议，不自动修改代码**（修复由用户在 Agent 辅助下手动完成）。

### 审查覆盖清单

| 规则类别 | 规则 ID 范围 | 关注重点 | 适用系统 |
|---------|------------|---------|:---:|
| **FUNC** — 功能正确性 | FUNC-001 ~ FUNC-030 | HAL 接口一致性、CMSIS 合规、组件注册完整性、返回值检查 | L0/L1 |
| **SEC** — 安全规则 | SEC-001 ~ SEC-060 | 缓冲区越界、栈溢出、空指针、整数溢出、ISR 安全 | L0/L1 |
| **EMB** — 嵌入式优化 | EMB-001 ~ EMB-040 | 栈使用量、RAM/Flash 占用、DMA 对齐、低功耗模式 | L0/L1 |
| **MAINT** — 可维护性 | MAINT-001 ~ MAINT-020 | 函数长度、嵌套深度、注释完整性、Magic Number | L0/L1 |
| **STYLE** — 编码风格 | STYLE-001 ~ STYLE-040 | 命名规范、缩进、括号风格、文件头模板 | L0/L1 |
| **MISRA** — MISRA-C 合规 | MISRA-001 ~ MISRA-200 | MISRA-C:2012 规则（嵌入式安全编码标准） | L0/L1 |

**输入**：待审查代码（.c/.h）+ 系统级别 + 外设类型 + CPU 架构 + 审查深度（缺失项追问；系统级别可从代码特征自动判定）。
**输出**：结构化审查报告——6 类主分组（按严重度）+ 8 维交叉矩阵视图 + 质量评分 + 修复优先级；每条问题带规则 ID + 位置 + Before/After 修复建议。
**不适用**：非 C 驱动代码；自动修改代码（只审不改，修复由用户完成）；功能性运行时验证（编译/运行验证走 Step 6 提示用户执行）。

## Initial Checks

收到审查任务后，按以下顺序先做判断（各步结论决定规则集和审查深度）：

1. **审查范围收集**：待审查代码 / 系统级别 / 外设类型 / CPU 架构 / 审查深度——缺失项追问用户；只给代码时从代码特征自动判定。
2. **系统级别自动判定（L0/L1）**：代码特征判定——`pthread_mutex`/POSIX 文件 I/O（open/read/close）/realpath/malloc → L1（LiteOS-A / L1-Linux 用户态 HAL）；CMSIS 头/裸寄存器操作/`LOS_*` 内核 API → L0（MCU）。**用户显式指定优先**，覆盖自动判定。
3. **L0/L1 规则适用性筛选**：L1 → 排除 FUNC-002 CMSIS 合规、SEC-003 ISR 严格、SEC-002 栈溢出严格模式（防 Cortex-M 规则误报）；L0 → 排除 HDF/HCS 绑定检查、OSAL 接口检查。
4. **审查深度判定**：快速扫描（仅 SEC 关键 + FUNC 核心，报 C+H）/ 标准审查（默认，全 FUNC+SEC+EMB，C+H+M）/ 深度审查（含 MISRA-C:2012，全级别）。
5. **静态分析输入盘点**：`-Wall -Wextra` / `-fstack-usage` / cppcheck 结果有没有——有则作为审查输入之一，无则以人工规则匹配为主并注明。

## Prohibited Practices（禁止操作）

| 禁止 | 正确做法 |
|------|---------|
| **凭印象判断"这个写法应该没问题"而不对照规则** | 每条审查结论必须引用具体的规则 ID（如 `SEC-001: 缓冲区边界校验`），附规则原文 |
| **不区分 L0/L1 的驱动框架差异就审查** | L0 = IoT 外设驱动子系统（操作函数表如 GpioOperations、无 HDF/HCS）；L1 = 精简版 HDF（HdfDriverEntry + HCS 绑定）。审查时先判定系统级别 |
| 审查报告只列问题不给修复建议 | 每个问题必须附带修复代码示例（Before/After 对照） |
| 对 ISR 函数和普通函数用同一套规则 | ISR 函数额外检查：无阻塞调用、局部变量总大小 < 256B、无动态内存分配 |
| 忽略编译器 warning 级别的静态分析结果 | `-Wall -Wextra` + `-fstack-usage` 的结果作为审查输入之一 |
| 对 MISRA-C 规则不做优先级区分 | MISRA-C 规则分 Mandatory / Required / Advisory 三级，优先报告 Mandatory 违规 |
| 取不到的规则定义/最佳实践直接标 TODO 留空 | **先上网查（用宿主联网检索能力，WebSearch 或等价物；坏用备选联网检索 CLI，如 opencode）**，查到填依据并注明来源；确实查不到才标 TODO 并注明来源/查询关键词，禁止凭记忆编造规则或留空 |

## ② 工作流

### Step 1: 确定审查范围

审查开始前，收集以下信息（缺失项需追问用户）：

| 必填项 | 说明 | 示例 |
|-------|------|------|
| 待审查代码 | .c / .h 文件内容 | `uart_driver.c` |
| 系统级别 | L0 (LiteOS-M) / L1 (LiteOS-A / L1-Linux) | L0 |
| 外设类型 | GPIO / UART / I2C / SPI / ADC / PWM / RTC / Watchdog / WiFi | UART |
| CPU 架构 | 影响 EMB 规则（栈对齐/DMA 对齐/原子操作要求不同） | Cortex-M4 |
| 审查深度 | 快速扫描（仅 CRITICAL+HIGH）/ 标准审查（全规则）/ 深度审查（+MISRA） | 标准审查 |

### Step 2: 选择适用规则

Read `references/review-rules.md`，根据系统级别和外设类型筛选适用规则：

```
审查深度判定：
├── 快速扫描
│   └── 仅检查: SEC 安全关键规则 + FUNC 核心正确性规则
│       报告: 仅 CRITICAL + HIGH
│
├── 标准审查（默认）
│   └── 检查: 全部 FUNC + SEC + EMB 规则
│       报告: CRITICAL + HIGH + MEDIUM
│       STYLE 和 MAINT 作为 INFO 级别附加
│
└── 深度审查
    └── 检查: 全部六类规则（含 MISRA-C:2012）
        报告: 全级别
```

**L0 vs L1 规则差异**（审查前必须判定）：

| 规则 | L0 (MCU) | L1 (MPU) |
|------|:---:|:---:|
| CMSIS 合规检查 (FUNC-002) | ✅ 必须 | ❌ 不适用 |
| HDF/HCS 绑定检查 | ❌ 不适用（L0 无 HDF） | ✅ 必须 |
| OSAL 接口使用检查 | ❌ 不适用（L0 无 OSAL） | ✅ 必须 |
| 栈溢出风险 (SEC-002) | ✅ 严格（栈通常 < 4KB） | ⚠️ 宽松（MPU 栈更大） |

### Step 3: 逐项审查

Read `references/review-rules.md`（按适用规则逐条对照代码检查）。对每条规则：

1. **匹配**：用规则的检测方法检查代码
2. **判定**：违规 → 记录规则 ID + 严重度；合规 → 跳过
3. **修复**：违规时参照 `references/coding-standards.md` 找到正确写法，生成 Before/After 对比

### Step 4: 补充 MCU 专项检查

Read `references/review-rules.md` §3（SEC 安全规则）和 §4（EMB 嵌入式优化规则），针对 MCU 特有的风险模式额外检查：

#### ISR 安全专项（仅 L0 MCU）

| 检查项 | 方法 | 规则 ID |
|--------|------|:---:|
| ISR 中无阻塞调用（如 `LOS_SemPend` 带超时、`printf`） | 审查 ISR 函数体中所有函数调用 | SEC-003 |
| ISR 中局部变量总大小 < 256B | 统计 ISR 函数内所有局部变量的 sizeof 总和 | SEC-002 |
| ISR 中无动态内存分配（`malloc`/`LOS_MemAlloc`） | 搜索 ISR 函数中的内存分配调用 | 见 SEC-003 |

#### 栈溢出风险

| 检查模式 | 说明 |
|---------|------|
| 局部大数组 > 256B | 函数内定义 `uint8_t buf[1024]` 等大数组 |
| 递归调用 | 任何形式的直接/间接递归 |
| 函数栈用量 > 任务栈 × 0.5 | 使用 `-fstack-usage` 数据评估 |

### Step 5: 生成审查报告

参照 `references/review-examples.md` 的格式，按严重度分组输出。**生成前必须做去重 + 严重度校准 + 跨文件断言证据核查（见下）**：

```
审查报告结构：
1. 概述（审查范围、系统级别、审查深度、问题总数）
2. CRITICAL 问题（必须修复，阻塞合入）
3. HIGH 问题（强烈建议修复）
4. MEDIUM 问题（建议修复）
5. LOW/INFO 问题（可选修复 / 编码风格建议）
6. 优化建议（非违规但可改进的代码模式）
7. 8维报告双视图（6类规则主分组 ↔ 8维交叉矩阵，见 §④）
```

每条问题格式：
```
● [规则ID] [严重度] 问题简述
  位置: <文件名>:<行号>
  描述: <问题详细说明>
  当前代码: <违规代码片段>
  修复建议: <修复后代码片段>
  参考: references/review-rules.md §<规则所在章节>
```

#### Step 5b: 去重 + 严重度校准 + 跨文件断言证据核查（生成报告前必做）

| 检查项 | 方法 | 级别 |
|--------|------|:----:|
| **去重检查** | 同一 bug（同一文件同一行号的同一根因）**不拆成两条**计数。若两规则角度不同但指向同一处代码（如 SEC-001 缓冲区越界 + FUNC-005 返回值未检查都指向同一 `stat()` 未检查），合并为一条、标注多规则 ID，**禁止为"突出某级别"故意拆分**导致总数虚高。去重后的问题总数须与报告概述一致 | ERROR |
| **严重度校准** | 每条严重度须与**实际风险**匹配，不偏严也不偏松。校准原则：① CRITICAL 限"可致 HardFault/安全漏洞/数据损坏/静默成功"——失败路径的少量内存泄漏、非持续的首次填充竞争窗口一般属 HIGH；② HIGH 限"功能正确性风险/资源泄漏/CMSIS 违规"——本地 flash 上极少失败的 `close` 返回值忽略、可维护性问题（函数重复/不可达代码）一般属 MEDIUM；③ MEDIUM 限"可维护性/次优实现"——纯格式对齐、单条中文注释一般属 LOW/INFO。偏严（CRITICAL 当 HIGH）和偏松（MEDIUM 当 HIGH）都须修正 | ERROR |
| **跨文件断言须出示等价证据** | 审查报告里若断言"函数 A = 函数 B"（如 `hal_pms.c:97 的 GetSerial()` 即 `hal_sys_param.c:31 的 HalGetSerial`）但**两函数名不同**，必须出示等价证据（宏展开/头文件 `#define` 映射/typedef 别名/调用链追溯），不能凭"大概同名"断言。无法出示证据时，断言须标注"等价性未验证"或改为"疑似调用 X，待核实"，**禁止未验证即当作同函数写入报告**。核心 bug（如无锁静态缓存竞争）若独立成立，断言瑕疵不影响结论但仍须补证或降级表述 | ERROR |
| **描述准确性自检** | 每条引用的文件名/行号/代码片段回查原始源码核实属实（行号差 1、标题自相矛盾、代码片段编造均须修正）；"审了但没发现问题"的近空操作条目降级为 INFO 或删除，不当问题列出 | WARNING |

### Step 6: 编译验证

审查通过后告知用户编译验证：

```bash
# 启用全部 warning
./build.sh --product <product_name>
```

建议附加静态分析（如有条件）：
- `arm-none-eabi-gcc -fstack-usage` → 每函数栈用量
- `cppcheck --enable=all` → MISRA-C 合规扫描

## ③ 审查规则速查

快速回忆用。完整规则定义和检测方法见 `references/review-rules.md`。

### 六大规则类别

| 类别 | 关注领域 | 典型规则示例 |
|------|---------|------------|
| **FUNC** 功能正确性 | HAL 接口一致性、CMSIS 合规、组件注册、状态机 | FUNC-001: HAL声明与实现一致; FUNC-005: 返回值检查 |
| **SEC** 安全 | 缓冲区边界、栈溢出、空指针、整数溢出、ISR 安全 | SEC-001: 缓冲区边界校验; SEC-002: 栈溢出风险 |
| **EMB** 嵌入式优化 | 栈用量、RAM/Flash、DMA 对齐、低功耗 | 局部大数组检测、函数栈用量评估 |
| **MAINT** 可维护性 | 函数长度、嵌套深度、注释、Magic Number | 单函数 ≤ 50 行; 嵌套 ≤ 4 层 |
| **STYLE** 编码风格 | 命名规范、缩进、括号、文件头 | 函数名小驼峰; 宏全大写+下划线 |
| **MISRA** MISRA-C:2012 | 嵌入式安全编码标准（Mandatory/Required/Advisory） | 共 ~200 条规则 |

### 严重度分级

| 级别 | 含义 | 处理要求 | 阻塞合入？ |
|------|------|---------|:---:|
| **CRITICAL** | 可导致 HardFault / 安全漏洞 / 数据损坏 | 必须立即修复 | ✅ 是 |
| **HIGH** | 功能正确性风险 / CMSIS 违规 / 资源泄漏 | 强烈建议修复 | ✅ 是 |
| **MEDIUM** | 可维护性问题 / 次优实现 | 建议修复 | ❌ 否 |
| **LOW** | 编码风格建议 | 可选修复 | ❌ 否 |
| **INFO** | MISRA Advisory 级别 / 优化建议 | 参考 | ❌ 否 |

### L0/L1 审查重点速判

| 审查维度 | L0 轻量系统（MCU） | L1 小型系统（MPU） |
|---------|------------------|------------------|
| 驱动框架 | IoT 外设驱动子系统（操作函数表注册，如 GpioOperations） | 精简版 HDF（HdfDriverEntry + HCS 绑定） |
| ISR 限制 | 严格：无阻塞调用、局部变量 < 256B、无动态内存 | 宽松（GIC 中断模型不同） |
| 栈大小 | 典型 2-4KB/任务 | 典型 8-32KB/线程 |
| CMSIS 要求 | ✅ 必须检查 FUNC-002 | ❌ 不适用 |
| OSAL 要求 | ❌ 不适用（L0 不使用 OSAL） | ✅ 检查 OSAL 接口使用 |
| HCS 配置 | ❌ 不适用（L0 不使用 HCS） | ✅ 检查 match_attr 配对 |

### 编码规范速查

| 规则 | 要求 | 级别 |

## ④ 8维报告双视图（6类规则主分组 ↔ 8维交叉矩阵）

> **背景**：skills/ohos-dev-workflow-router/SKILL.md P6 用「8维」描述审查产出（正确性/安全性/规范性/性能/可测试性/可维护性/兼容性/文档），而本 skill 的规则引擎是「6类」（FUNC/SEC/EMB/MAINT/STYLE/MISRA）。两套体系不冲突——**6类是规则引擎（怎么查），8维是报告视图（怎么看）**。审查产出 = **6类主分组报告**（Step 5 §1-6，按严重度列问题）+ **6类↔8维交叉矩阵**（同一批问题按 8 维重新切片，方便不同角色按维度读报告）。映射是多对多。

### 双视图结构

```
审查报告 = ① 6类主分组报告（Step 5 §1-6，默认主视图，按严重度分组）
        + ② 8维交叉矩阵视图（本节，同一批问题按 8 维重新切片）
```

- **① 6类主分组报告**：审查引擎的原始产出，按 FUNC/SEC/EMB/MAINT/STYLE/MISRA + 严重度（CRITICAL/HIGH/MEDIUM/LOW/INFO）分组列问题。这是**主视图**，每条问题带规则 ID + 位置 + 修复建议。
- **② 8维交叉矩阵视图**：把 ① 的问题按 8 维重新归组，**不重新审查、不产生新问题**，只是换个切片。矩阵每格列出该维命中的问题编号（回链 ① 的规则 ID）。

### 8 维定义

| 维度 | 含义 | 关注角色 |
|------|------|---------|
| 正确性 | 功能逻辑对不对、HAL 接口一致性、返回值检查、状态机 | 功能开发 |
| 安全性 | 缓冲区越界/栈溢出/空指针/整数溢出/ISR 安全 | 安全/质量 |
| 规范性 | 命名/缩进/括号/文件头/MISRA 合规 | 代码规范 |
| 性能 | 栈用量/RAM-Flash 占用/DMA 对齐/中断延迟 | 性能优化 |
| 可测试性 | 能否写单测、依赖可注入性、副作用隔离 | 测试 |
| 可维护性 | 函数长度/嵌套深度/注释/Magic Number/模块耦合 | 维护 |
| 兼容性 | L0/L1 跨系统、CMSIS/OSAL 接口、HCS 配对、跨芯片移植 | 适配/移植 |
| 文档 | 注释完整性/API 文档/文件头/适配手册对齐 | 文档 |

### 6类 ↔ 8维 交叉矩阵（多对多映射）

> 映射是多对多：一条 6类规则可跨多个 8维（如 EMB 既算性能又算可测试性又算兼容性）；一个 8维可被多类规则覆盖（如规范性 = STYLE + MISRA）。**8维的"文档"和"兼容性"在 6类规则里覆盖稀疏，可能空格**——这本身就是信号（说明这两维没专门规则查，靠人工补）。

| 8维 ＼ 6类 | FUNC | SEC | EMB | MAINT | STYLE | MISRA |
|------------|:----:|:---:|:---:|:-----:|:-----:|:-----:|
| **正确性** | ✅ 主（HAL 一致/返回值/状态机） | ⚠️（空指针/越界影响正确性） | — | ⚠️（逻辑复杂度） | — | — |
| **安全性** | — | ✅ 主（越界/栈溢出/ISR 安全） | ⚠️（栈溢出风险） | — | — | ⚠️（安全相关 Mandatory） |
| **规范性** | — | — | — | ⚠️（注释/Magic Number） | ✅ 主（命名/缩进/括号） | ✅ 主（MISRA Required/Advisory） |
| **性能** | — | — | ✅ 主（栈用量/RAM-Flash/DMA/低功耗） | ⚠️（函数长度间接） | — | — |
| **可测试性** | ⚠️（状态机可测性） | — | ⚠️（DMA/硬件依赖可注入性） | ✅ 主（耦合度/副作用/依赖注入） | — | — |
| **可维护性** | — | — | — | ✅ 主（函数长度/嵌套/注释/Magic Number） | ⚠️（命名可读性） | — |
| **兼容性** | ⚠️（CMSIS/OSAL 接口跨系统） | — | ⚠️（栈对齐/DMA 对齐跨架构） | — | — | — |
| **文档** | — | — | — | ⚠️（注释完整性） | ⚠️（文件头） | — |

> ✅ = 该 6类规则是该 8维的主要覆盖；⚠️ = 部分覆盖；— = 6类规则里基本不直接查（空格即信号，靠人工补）。

### 矩阵视图输出格式

```markdown
### 8维交叉矩阵视图（同一批问题按维度切片）

| 维度 | 命中问题（规则 ID） | 数量 |
|------|---------------------|:----:|
| 正确性 | FUNC-005, FUNC-012, SEC-001 | 3 |
| 安全性 | SEC-002, SEC-003, SEC-007 | 3 |
| 规范性 | STYLE-004, MISRA-021, MISRA-088 | 3 |
| 性能 | EMB-005, EMB-018 | 2 |
| 可测试性 | MAINT-009 | 1 |
| 可维护性 | MAINT-002, MAINT-007, STYLE-004 | 3 |
| 兼容性 | — | 0 |
| 文档 | — | 0 |

> 兼容性/文档维 0 命中：6类规则对这两维覆盖稀疏，需人工补充审查（CMSIS/OSAL 跨系统、API 文档/适配手册对齐）。
```

### 规则

- **② 矩阵视图不重新审查、不产生新问题**——只把 ① 的问题按 8 维重新归组，每格回链 ① 的规则 ID。
- **一条问题可出现在多个维**（多对多）：如 `SEC-002 栈溢出风险` 同时算"安全性"和"性能"；`STYLE-004 命名` 同时算"规范性"和"可维护性"。
- **空格是信号不是错误**：8维的"文档"/"兼容性"在 6类规则里覆盖稀疏，矩阵这两维可能 0 命中——报告里标注"需人工补充审查"，别假装覆盖了。
- **主视图仍是 ① 6类主分组**：矩阵是辅助切片，方便测试/安全/性能等不同角色按维度读报告。修复优先级仍按 ① 的严重度（CRITICAL/HIGH/...）。

## Exceptions and Fallbacks（异常与兜底）

规则拿不到、证据不足、判定存疑时的处理规则（按场景）：

| 场景 | 处理 |
|------|------|
| **规则定义/最佳实践查不到** | 先上网查（用宿主联网检索能力，WebSearch 或等价物；坏用备选联网检索 CLI，如 opencode），查到注明来源；确实查不到才标 TODO + 注明查询关键词，**禁止凭记忆编造规则**（见 Prohibited Practices） |
| **跨文件断言（函数 A = 函数 B）无等价证据** | 出示宏展开/头文件 `#define`/typedef/调用链证据；无法出示 → 标注"等价性未验证 / 待核实"并列出核实路径（如"需提供头文件核实"），**禁止未验证即当同函数写入报告**。核心 bug 独立成立的，断言瑕疵不影响结论但仍须补证或降级表述（Step 5b） |
| **严重度拿不准** | 按 Step 5b 校准原则就低不就高并注明理由：失败路径内存泄漏 / 首次填充竞争窗口 → HIGH 非 CRITICAL；本地 flash 极少失败的 close 返回值忽略 → MEDIUM 非 HIGH；纯格式/单条注释 → LOW/INFO |
| **疑似 bug 但证据不足** | 不删也不定高级——降级表述（"疑似 X，待核实"）或列 MEDIUM 并注明核实方法，禁止为凑数升格为确定性结论 |
| **"审了但没发现问题"的项** | 降级为 INFO 或从问题清单删除，不当问题列出充数（Step 5b 描述准确性自检） |
| **行号/代码片段与源码对不上** | 回查原始源码修正（行号差、片段编造、标题自相矛盾均须修正）后再出报告 |
| **同一 bug 被多规则命中** | 合并为一条、标注多规则 ID，去重后总数须与报告概述一致——**禁止为突出某级别故意拆分**，也不能因整合漏报独立真 bug |
| **文件过大/过多** | 分批审查 + 汇总去重，概述统计以去重后为准；MISRA 全量规则只对齐深度审查档，快速扫描不硬跑 |
