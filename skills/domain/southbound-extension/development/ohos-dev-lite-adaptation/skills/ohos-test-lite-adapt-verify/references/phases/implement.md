# 阶段 3 · implement — 实现改动

**前置**：已完成 analyze（有用户批准的提案 + tasks）。

**约定路径**：

- 目标代码仓：经 `ohos-ci-lite-deploy-burn/config.json` 配置的连接方式访问
- 提案文档：`xts_test/proposals/<proposal-id>/tasks.md`
- 本阶段在目标代码仓内改代码（不改本地副本，除非是 local 模式）

## 执行步骤

用任务清单跟踪，按 tasks 清单逐条推进。

### 1. 按 task 实施

读取 `tasks.md`，逐条执行：

**改动方式取决于连接模式**：
- **SSH 模式**：通过 SSH 用 `sed` / `cat >` / python 脚本在远程改文件，或 scp 本地改好的文件回远程
- **Local 模式**：直接编辑本地文件
- **Custom 模式**：按用户在 init 阶段描述的方式操作

**保持代码仓 git 工作区可追溯**（暂不提交，提交留给 summary 阶段）。

每个 task 完成 → 更新其状态为 done。

### 2. 代码规范 checklist（每处改动自检）

每处改动完成后，逐项检查：

| 检查项 | 标准 |
|--------|------|
| 命名风格 | 匹配周边代码（先读邻近代码再写） |
| 注释密度 | 与所在模块一致，非必要不增不减 |
| 缩进风格 | 匹配周边代码（tab/spaces/宽度） |
| 复用既有能力 | 不重复造轮子；优先用已有工具函数/宏 |
| 死代码 | 不引入新的未使用代码 / include |
| 错误处理 | 与所在模块风格一致 |
| 硬编码 | 不引入新魔数；用既有宏/定义/常量 |
| 内存安全 | buffer 大小、对齐、生命周期无回归 |
| 裁剪安全性 | 删除的代码确认无引用残留 |

不符合则当场修正。

### 3. 对照文档确认实现

逐条 task 核对：
- [ ] 改动文件是否正确
- [ ] 改动意图是否落实
- [ ] 预期收益是否合理（不做精确测量，留给 verify 阶段）

汇总本阶段实际改动清单（文件路径 + 改动摘要 + 预期 RAM/ROM 收益），
写入 `xts_test/reports/implementation_report.md`。

- [ ] 提案 tasks 全部实现并标记完成
- [ ] 代码规范 checklist 全部通过
- [ ] `implementation_report.md` 已生成（含完整改动清单）
