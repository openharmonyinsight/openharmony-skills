## 交互界面模板

> 本文件定义测试设计协调器的用户交互界面渲染格式（Markdown展示块），供编排器渲染使用。
> 配置问题、领域匹配流程、门控逻辑、计时报告等规则详见 SKILL.md 和对应 rules 文件，此处仅保留界面渲染模板。

---

### 1. 启动界面

> AskUserQuestion配置表、领域匹配流程详见 SKILL.md 启动流程章节。

配置完成后显示扫描结果：

```markdown
=== 测试设计协调器启动 ===

配置信息：
- 输入目录：{路径}
- 输出目录：{路径}
- 知识库：{领域选择结果}（通用固定加载。三层：领域知识→Phase1, 测试经验→Phase2, 细化步骤→Phase4）
- 用例编号起始值：{编号}

文档扫描结果：
- 需求文档：X 个（.md: X, .docx: X, .pdf: X）
- 输入目录验证：✓ 可读
- 输出目录验证：✓ 可写

正在初始化计时系统...
```

#### 1.1 领域选择展示（用户选择②领域后触发）

> 选择流程详见 SKILL.md 领域选择与确认章节。由用户选择领域，AI通过index.md索引定位条目。

```markdown
=== 领域选择 ===

可选择的领域：
- ArkUI（组件、动画、生命周期）
- ArkWeb（加载、导航）
- 元能力（生命周期、权限）
- 包管理（安装卸载、权限、应用管理）

通用经验库：固定加载（无需确认）
选择领域后，AI将通过index.md索引自动定位相关经验条目。
```

### 3. 阶段确认界面

> 各阶段确认策略（需确认/自动执行）详见 `rules/timing_rules.md`。

#### 3.1 需确认阶段（Phase1、Phase2Adv不达标时、Phase4Adv不达标时）

```markdown
=== [阶段名称]完成 ===

执行结果摘要：
- 主单元数：X 个
- 被测场景数：X 个
- API接口数：X 个（public接口，inner已过滤）
- 待确认项：X 个（如有）

输出文件：
- {输出目录}/requirement_analysis.md
- {输出目录}/knowledge_match.md（三段式：领域知识段+测试经验段+细化步骤段）

计时信息：
- Agent耗时：Xs
- 确认耗时：待记录
```

#### 3.1.1 Phase1 待确认项答疑展示（Phase1特有）

> 答疑交互规则（前置检查、分批策略、问题设计、选项生成规则、答疑结果处理）详见 `rules/phase1_clarify_rules.md`。

**分批答疑展示**（每批最多10个问题）：

```markdown
=== 待确认项答疑（第X/Y批） ===

待确认项列表：
```

**答疑结果处理**：用户回答后，协调器 Edit 更新 requirement_analysis.md（回写待确认项表格的"用户回答"和"回答来源"列，并根据影响范围回填到主单元场景表、参数规格表和字段关联图谱）。

#### 3.1.2 最终确认（所有需确认阶段共用）

使用 AskUserQuestion 询问：

| 问题 | 选项 |
|------|------|
| [阶段名]是否[正确完整/充分]？ | 确认完成，下一步 / 输入优化建议 |

**用户选择"确认完成，下一步"**：
- 记录 T4 时间（confirmation_completed_at）
- 保存检查点
- 进入下一阶段

**用户选择"输入优化建议"**：
1. 用户在"Other"文本框中输入具体建议
2. spawn Agent 执行增量修改
3. 修改后仅显示变更摘要
4. optimization_rounds += 1
5. 再次确认，直到用户选择"确认完成，下一步"

#### 3.2 自动执行阶段（Phase2、Phase3、Phase4、Phase5）

不暂停确认，仅显示摘要后自动进入下一阶段：

```markdown
=== [阶段名称]完成 ===

执行结果摘要：
- [指标1]：X个
- [指标2]：X个
- [指标3]：X个

输出文件：{文件列表}

自动进入下一阶段...
```

### 4. 对抗评估界面

#### 4.1 达标时（自动进入下一阶段）

```markdown
=== 对抗评估通过 ===

三维度评分：
| 维度 | 得分 | 阈值 | 状态 |
|------|------|------|------|
| 需求覆盖率 | X% (X分) | ≥95% (40分) | ✓ 达标 |
| 关键场景评分 | X分 | ≥85分 | ✓ 达标 |
| 变异杀死率 | X% (X分) | ≥50% (15分) | ✓ 达标 |

总分：X/100分

自动进入下一阶段...
```

#### 4.2 不达标时（需用户确认）

```markdown
=== 对抗评估未达标 ===

三维度评分：
| 维度 | 得分 | 阈值 | 差距 | 状态 |
|------|------|------|------|------|
| 需求覆盖率 | X% (X分) | ≥95% (40分) | -X分 | ✗ 未达标 |
| 关键场景评分 | X分 | ≥85分 | -X分 | ✗ 未达标 |
| 变异杀死率 | X% (X分) | ≥50% (15分) | -X分 | ✗ 未达标 |

总分：X/100分（达标线：80分）

缺失项：
- 未覆盖场景：[场景列表]
- 未覆盖API：[API列表]
- 存活变异体：[变异体列表]
```

使用 AskUserQuestion 询问：

| 问题 | 选项 |
|------|------|
| 是否补充测试点/用例以达标？ | 自动补充（最多3轮） / 查看详情后手动补充 / 跳过继续 |

**用户选择"自动补充"**：
- 进入对抗评估循环（最多3轮）
- 每轮补充后重新调用脚本评分
- 达标后自动进入下一阶段

**用户选择"查看详情后手动补充"**：
- 展示 adversarial_report.md 内容
- 用户手动输入补充内容
- 重新评分

**用户选择"跳过继续"**：
- 记录不达标状态
- 进入下一阶段

### 5. Demo流水线界面

#### 5.1 跳过条件判断

> 条件执行判断逻辑详见 SKILL.md 阶段3编排器执行流程。

```markdown
=== Demo流水线跳过判断 ===

执行方式统计：
- XTS：X 个测试点
- 黑盒自动化：X 个测试点
- API性能自动化：X 个测试点
- 手工：X 个测试点

判断结果：全部测试点为XTS → 跳过Demo流水线

⏭️ Demo流水线已跳过（无需Demo）

自动进入Phase4...
```

#### 5.2 执行Demo流水线

```markdown
=== Demo流水线启动 ===

输入：
- 测试点设计：{输出目录}/demo_test_points.md（仅包含非XTS测试点）
- 需求分析：{输出目录}/requirement_analysis.md
- 领域名称：{领域}

子阶段进度：
✓ 子阶段1：Demo UI设计（已完成）
✓ 子阶段2：Demo代码生成（已完成）
→ 子阶段3：编译验证与修复（进行中）
○ 子阶段4：完成

Demo UI设计摘要：
- Demo页面：X 个
- UI控件：X 个
- 操作模式：X 种
- 测试点覆盖率：X/X (XX%)

Demo代码生成摘要：
- 源文件数：X 个
- 控件ID数：X 个
- 权限声明：X 项
- MCP知识库查询：控件专项 X 次 + 通用知识 X 次
```

#### 5.3 编译验证异常处理

> SDK缺失/HVIGORW_NOT_FOUND/BUILD FAILED处理流程详见 SKILL.md 阶段3编排器执行流程。

```markdown
=== 编译验证异常 ===

编译状态：SDK版本过低

缺失API清单：
- API1：{完整名称}
- API2：{完整名称}
- ...

处理建议：需用户选择：
1. 替换SDK后重新编译
2. 跳过编译验证，继续后续流程
```

### 6. 门控检查失败界面

> 门控检查点、触发时机、未通过处理详见 `rules/gate_rules.md`。

```markdown
=== 门控检查未通过 ===

门控类型：[门控类型]
检查项：[检查项名称]
失败原因：[详细描述]

处理选项：
```

| 门控类型 | 问题 | 选项 |
|---------|------|------|
| 输出文档缺失 | 文件{文件名}不存在，如何处理？ | 重试生成 / 终止执行 |
| 数据空值 | 主单元数=0且被测场景数=0，请确认文档格式 | 重新检查文档 / 终止执行 |

### 8. 恢复界面

从检查点恢复时：

```markdown
=== 从检查点恢复 ===

检测到历史执行记录，可用的检查点：

| 检查点 | 阶段 | 时间 | 输出文件状态 |
|--------|------|------|-------------|
| phase1_requirement_checkpoint.json | Phase1：需求解析 | 2026-06-25 16:01 | ✓ 全部存在 |
| phase2_testpoint_checkpoint.json | Phase2：测试点生成 | 2026-06-25 16:15 | ✓ 全部存在 |
| phase3_demo_checkpoint.json | Phase3：Demo流水线 | 2026-06-25 16:30 | ✗ 输出文件缺失 |

恢复建议：从 Phase3 重新执行（Phase2 检查点为最后一个有效检查点）
```

使用 AskUserQuestion 询问：

| 问题 | 选项 |
|------|------|
| 是否从检查点恢复？ | 从Phase3恢复执行 / 从Phase1重新开始 / 查看检查点详情 |

**用户选择"从Phase3恢复执行"**：
- 读取 phase2_testpoint_checkpoint.json 的 outputs 字段
- 验证所有输出文件存在
- 从 Phase3 开始执行

**用户选择"从Phase1重新开始"**：
- 清理已有输出文件（询问用户确认）
- 从 Phase1 开始执行

**用户选择"查看检查点详情"**：
- 展示检查点文件内容（timing_snapshot、outputs、error_history）
- 再次询问恢复选项

### 9. 错误处理界面

```markdown
=== 任务执行失败 ===

任务名称：[阶段名称]
错误类型：[错误类型]
错误信息：[详细错误描述]

重试信息：
- 已重试：X次
- 最大重试：3次
- 重试间隔：指数退避（1s → 2s → 4s）
```

使用 AskUserQuestion 询问：

| 问题 | 选项 |
|------|------|
| 如何处理执行失败？ | 重试任务 / 查看错误详情 / 终止执行 |

**用户选择"重试任务"**：
- 重新 spawn Agent 执行当前阶段
- 重试次数累加

**用户选择"查看错误详情"**：
- 展示 error_history 内容
- 再次询问处理选项

**用户选择"终止执行"**：
- 保存当前检查点（即使失败）
- 记录失败状态到 task_history.json
- 输出终止摘要
