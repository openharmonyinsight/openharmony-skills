# 阶段1：需求解析规则

## NEVER（执行约束）

### 内容规范类
- NEVER 输出推导性内容或实现层信息——只输出文档明确描述的黑盒可验证行为
- NEVER 推导未明确的业务逻辑/错误码/业务场景——零推导原则
- NEVER 应用测试设计方法（等价类/BVA/错误推测/判定表）——属于phase2职责
- NEVER 未识别spec格式信号时硬套用户故事结构——必须先执行格式探测
- NEVER 将spec原文表格直接拷贝到输出——必须经过分析提炼，附加增量信息
- NEVER 将文档验证类US作为主单元分析——文档验证类US（验证目标为"API参考文档内容"、"d.ts签名完整性"、"示例代码可执行性"等文档检视行为，而非功能性行为）不纳入主单元章节、不提取输入条件、不生成耦合分析、不生成被测场景，仅在§1需求概述的变更范围概要中标注"文档验证类US: {US编号列表}，Phase4统一生成资料用例"

### 输入输出过滤类
- NEVER 内部接口（Inner API/internal标记）——严格执行inner接口过滤
- NEVER 内部变量/内部状态作为输入，内部处理机制/内部流转作为输出——IBO原则
- NEVER 遗漏上下文条件——权限/功能/异常规则中存在的隐式输入条件必须提取
- NEVER 将跨US前置状态作为输入条件列入§2.1——必须标注为前置依赖，说明来源US和取值空间
- NEVER 可测试性手段混入SDK API表——归入§2.4

### ID与格式类
- NEVER 主单元ID不连续/重复，条件ID重复，来源未标注——ID必须连续无间断
- NEVER 被测场景表含"拆分依据"列——仅输出原文档明确描述
- NEVER 内部追溯ID出现在面向执行者的内容中——仅用于phase间追溯引用
- NEVER 在共享资源§2和主单元章节中重复输出相同信息——共享资源§2为权威来源，主单元仅引用ID

### 正交判定类
- NEVER 跳过正交判定——每个主单元必须判定正交/非正交并采用对应格式表述
- NEVER 正交时使用组合真值表——正交关系必须按条件分表表述，不得组合穷举
- NEVER 非正交时省略组合真值表——非正交关系必须穷举关键组合路径

### 跨US处理类
- NEVER 遗漏跨US场景重叠检测——当多个US涉及相同被测对象时，必须在主单元资源关联中标注"场景重叠"

### 待确认项类
- NEVER 工程常识可推断或逻辑互补可唯一确定的内容——无需待确认
- NEVER 待确认项不能回答"知道答案后能写出哪条原本写不出的测试用例"——必须验证价值

## 2. 共用规则

### 2.1 IBO原则

**定义**：黑盒测试视角，只提取外部可触发且可验证的行为

**纳入**：API调用/系统设置/用户操作传入；返回值/UI变化/回调/错误码观测
**过滤**：内部组件间传递/编译时配置/内部注册机制；内部状态变化/仅内部可感知的输出

**IBO过滤-跨US补充**：
- 跨US传递的中间状态（US-A的输出→US-B读取）属于内部状态，不作为US-B的"输入条件"
- 测试US-B时，需要先通过US-A设置前置状态——这是"前置依赖"，不是"输入"
- 前置依赖在主单元章节标注来源US和取值空间，不列入§2.1输入条件规格表
- 前置依赖的取值变化影响US-B的输出行为，但需通过前置US间接控制，不参与US-B的正交/非正交判定

### 2.2 零推导原则

- 禁止推导未明确的业务逻辑/错误码
- 禁止应用等价类/BVA/错误推测/判定表等测试设计方法（phase2职责）
- phase1仅输出原文档明确描述的场景

### 2.3 可测试性手段识别（强制执行）

**定义**：为触发/观测被测对象而提供的外部入口或操作方式。§2.4中的手段是可测试手段（外部入口/观测窗），US章节中的内容是被测对象。

**6类枚举**：CLI命令行、配置项修改、系统应用UI操作、环境状态变化、调试观测工具、辅助API测试桩

**提取步骤**：扫描识别6类手段 → 归入§2.4（禁止归入§2.3）→ 主单元引用时标注为"可测试手段"

**§2.3/§2.4边界**：`@ohos.xxx`模块导出的public SDK API→§2.3；CLI/配置项/UI操作/环境变化/调试工具→§2.4；InnerApi→过滤

#### 2.3.1 ID体系角色边界（强制执行）

**内部追溯ID（COND-/TM-/VM-/BR-/EX-/NF-等）仅用于phase间追溯引用**

**允许位置**：规格表ID列、耦合分析表列头/VM ID列、手段表ID列、主单元资源关联清单、phase2"来源"列、phase4"关联测试点"和"备注"列

**禁止位置**：被测场景WHEN/THEN、验收标准原文、测试步骤操作、预期结果、用例名称、预置条件

### 2.4 API过滤

**过滤关键词**：`inner`、`internal`、`_`前缀、`@internal`、`@deprecated`、`@system-api`、`@hidden`、"仅供内部使用"、"系统内部"

**完整流程**：
1. 提取前标注：扫描§API变更分析表的"开放范围"列，标记InnerApi
2. API条目删除：InnerApi接口不输出到§2.3 SDK API表
3. **参数连带删除**：InnerApi的参数不提取到§2.1输入条件表（强制执行）
4. 生成后二次检查：检查§2.1是否存在来自InnerApi的参数
5. 输出过滤说明：删除Inner接口数：X，删除参数数：Y

**编排器追问义务**：
- 若Phase 1 Agent输出"删除Inner接口数：X"但§2.1仍有来自InnerApi的参数 → 必须追问："为什么InnerApi参数仍在§2.1？请重新过滤"

### 2.5 输入条件规格提取

从spec文档提取全部影响输出的输入条件，包含直接参数和上下文条件两类。

#### 2.5.1 直接参数提取

**来源**：Public SDK API→§2.1标注"直接参数"；CLI命令参数→§2.1标注"CLI参数"；配置项参数→§2.1标注"配置项"；InnerApi参数→不提取

**追问清单**（提取参数前必须回答）：该参数所属API开放范围？用户能否通过外部操作控制？若InnerApi或系统生成值→不提取

#### 2.5.2 上下文条件提取（强制执行）

**来源**：从业务规则、功能规则、异常规则中识别隐式影响输出的前置条件

| 提取源 | 可识别条件 | 识别方法 | 分类 |
|--------|----------|---------|------|
| 权限控制规则 | 调用者身份/角色 | 含"权限""仅允许""授权"关键词 | 上下文条件 |
| 功能规则作用对象 | 对象属性条件 | "作用对象"列含前置属性 | 上下文条件 |
| 异常规则触发条件 | 被拒绝的条件 | "触发条件"列 | 上下文条件 |
| 默认行为规则 | 状态前置条件 | 含"默认""未配置""初始" | 上下文条件 |
| 另一个US的输出 | 跨US前置状态 | 值由另一个US产生，无法外部直接控制 | 前置依赖（不列入§2.1） |

**前置依赖判定**：值是否可由外部直接控制（不依赖其他US）？→是：上下文条件→否：前置依赖；值是否由另一个US输出产生？→是：前置依赖标注来源US→否：上下文条件

**注意**：上下文条件必须符合IBO原则和零推导原则；内部状态/变量不得作为上下文条件；跨US前置状态标注为前置依赖并说明来源US和取值空间

#### 2.5.3 输入条件规格表格式

| 条件ID | 条件名称 | 数据类型 | 取值范围 | 必填/可选 | 枚举值 | 默认值 | 条件类型 | 来源章节 |

- 条件ID：唯一编号COND-XXX，编号连续无间断
- 条件类型：直接参数 | 上下文条件

### 2.6 输入条件耦合分析（强制执行）

对每个主单元的全部输入条件（直接参数 + 上下文条件），执行正交判定并采用差异化表述格式。

#### 2.6.1 正交判定规则

**正交**：任一输入条件的变化**独立**影响输出，不依赖其他条件的取值。即：改变条件A的值，输出变化路径在其他条件取任何合法值时均相同。

**非正交**：某些输入条件的输出影响**依赖**其他条件的取值。即：条件A在不同上下文（条件B/C取值不同）下产生不同输出。

**混合型**：部分路径正交（如错误路径），部分路径非正交（如成功路径）。此时整体判定为**非正交**，但须标注正交子路径。

#### 2.6.2 正交关系的表述格式

正交时无需组合穷举。每个输入条件一张独立的"取值→影响"分表，内嵌验证映射关联：

```markdown
**正交判定**：正交
**判定依据**：每个输入条件的变化独立影响输出，不存在条件间耦合。

#### COND-XXX（条件名称）→ 独立影响路径

| 取值类别 | 具体取值 | 对输出的影响 | 关联AC | VM ID | 来源 |
|---------|---------|------------|--------|-------|------|
| 合法值 | [具体合法取值或范围] | [该取值下的输出] | AC-X.X | VM-XXX | §[来源章节] |
| 非法值 | [具体非法取值] | [该取值下的输出] | AC-X.X | VM-XXX | §[来源章节] |
```

N个条件 = N张分表，每表约2~3行（合法值行 + 非法值行）。验证映射信息直接内嵌，无需独立验证映射表。

#### 2.6.3 非正交关系的表述格式

非正交时必须组合穷举关键路径。包含3个组成部分：

**组成部分1：耦合路径说明**（自然语言描述）

```markdown
**正交判定**：非正交
**判定依据**：[哪些条件之间存在耦合，具体描述耦合关系]

**耦合路径说明**：

输出"[成功输出1]"需要同时满足：COND-XXX合法 + COND-YYY=特定值 + ...
输出"[成功输出2]"需要：[具体条件组合]
输出"[错误输出]"仅需：COND-XXX非法（与其他条件取值无关，此部分正交）

**耦合性质**：[纯非正交 / 混合型（部分路径正交，部分路径非正交）]
```

**组成部分2：组合真值表**（穷举非正交路径的关键组合，内嵌验证映射）

```markdown
#### 组合真值表（非正交路径）

| COND-XXX | COND-YYY | COND-ZZZ | 输出 | 关联AC | VM ID | 路径类型 |
|---------|---------|---------|------|--------|-------|---------|
| 合法 | 特定值A | 合法 | [输出A] | AC-X.X | VM-XXX | 成功路径（N条件耦合） |
| 合法 | 特定值B | 合法 | [输出B] | AC-X.X | VM-XXX | 成功路径（N条件耦合） |
| 非法 | * | * | ERR_XXX | AC-X.X | VM-XXX | 错误路径（COND-XXX正交） |
| * | 非法 | * | ERR_YYY | AC-X.X | VM-XXX | 错误路径（COND-YYY正交） |

注：`*` 表示该条件取值对当前输出无影响（正交子路径）
```

**部分3：正交子路径表**（混合型时）

```markdown
#### 正交子路径（可独立表述的部分）

| 条件 | 取值 | 独立影响 | 正交范围 |
|------|------|---------|---------|
| COND-XXX | 非法 | ERR_XXX | 任何其他条件取值下均独立生效 |
```

#### 2.6.4 执行步骤

1. 列出主单元涉及的全部输入条件（引用§2.5 COND-XXX）
2. 对每个条件判断输出影响是否依赖其他条件取值
3. 全部独立→正交（§2.6.2格式）；存在耦合→非正交（§2.6.3格式）
4. 检查混合型→判定为非正交，标注正交子路径

### 2.7 前置依赖→输出映射（跨US前置状态专用格式）

当前US存在跨US前置依赖时，前置依赖的取值变化影响输出行为，但前置依赖不参与正交/非正交判定（因需通过前置US间接控制）。用独立映射表表述：

```markdown
**前置依赖**：US-X的输出（描述，如"配置结果: enabled/disabled/not_configured"）
**控制方式**：通过US-X的TM-XXX间接设置前置状态，再触发当前US的TM-YYY

##### 前置依赖→输出映射

| 前置依赖取值 | 对输出的影响 | 关联AC | VM ID | 来源 |
|-------------|------------|--------|-------|------|
| 取值1 | [该取值下的输出] | AC-X.X | VM-XXX | §[来源] |
```

当前US既有输入条件又有前置依赖时，§2.2耦合分析包含两部分：输入条件耦合分析（§2.6）+ 前置依赖→输出映射（§2.7）。前置依赖和输入条件之间如果存在耦合，在耦合路径说明中标注。

### 2.8 待确认项生成（强制执行）

**缺口模板**（识别候选项）：

| 序号 | 缺口类型 | 描述 |
|------|---------|------|
| 1 | 有效值→无效值 | 有有效值行为但无无效值输出 |
| 2 | 正常路径→异常路径 | 有正常流程但无异常行为 |
| 3 | 存在阈值→边界极值 | 有范围约束但未明确上下界 |
| 4 | 有状态转换→缺失状态 | 转换矩阵不完整 |
| 5 | 组合条件→缺失分支 | 多条件组合结果未覆盖 |
| 6 | 可选参数→默认值 | 参数可选但无默认值 |
| 7 | 不传参数→处理方式 | 有传参行为但无不传参处理 |
| 8 | 手段覆盖完整性 | §2.4手段无法触发被测对象全部状态 |
| 9 | 手段生效可观测性 | 手段触发的行为缺乏外部可观测证据 |
| 10 | 手段与实际效果一致性 | 手段返回值与被测对象实际效果可能不一致 |

**过滤规则**：实现细节、实现机制、工程常识可推断、逻辑互补自明、已知豁免、已有足够信息

**价值检验**：每条候选项必须能回答"知道答案后能写出哪条原本写不出的测试用例"——能指出主单元和缺失预期输出→保留；否则→过滤。

### 2.9 验证映射提取

从spec.md"验收追溯"表格提取验证映射信息，内嵌到§2.2耦合分析的条件分表/组合真值表的"关联AC"和"VM ID"列中（无验收追溯表则不生成VM ID）。

每条验证映射分配VM-001~XXX编号，包含：AC编号、验证方式、验证重点、来源规则。此信息在耦合分析表中呈现，主单元章节不再重复输出独立验证映射表。

## 3. 格式探测规则

**spec格式信号**（命中+1）：标题含"用户故事/User Story/US-"；文本命中"作为.*我想要.*以便"；存在AC编号；AC与US编号关联

**判定**：≥2项→分支A（用户故事）；0-1项→分支B（功能规格）。多文档取多数派，混合格式按主格式处理，结果写入§1"拆分策略声明"。

## 3.5 变更范围识别规则（交付推断）

语义识别变更内容→标注测试对象，从DK条目提取已交付功能→写入knowledge_match.md§1.1。详细规则（变更标记识别、回归对象提取、交付推断输出格式）详见 `rules/knowledge_usage_guide.md` §11。

InnerApi仍严格执行过滤。当spec提及InnerApi变更时：标注InnerApi关联的US业务场景；无法分析关联US场景→加入待确认项告警

## 4. 分支处理规则

### 4.1 分支A：主单元=用户故事(US-X)

- 每个US独立成章节，ID沿用原文档编号
- 每个AC→一条被测场景，ID格式`USX-ACYz`
- 场景仅提取WHEN/THEN原文，不应用测试设计方法
- 一条AC含多种输入条件时合并为一条场景，由phase2拆分
- 未关联AC的规则处理：
  - 业务规则(BR)、异常规则(EX)、字段关联(ASSOC)等若未标注关联AC → 不做解析处理
  - 判断依据：规则描述中无AC编号引用，或规则表格中"关联AC"列为空
  - 处理方式：跳过该规则，不提取到输入条件、不生成耦合分析、不生成被测场景

### 4.2 分支B：主单元=功能规格(TR-XXX)

- 按功能点识别，ID连续编号；场景ID格式`TRXXX-SNN`；仅提取原文档明确描述的输入输出

## 5. 执行逻辑

1. 逐一读取输入文档
2. 格式探测→确定分支→记录拆分策略
3. 知识库语义匹配→语义识别变更内容→提取已交付功能→标注测试对象
4. 识别可测试性手段→归入§2.4
5. API过滤→排除inner接口（InnerApi不作为测试对象，但标注其关联的US场景提示）
6. 提取输入条件规格表（区分上下文条件vs前置依赖，前置依赖不列入§2.1）
7. 按分支识别主单元（可测试手段不作为主单元，仅在主单元资源关联中标注为外部入口；文档验证类US不作为主单元，仅在§1标注）
8. 对每个主单元执行输入条件耦合分析（§2.6 正交判定 + 差异化表述），同时将验证映射信息内嵌到条件分表/组合真值表
9. 对有前置依赖的主单元，生成前置依赖→输出映射（§2.7 格式）
