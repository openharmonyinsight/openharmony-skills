# 特性规格

> 固化用户可见行为和验收标准。复杂交互、状态机、异常流程可补充 Gherkin 场景。

> **不应包含：** 内部实现流程、中间件调用链路、框架层类名/方法名、内部性能指标（如函数执行时间、内存分配次数）。这些内容属于 design.md。Spec 只描述用户可见行为、API/InnerAPI 行为契约和验收标准；InnerKit/内部实现接口定义仍放在 design.md。
>
> **THEN 边界：** 每条 AC 的 `THEN` 必须能通过终端用户行为，或 Public / System / InnerAPI 三层接口边界的返回值、回调、错误码、事件或可查询结果直接判定。`THEN` 禁止描述内部数据结构、状态机转换、调用链、类/方法、缓存/队列、锁或算法；若必须读取内部状态才能判断是否通过，应把该内容移到 design.md 的状态、资源、并发或算法章节。
> 机器对内部实现词法只产生 WARN；合法引用错误码枚举、接口归属或源码名称而被误报时，可在 AC 行尾添加 `<!-- ext-ok -->`。该豁免会保留审计告警，必须在 `gate-checklist.md` 记录处理结论。
>
> **复杂度裁剪提示：** L0（简单）需求可精简填写"接口规格""多设备适配""全局特性影响"等章节（写"无新增接口规格"/"无差异"/"否"即可）；L1+ 需求涉及时必须完整填写。详细裁剪规则见 `gate-checklist.md` 按复杂度裁剪表。

## 规则定义

> 统一规则表，取消 FR/BR/EX/RC 四分类。类型标签：**行为**（正常路径下的系统行为）、**边界**（输入/状态的临界点）、**异常**（非法输入或异常状态的处理）、**恢复**（系统异常后的恢复策略；预期行为须写明恢复路径与恢复到何种状态，如重启子系统 / 回退到缓存 / 降级只读，时间约束写入边界/约束列）。
>
> **规则质量要求（每条规则必须满足）：**
> 1. **触发条件可复现** — 给出具体输入值或操作步骤，不允许"某些情况下"
> 2. **预期行为可观测** — 描述可从终端用户或 Public/System/InnerAPI 边界验证的结果（UI 状态/返回值/回调/错误码/事件），不允许"正确处理"，也不写内部状态变化
> 3. **边界值已标注** — 数值型必须写出边界点（=0/负数/最大值/精度）
> 4. **关联 AC 已填写** — 不允许孤立规则
> 5. **无重叠冲突** — 两条规则的触发条件不能覆盖同一输入范围且预期行为矛盾

| 规则ID | 类型 | 触发条件 | 预期行为 | 边界/约束 | 关联AC |
|--------|------|----------|----------|-----------|--------|
| R-1 | 行为 | [合法输入 + 正常状态] | [预期结果] | [约束] | AC-1.1 |
| R-2 | 边界 | [边界值条件] | [边界处理] | [精度/范围] | AC-1.3 |
| R-3 | 异常 | [非法输入/异常状态] | [忽略/降级/报错 + 错误码] | [超时阈值] | AC-1.2 |
| R-4 | 恢复 | [崩溃/断连/数据损坏] | [恢复路径(重启/回退/降级) + 恢复到何种状态] | [恢复时间约束/超时] | AC-2.1 |

## 验证映射

> 每个 AC 至少关联一个可执行测试入口。`Red 条件` 描述实现前测试为什么必然失败以及失败时可观察到什么，不得写“测试应失败”这种循环表述，也不得用尚未实现的 Mock/占位断言制造假 Red。
>
> 对纯规格补录或无代码行为变化的事项，可填写 `N/A：<具体理由>`；不得只写 `N/A`。实现后测试从 Red 转 Green 的实际结果和证据由 execution-plan / Verification Evidence 回填。

| 编号 | 对应规格项 | 测试入口 | 验证方式 | Red 条件（实现前失败信号） | 通过标准 |
|------|------------|----------|----------|---------------------------|----------|
| VM-1 | R-1 / AC-1.1 | `[测试文件::测试名 / XTS 用例 / 手工场景]` | 单测/集成/XTS/人工 | [旧行为、缺失接口、错误返回值或未触发回调导致的具体失败] | [精确输出/错误码/事件/用户结果] |

## 接口规格

> 供 code-gen 直接消费的接口行为定义。与 API 变更分析（声明层）互补，本节定义接口的调用语义、参数约束和行为场景。
>
> **与"API 变更分析"的信息边界：**
> - "API 变更分析"只回答"有哪些 API、什么级别、影响谁"（声明层，一行一个 API 的清单视图）。
> - "接口规格"回答"这个 API 怎么用、参数有什么约束、什么场景返回什么"（语义层，每个 API 的详细行为视图）。
> - "API 变更分析"的"入参概要/返回值/错误码范围"是概要级别的，"接口规格"的"参数约束/行为场景"是详细级别的。两者不要求重复填写——概要写清单，详细写行为。
>
> API 命名、参数设计、JSDoc 等通用规范遵循 `rules/architecture/` 的 API 规则；d.ts 位置、内部调用链等实现细节见 design.md。本节只承载 per-feature 的实例数据。
>
> 本节描述单接口级约束（参数、错误码、兼容性、安全校验等）。系统级指标（如 P95 响应时间、功耗、整体可靠性）写入"非功能性需求"章节。

## 行为场景（可选，Gherkin）

> **与"接口规格 → 行为场景"表的关系：** 两者信息高度重叠，按复杂度二选一，不要同时填写。
