# 故障注入手段

填写「故障注入建议」列时，从本文选取手段并写明注入点，不要只写"构造异常场景"。

## 主用手段

| 手段 | 适用故障模式类别 | 注入点 | 典型注入内容 | 常用工具与机制 | 注意事项 |
|---|---|---|---|---|---|
| **文件注入** | 配置解析、数据持久化、升级迁移、掉电半写、磁盘满、路径与权限、路径穿越 | 目标文件本身，或其读写所依赖的目录与文件系统 | 预置损坏或截断文件、字段超长或长度字段伪造、内容置零、魔数与校验值篡改、权限改为 000、只读重挂载、分区填满 | `dd`、`truncate`、`chmod`、`chattr`、`mount -o remount,ro`、FUSE 或 faultfs 自定义文件系统、掉电脚本与继电器 | 注入前记录原始文件校验和，保证可还原；文件类故障常与掉电窗口耦合，需在两个写入点之间分别注入 |
| **IPC 消息注入** | 序列化契约不对称、返回值与 errcode 未处理、权限校验缺失、流控失效、对端异常 | 消息发送方与接收方之间，通常替换 Proxy 实现或在反序列化前改写缓冲 | 字段错位与类型错配、长度字段伪造、版本号不匹配、空 reply 或截断 reply、注入各类 errcode、超大 payload 超出事务上限、终止对端进程 | 替换 Proxy 或 mock 服务端桩、在 Parcel 与 Mojo 反序列化前改写缓冲、`kill` 对端进程模拟死亡、注入延迟模拟无响应、`tc qdisc netem` 注入网络侧错包丢包乱序 | 必须覆盖接收侧全部 errcode 分支，而非只测成功路径；跨设备场景注意部分 JS 侧接口不适用 |
| **PLT/GOT hook 注入** | 返回值未检查、失败路径未覆盖、资源申请失败、系统调用异常、耗时与阻塞 | 被替换函数的 PLT 表项或 GOT 表项；静态链接或内联调用需改用 inline hook | 指定调用返回错误码（`ENOMEM`、`EMFILE`、`EINTR`、`ENOENT`）、第 N 次调用失败、返回空值或非法句柄、注入延迟与阻塞 | `LD_PRELOAD` 配合 `dlsym`、GOT 覆写、inline hook 框架（bhook、ShadowHook、xhook 等）、mockcpp 等打桩框架 | 需处理 RELRO 与只读 GOT；被测目标直接静态链接的函数无法用 PLT hook；注入点要精确到函数名与调用序号，保证可复现 |

## 补充手段

| 手段 | 适用场景 | 注入方式 |
|---|---|---|
| 系统调用层注入 | 需验证内核对错误的处理，且 PLT hook 不适用 | `ptrace` 拦截、`seccomp` 过滤、eBPF 挂点、内核 fault-injection 框架按调用序号注入错误 |
| 信号注入 | 应用崩溃、应用异常退出、应用被查杀、进程挂起与停止 | `kill` 发送 `SIGSEGV`、`SIGABRT`、`SIGKILL`、`SIGSTOP`，或直接调用 `abort()` |
| 资源压力注入 | 内存、句柄、线程、磁盘、CPU 的上限与降级路径 | cgroup 限制内存、`ulimit` 限制句柄数、循环申请直至耗尽、填满磁盘、CPU 与 IO 压力工具 |
| 时序注入 | 竞态条件、超时、时钟跳变、休眠唤醒、看门狗窗口 | 在两条竞争路径之间插入延迟、修改系统时间、`tc netem` 注入延迟、放大竞态窗口 |
| 编译期注入 | 编译开关双分支、测试模式跳过、断言开关 | 以不同编译参数各构建一版并分别验证，例如功能开关的开启分支与关闭分支 |
| 环境与配置注入 | feature flag、环境变量、沙箱与容器限制 | 修改配置项、设置环境变量、在容器或受限环境中运行 |
| `rphone`（语料代号） | 网络类故障注入（丢包/时延/限速） | 经 `rNet` 子命令按接口定向注入：`fault=corrupt ratio=%`（错包）、`fault=delay time=ms`（时延）、`fault=limit downlimit/uplimit kbit`（限速）；接口示例 4G `rmnet0`、WiFi `wlan0` |

## 选择原则

由故障原因反推注入手段：

1. 故障原因指向文件内容或磁盘状态，用文件注入。
2. 故障原因指向跨进程或跨线程的契约与消息语义，用 IPC 消息注入。
3. 故障原因指向某个函数的返回值或失败分支未被处理，用 PLT/GOT hook 注入。
4. 故障原因指向进程消亡、资源耗尽、时序竞争、编译分支，分别用信号注入、资源压力注入、时序注入、编译期注入。
5. 一个故障模式可给多种手段时，优先选能在单元测试或 CI 中自动重跑的那种；只能手工执行的方案，在建议中注明为手工验证。

## 填写格式与约束

格式为 `手段｜注入点｜注入内容`。示例：

- `PLT hook｜wrap open()｜第 2 次调用返回 -1 且 errno 置 ENOENT`
- `文件注入｜目标挂载点｜重挂载为只读，使 opendir 失败`
- `IPC 消息注入｜替换 Proxy 的查询接口｜返回空 reply 且 errcode 置 DEAD_OBJECT`

约束：

- 注入必须可复现：写明注入点、次数、持续时间，他人按描述能重现。
- 注入必须可卸载：不得把注入代码留在交付物中，注入改动与业务改动分开提交。
- 注入不得改变注入点之外的行为语义，否则验证结论不成立。
- 涉及数据破坏的注入（删文件、格式化、填满磁盘）须在可回滚环境执行，并预先记录还原方式。
