# 用语规范（术语对照与行文要求）

输出用语对齐 [HarmonyOS 稳定性最佳实践](https://developer.huawei.com/consumer/cn/doc/best-practices/bpta-stability-detection) 的术语体系。写作时按下面的对照表取词，不要自造同义词。

三条铁律（原 SKILL.md「用语规范」节摘要，交付前通检）：

1. 用"故障模式 / 故障影响 / 故障原因 / 严酷度 / 现有控制措施 / 优化建议"，不用"失效模式 / 严重度"等旧称。
2. 结构化信息一律用表格承载，能量化就量化（"超过 3s""不高于 1%"，不写"较长""较高"）。
3. 交付前按本对照表与行文要求通检一遍。

## 术语对照

| 不要用 | 应当用 | 说明 |
|---|---|---|
| 失效模式 | **故障模式** | 鸿蒙统一称"故障模式"，如"应用句柄泄漏故障模式说明" |
| 失效影响 / 潜在影响 | **故障影响** | |
| 失效原因 / 潜在原因 | **故障原因** | 官方分析表中也用"产生原因" |
| 严重度 | **严酷度** | 沿用仓级 `fmea.yaml` 与 DFX 表的列名 |
| 建议措施 / 计划优化措施 | **优化建议** | 对应官方"稳定性优化"章节 |
| 现有消减措施 | **现有控制措施** | 其中偏"发生前预防"的称预防措施，偏"发生后发现"的称检出手段 |
| 排障 / 排查问题 | **问题定位** | 官方高频用"快速定位" |
| 开发环境 / 生产环境 | **开发态 / 运维态** | 官方文档的基本二分 |
| 冻屏、卡死 | **应用冻屏**（AppFreeze） | 首次出现给英文缩写 |
| 崩溃 | **应用崩溃**（CppCrash / JS Crash） | 按故障类型细分 |
| 被系统杀死 | **应用被查杀** / 应用闪退 | 视语境 |
| 进程异常退出 | **应用异常退出** | |
| fd 泄漏、文件描述符泄漏 | **句柄泄漏** | 官方中文用"句柄泄漏"；细分有文件/socket/pipe/ASHMEM/dmabuf 句柄泄漏 |
| 内存越界 | **地址越界**（ASan）/ **内存越界** | ASan 语境用"地址越界" |
| 日志、打点 | **故障日志**（现场日志）/ **维测日志**（维测数据日志）/ **应用事件**（HiAppEvent） | 区分日志类型 |
| 假阳性 / 假阴性 | **误报** / **漏报**、逃逸 | "逃逸"用于"检测机制未覆盖到" |
| 根因层级用 L1/L2/L3 | **一级根因 / 二级根因 / 三级根因** | 官方故障模式说明用三级根因体系 |
| 代码正例/反例 | **正向案例 / 负向案例** | 官方代码示例用 `xxxPositive()` / `xxxNegative()` |
| 规范条目 | **【规则】/【建议】** | 官方编码规范的前缀格式 |
| 打桩、mock、造异常 | **故障注入**（fault injection） | 发生的具体位置称**注入点**，采用的方式称**注入手段** |
| 劫持函数、拦截调用 | **hook**（PLT/GOT hook、inline hook） | 按注入位置命名，不笼统称"hook 一下" |

## 行文要求

1. **开头先写 `## 概述`**：一段话交代问题场景与本文范围，再进入细节。
2. **结构化信息用表格承载**，不要写成连续段落；表格列名用官方措辞。
3. **补充说明用 `> 说明` 引用块**，与正文区分。
4. **不使用破折号作插入语**。官方稳定性文档在 26 万字中使用该标点 0 次。需要停顿或解释时改用冒号、句号或括注。
5. **不滥用加粗**：只加粗真正的术语首次出现与结论性判断，行内罗列不加粗。
6. **能量化就量化**：写"超过 3s""不高于 1%""不超过基线 110%"，不写"较长""较高"。
7. **术语首次出现给英文或缩写**：应用冻屏（AppFreeze）、应用句柄泄漏（FD Leak）、异常退出（CppCrash）。
8. **可用"掌握 X 是问题定位的前提"这类句式**引出必要背景（官方常见表述）。
9. **结论句直陈**，不用"综上所述""由此可见"式套话。
