# 设计文档驱动的对象抽取与路由

> 本节自 SKILL.md 移入（渐进披露）。适用于 codespec 增量需求设计文档（`changes/<repo>/<proposal-id>/`）。与代码输入的核心差别：分析对象不是人挑的，而是从文档的结构化段落与图里抽出来的。

## 1. 对象抽取清单（逐段落落实）

| 文档段落 | 抽取出的对象 | 用途 |
|---|---|---|
| 需求基线摘要 / 设计约束 / 非目标 | 约束条件与不变量 | 判定哪些故障是设计已排除的，非目标覆盖的场景不列 |
| 代码事实基线表 | 每个 `文件:行` 即一个对象；"对设计的约束"即一条潜在故障 | 对象 + 已有事实 + 约束 |
| 架构图（mermaid `graph`） | 节点即对象，有向边即交互 | 对象清单与链路 |
| 类图（mermaid `classDiagram`） | 类即对象，类的属性与方法即功能 | 结构树的叶子节点 |
| 模块影响表 | 子系统 / 仓库 / 模块路径、影响类型 | L2 域门控的输入（仓库名映射到基础域） |
| 实现入口表 | 每个 Entry Point 即对象，含当前职责与预期变更 | 变更点即高故障密度区 |
| 时序图（mermaid `sequenceDiagram`） | participant 即对象；每条消息即一次交互；`alt`/`else`/`opt`/`loop` 分支即状态迁移点；`-->>` 返回即契约 | 候选故障模式的主要产地 |
| 状态归属与不变量 | Ownership / Lifecycle / Concurrency / Compatibility / Performance 五类不变量 | 每条不变量被打破即一条故障模式 |
| 风险与缓解表 | 已有风险与已有缓解措施 | 现有控制措施的权威来源 |
| DFX 设计表 | 空则本次输出目标；有内容则作为增量扩充基线 | 输出落点 |
| DFX 故障模式处置表 | 已处置条目（`FM-xx`/`AD-xx` → 处置/关联 AC） | 判定哪些模式已挂 AC，未处置的命中与 AD 条目即本次处置缺口 |
| 验证思路 / spec 的 AC 表 | 每条 AC 即一条可验证的期望行为 | 故障模式的反面；AC 未覆盖处即盲区 |

图解析规则：

- 图中每个节点、participant、类都是分析对象，逐一登记，不只挑"看起来重要"的。
- 图中每条边、消息都是一次可能失败的交互，逐条推演。
- `alt` / `else` / `opt` / `loop` 是状态迁移点，每个分支都要问"另一分支走错会怎样"。
- 图与正文、代码事实基线不一致时，以正文与代码事实基线为准，并把不一致本身记为一条设计问题。

## 2. 关键词生成

| 类别 | 从设计文档哪里抽 |
|---|---|
| object | 仓库名、模块路径、类名、participant 名、运行实体、语言（ArkTS / C++ / Blink） |
| symbol | 方法名、字段名、API 名、feature flag、配置项、结构体、mojom/traits 名 |
| scenario | 需求场景、业务规则 `BR-x`、异常与边界规则 `EB-x`（空值 / reset / 主题切换 / 降级） |
| symptom | 风险与缓解表已列出的后果（应用崩溃 / 编译失败 / 颜色漂移 / 性能回归） |

## 3. 路由与推演

1. **L2 域门控**：由模块影响表的仓库与模块决定打开哪些基础域（如 ArkUI 组件打开应用框架 + 资源与句柄 + 运行时边界；跨进程 Mojo 打开 IPC；feature flag 与 size-versioned 结构打开版本配套）。
2. **L1 全量**：作为根因兜底。
3. **L3 业务命中**：按业务域打开（Web/ArkWeb、主题、界面等）。
4. **逐（对象 × 交互）推演**，对时序图每条消息、类图每条调用边套用高优先级根因清单：
   - 失败路径：解析失败 / 契约未实现 / 错误码未处理
   - 空值与边界：未设置 / 精确零 sentinel / 非法值 / 未初始化字段
   - 生命周期：异步任务持有对象 / 回调未解绑 / 销毁后被调用
   - 并发与传递：跨线程发布值 / 跨进程序列化对称性
   - 兼容：ABI 成员偏移 / size-versioned 字段 / 开关双分支 / 多入口语义一致性
   - 原子性：两条消费链（如 overlay 与 renderer）看到的值是否一致
5. **剔除设计已排除项**：被"非目标"或"设计约束"明确排除的故障不列，或列入"设计已排除"附注。

## 4. 控制措施与日志的二分判定

每条故障模式都必须判定"文档/代码中是否已有措施"：

| 判定 | 依据 | 填法 |
|---|---|---|
| **已有** | 有明确出处：设计决策 ID、设计约束编号、风险表缓解、代码事实基线 `文件:行`，或仓级 `fmea.yaml` 命中记录 | 照录要点 + 给出处（`DD-x` / 约束编号 / `文件:行` / `fmea.yaml#标识`） |
| **部分已有** | 设计要求已提出但实现或验证手段缺失（如要求移除守卫，而代码事实显示守卫仍在） | 前半写已有要求与出处，后半在优化建议列标出缺口 |
| **无** | 文档与代码均未提及 | 控制措施列写"无"，优化建议列给出可落地方案（校验 / 超时 / 降级 / 埋点 / 自愈） |

**矛盾项优先**：当"代码事实基线表"的描述与"关键设计决策"的要求相互矛盾时（如决策要求移除某个守卫，而代码事实显示守卫仍在），该矛盾本身就是一条高优先级条目，不要拆成两条分别叙述，应单列并在优化建议中给出"以哪一侧为准"的判断依据。这类条目是设计文档分析中价值最高的产出，它直接指出"设计已想清楚但实现没跟上"的缺口。

故障日志与维测日志同样二分：

- 文档中已有埋点，照录事件名。
- 仓 `fmea.yaml` 记录中关键日志为 `NA`，照写"NA（无专用关键日志）"，不得自作补充。
- 完全无埋点，写"无"，并给出建议：日志级别 + TAG + 触发点 + 是否需限频，以及是否需要 HiSysEvent 事件（含事件名）。绘制、主循环等热路径上的埋点必须限频或聚合，不得逐帧打印。
