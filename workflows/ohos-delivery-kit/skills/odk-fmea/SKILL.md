# 鸿蒙故障模式分析（FMEA）

> 本 skill 随 ohos-delivery-kit 分发（`core/skills` 目录下的 `odk-fmea`）。除独立使用外，`odk-design` Step 6（DFX 设计）将其作为故障模式分析引擎委托调用：输入为 codespec 增量需求设计文档（`changes/<repo>/<proposal-id>/`），仓知识库命中结果按其 DFX 表兼容模式回填 `design.md` 的 `### DFX 故障模式分析`。
>
> 七步法方法论见 [references/methodology.md](references/methodology.md)；故障模式库 18 类采用「触发索引 → 按需详情」两级加载（`references/triggers/`），仅按路由场景加载。本文只保留输入识别、流程骨架、故障模式库路由与对外落盘契约（渐进披露：本文件调用即全量载入）。

## 执行模式（subagent 隔离）

本 skill 的分析过程（结构分析、库扫描、推演、输出内容生成）**默认在 subagent（隔离上下文）中执行**——故障模式库与推演产物体量大，进入主会话会挤占交付流程上下文：

- **主会话职责**：准备并传递输入（`design.md` 路径或代码范围、涉及仓清单、变更检索摘要 `involved_repos` / `modules_and_symbols` / `business_process_tags` / `associated_acs`、领域取值），经 Agent 工具派发；只接收结构化结果（命中记录、AD 级推导条目、逐仓状态、回填内容或落盘路径）。**主会话不加载任何类文件或触发表。**
- **subagent 职责**：按本文完整执行（含两级库加载与输出契约）；落盘类结果（回填内容、`docs/dfx/fmea-analysis.md`）由 subagent 直接写盘，主会话只取路径与摘要。
- **降级**：运行环境无 Agent 工具时在当前会话内联执行——此时两级加载纪律为强制（见「通用故障模式库」），且分析结果分批输出，避免单次上下文膨胀。

## 输入识别

分析前确认输入类型，采用对应的结构来源：

| 输入类型 | 结构分析来源 | 重点关注 |
|---|---|---|
| 代码仓 / 代码片段 | 目录结构、BUILD.gn、bundle.json / module.json5 / app.json5、模块依赖、关键类与接口 | 自下而上为主：从代码实现反推故障模式 |
| 设计文档（.md/.docx/.pdf） | 文档中的架构图、模块划分、流程图、接口定义 | 自上而下为主：从架构与流程推导故障模式 |
| **增量需求设计文档**（codespec `changes/<repo>/<proposal-id>/`，含 proposal / spec / design / execution-plan） | 见 [references/design-doc-routing.md](references/design-doc-routing.md)：需求基线摘要、代码事实基线表、架构图、类图、模块影响表、实现入口表、时序图、状态归属与不变量、风险与缓解表 | 对象来自图与表，故障模式来自对象间的交互与不变量；文档已有的"风险与缓解""设计约束"优先作为现有控制措施 |
| 已有问题列表 / 案例 | 问题单中的模块归属、现象、根因 | 以问题为种子扩展同类故障模式，横向扫描 |

混合输入时先建立统一的功能结构树，再把三类来源的故障模式挂接到同一棵树上。

## Steps（分析流程）

1. **界定范围**：确认分析对象（系统服务 / 子系统 / 单模块）、运行环境（设备形态、进程模型）、深度（模块级还是函数级）。设计文档回填场景同时向用户确认故障模式库"领域"取值（导出表二级对象）；未获回答则该列留空。
2. **结构分析**：画出功能结构树。代码输入的来源：
   - **BUILD.gn 依赖**：模块划分、deps 依赖方向、so 边界。
   - **bundle.json / module.json5 / app.json5 依赖分析**：入口 Ability / ExtensionAbility（确定运行实体与进程）、abilities/extensionAbilities 的 type 与 srcEntry、dependencies（依赖的 HSP/HAR/共享库）、reqPermissions/requestPermissions（声明权限，关联越权风险）、metadata/deviceTypes（运行环境约束）、系统应用的 saId 声明。
   - **入口类**：SystemAbility（OnStart/OnStop/OnAddSystemAbility）、Extension / NAPI 模块（napi_module 注册）。
   文档输入从架构章节入手。结构树的叶子节点应落到"可定义功能的组件/接口/关键函数"。
3. **功能分析**：为每个结构元素写功能描述（做什么 + 约束条件，如时序、并发、容量）。
4. **故障分析（自下而上）**：对每个功能推导故障模式，覆盖四类失效形态：功能丧失、功能退化、功能异常（错误结果）、非预期功能（安全/越权）。对每个故障模式：
   - 向上：故障影响（对上一层结构元素直至系统/用户的影响）。
   - 向下：故障原因（结合代码实现和通用故障模式库）。
5. **关键流程反思**：对涉及关键流程（启动、通信、数据持久化、并发调度）的故障模式，逐条过 [references/critical-flow-checklist.md](references/critical-flow-checklist.md)。
6. **风险分析**：填写现有控制措施（代码/设计中已有的预防、重试、降级、校验、检出手段）。若代码中已有防御逻辑，引用具体位置（文件:行）。
7. **优化**：对风险较高且无有效控制措施的项，给出优化建议（可落地、可验证）。
8. **颗粒度分层**：把每条故障模式按修复动作归类为架构与设计问题（AD 级，机制/流程/结构）或单点编码问题（SC 级，函数/语句），拿不准时按根因作用域归类并说明理由；标注两类条目之间的放大与触发关联。分层规则见 [输出格式](references/output-format.md)。
9. **输出**：按 [输出格式](references/output-format.md) 输出两张表与分层汇总。若输入为设计文档且文档已有 DFX 章节，按其中的 DFX 表兼容模式回填，并附**故障模式库导出表格**（全列模板表，命中与推导条目全部进入，见输出格式）。分析对象多时分批交付：先输出功能结构树与用户确认范围，再逐模块输出表格。分析对象为代码仓时，结果默认写入 `docs/dfx/fmea-analysis.md`；纯会话分析则在对话内输出。交付前按 [references/quality-requirements.md](references/quality-requirements.md) 逐条自查。

## 仓级 FMEA 知识库（docs/dfx/fmea.yaml）

鸿蒙各代码仓可在仓根维护 `docs/dfx/fmea.yaml` 作为**该仓既有的故障模式知识库**。分析涉及具体代码仓的对象时，必须先逐仓探测该文件，再决定走增量还是全量分支。

```
对每个涉及仓执行探测
├── 仓可达 且 docs/dfx/fmea.yaml 存在  → 分支 A：增量分析（仓知识库为权威来源）
├── 仓可达 但无 docs/dfx/fmea.yaml      → 分支 B：完整生成全新 FMEA（标注为推导产物）
└── 仓不可达                            → 记录 UNREACHABLE，不得跳过或以推导冒充
```

仓级状态取值（分析过程四态）：

| 状态 | 含义 | 处理 |
|---|---|---|
| `READ` | 知识库已读取 | 写明命中条数，并说明库中其余条目为何不采纳 |
| `NO_HIT` | 知识库已读取但无匹配 | 不得为凑数强行关联 |
| `NO_DFX_KNOWLEDGE` | 仓可达但无 `docs/dfx/fmea.yaml` | 转分支 B |
| `UNREACHABLE` | 本地仓不可达 | 记录待补，不得以推导代替 |

落盘闭包表时的四态→三态映射与理由固定值以输出格式（DFX 表兼容模式·逐仓状态表）为唯一定义处。逐仓闭包表（`仓库 / 状态 / 理由`）仅在主表无命中条目（"不涉及"分支）时填写，须精确覆盖全部涉及仓库——与 odk-design Step 6 落盘契约一致；有命中时逐仓结论在正文说明即可。

### 分支 A：增量分析（fmea.yaml 存在）

知识库单条记录的字段与 DFX 表列一一对应：`故障模式`、`故障影响`、`故障原因`、`严酷度`、`恢复措施`、`关键日志`、`大数据打点事件`；条目标识格式为 `分类-故障模式名`（如 `GC-非法对象`）。

1. **读取**：按涉及仓逐个读取 `docs/dfx/fmea.yaml`，记录读取时的 commit。
2. **匹配**：以本次变更的业务流程与触发条件（而非文件名或模块名）与库中记录做语义匹配。判据是"本次变更是否落在该记录的触发条件内"。
3. **罗列已有**：命中的记录按库中原文填入，恢复措施与关键日志一律照录。库中关键日志为 `NA` 时写"知识库原记录为 NA（无专用关键日志）"，不得自行补一条。
4. **增量补充**：只针对库中未覆盖的部分补充新模式，即本次新增的交互、新增的状态、新增的边界。补充条目来源列标注"本次推导"，与库命中条目严格区分。
5. **来源列格式**：`<repo>@<commit>:docs/dfx/fmea.yaml#<记录真实标识>`——锚点照录 `fmea.yaml` 中该记录的 id 原文，不得按 `分类-故障模式名` 自行拼装（拼装锚点可能定位不到任何记录，含空格或 `|` 时还会破坏表格与来源匹配）。

禁止把模型推导的内容写成看起来像库命中的来源；也不得因"库里有类似条目"就省略对本次变更特有交互的分析。

### 分支 B：完整生成全新 FMEA（fmea.yaml 不存在）

1. **全量推演**：按 [references/design-doc-routing.md](references/design-doc-routing.md) 完整走一遍，对每个（对象 × 交互）推演故障模式。
2. **推导标注**：所有推导条目显式标注 `本次推导（仓无 docs/dfx/fmea.yaml）`——独立输出写在分层表下方的说明行；回填 design.md 时推导条目**不进** `### DFX 故障模式分析` 主表，以 AD 级分层表或独立小节附于 `## DFX 设计` 之下（不进主表的强匹配依据、AD 表承载与四态映射见 [输出格式](references/output-format.md) DFX 表兼容模式）。
3. **控制措施与日志二分**：文档/代码中已有的措施照录并给出处；不存在的写"无"，并在优化建议列给出方案。
4. **沉淀建议**：给出"回写为仓级 `docs/dfx/fmea.yaml`"的建议，把本次推导中稳定可复用的条目整理成条目草案（标识按 `分类-故障模式名`），提示提交到对应仓 `docs/dfx/`；设计文档回填场景同时产出故障模式库导出表格（平台批量导入格式，见 [输出格式](references/output-format.md)）。

## 通用故障模式库

分析时必须对照 `references/` 下预置的通用故障模式库逐类扫描，避免遗漏。库加载为**两级：先触发索引判定，命中后再取详情**（subagent 内同样执行；内联降级时为强制纪律）：

1. **第一级（判定）**：按本节路由选中类后，只读该类触发索引 `references/triggers/NN-xxx.md`（每条目一行：ID / 故障模式 / 触发条件），对照被分析对象的结构树、代码特征与业务流程逐条判定是否命中。
2. **第二级（详情）**：条目触发条件命中后，读对应类文件 `references/NN-xxx.md` 中该 `### ID` 条目详情并实例化；同类多条目命中则该类文件整读一次，12/16/18 大文件可按 `### ID` 锚点用 Read offset/limit 局部读。未命中的条目不加载其详情。

总索引（编号规则与条目前缀范围）：[references/failure-mode-library.md](references/failure-mode-library.md)；类文件路由以本节为唯一定义处：

- **任何模块**必扫 11（高危操作）：读其触发索引按特征检索（exit/abort/kill/remove/跨模块 free 等调用点形态），命中再取详情。
- **模块类别候选**（按被分析对象类型；候选 ≠ 全量，逐类以其触发索引判定）：
  - 系统服务 / SA：11、03、07、09、15；涉及文件持久化加 01；使用 RDB/Preferences/KV 等数据库加 02；Native 实现加 05、06；涉及硬件/驱动加 14。
  - 应用中间件（NAPI 动态库）：11、08、05、06；涉及自建线程/锁加 07。
  - 应用 ArkTS/UI：11、09、08、12；涉及网络/图片加载重点看 09 的 A-02 与 12 的输入事件条目。
  - 分布式 / 跨设备模块（近场/远场通信、发现组网、跨设备传输）：加 16。
- **机制条件（独立入口，凭代码/设计证据加读，与模块类别无关）**：
  - 使用 FFRT 任务调度（ffrt:: 命名空间、ffrt submit/wait 依赖，SA 与中间件同样适用）→ 加 04。
  - 使用 c_utils 组件（SafeMap/SafeQueue/Timer/IOEventReactor）或 Parcel/MessageParcel 序列化 → 加 10。
  - 涉及 OTA/升级路径、数据格式或 ABI 演进（schema/序列化结构/枚举契约跨版本变化）、跨设备版本协同 → 加 13。
  - 运行于或对接虚拟机/容器（VM、卓易通类）→ 加 17。
- **稳定性 / 压测类问题**：加 18（其触发索引同样仅在此类场景加载）。

使用方法：把命中的模式实例化为当前代码或设计的具体故障模式（标注代码位置或设计环节），并在输出表**"故障原因"列尾注记实际命中的库编号**——`（库依据：I-03）`，多条并列用顿号（如 `（库依据：I-02、I-10）`）。该注记适用于**主表与 AD 级分层表（含委托回填场景）**，用于审计"推导条目对照过哪些库条目"；对照后未命中任何库条目的推导条目标注 `（无库依据：本次特有推导）`，区分"对照未命中"与"未对照"。库中模式被代码证据排除时无需列出。跳过触发索引直读类文件全文、或在**无模块类别或机制条件证据**的情况下加载路由外类文件（含其触发索引），视为路由违规——会挤占分析上下文；反之，凭明确证据按机制条件增量加读不属于违规。

## 故障注入

填写「故障注入建议」列时，从 [references/fault-injection.md](references/fault-injection.md) 选取手段并写明注入点，不要只写"构造异常场景"。格式为 `手段｜注入点｜注入内容`，示例：`PLT hook｜wrap open()｜第 2 次调用返回 -1 且 errno 置 ENOENT`。注入必须可复现、可卸载、不改变注入点之外的行为语义。

## 输出格式

按颗粒度分层输出两张表（架构与设计问题表 `AD-` 在前，单点编码问题表 `SC-` 在后）与分层汇总。分层标准、12 列定义、严酷度判据、DFX 表兼容模式与示例行见 [references/output-format.md](references/output-format.md)。

## Limitations

- **四态闭包语义**：落盘闭包表时分析过程四态收敛为三态、归档门禁不认 `NO_HIT`——映射与理由固定值见 [输出格式](references/output-format.md) DFX 表兼容模式（唯一定义处）。
- **委托回填不产 SC 级表**：受 odk-design 落盘契约约束，DFX 回填场景只附 AD 级分层表；独立使用时两张分层表齐全。
- **仓不可达只能记录待补**：`UNREACHABLE` 仓不得以推导冒充知识库命中；是否补扫由调用方决策。
- **落盘位置**：代码仓输入默认写入该仓 `docs/dfx/fmea-analysis.md`；仓不可写时在会话内输出。
- **语料内部代号未定义**：`rphone` 等为取材语料的工作代号（语义见 [references/fault-injection.md](references/fault-injection.md) 补充手段表），使用时替换为本环境实际可用的工具/模式。
- **素材加载纪律**：库加载两级（触发索引判定 → 命中条目详情按需）；18 类（系统稳定性与压测素材）的触发索引与详情均仅在稳定性/压测场景加载。跳过触发索引直读类文件全文、或在无模块类别或机制条件证据时加载路由外类文件，视为路由违规。
- **库导出表的空值语义**：所有 ID 列留空（首次导入=新增）；二级"领域"列依赖用户回答、可能留空；SIL 默认空；发生频度/可检测度为 AI 评估值，无直接证据时必须标注 `（推测）`。

## Output

- 委托回填：`### DFX 故障模式分析` 主表（仅仓知识库命中条目）+ 逐仓状态表 + AD 级推导分层表 + `### 故障模式库导出表格`（全列模板表，命中与推导条目全部进入；独立小节，不参与主表 9 列契约与闭包表校验），落盘进 `design.md` 的 `## DFX 设计` 之下（odk-design 落盘契约）。AD 级分层表每条"故障原因"列尾带库依据注记（`（库依据：I-01、I-02）`；对照未命中标 `（无库依据：本次特有推导）`）。落盘后由 `odk-design` 第 6.4 步对主表命中行与 AD-xx 推导条目逐条做处置决策（`### DFX 故障模式处置`，处置为「新增 AC/复用 AC」的条目回填 spec.md）——本 skill 的输出即该处置表的全部输入，AD 分层表编号须保持稳定以便被 `AD-xx` 引用。
- 代码仓输入：分析结果写入 `<repo>/docs/dfx/fmea-analysis.md`；纯会话分析在对话内输出两张分层表与分层汇总。
- 所有输出用语遵循 [references/terminology-style.md](references/terminology-style.md)（三条铁律与术语对照表）；推导条目一律显式标注"本次推导"。
