# scope：③漏改/完整性 / ④外部接口影响

## ③ 漏改与完整性

- 建立 Task 的 AC → 行为入口 → 实现分支 → 验证证据对应。文件出现在 diff 中不等于
  行为已完成；预期文件未改也可能由已有实现满足，用源码判断并写依据。
- 沿正常、错误、超时/取消、清理和兼容路径检查。新增状态或类型时搜索分派表、switch、
  工厂、注册/注销、双向转换和持久化读写；资源/i18n 检查构建收录与各语言/设备分支。
- 测试以可观察行为为准：边界输入、失败恢复、重复调用、异步交错，以及 AC 要求的
  负向断言。mock 是否屏蔽了真实契约？测试是否会在旧实现上因同一缺陷失败？
- 建议新增测试时给出能漏过当前检查的具体回归场景；不以行覆盖率或测试数量作门禁。
  只提出约定范围内的缺口，不把个人期待升级为新需求。

## ④ 外部接口影响

- 从实际修改符号搜索声明、实现、导出、调用者、适配层和测试；包括不在 diff 内的调用方。
  检查 inner API、JS/C API、`.d.ts`/头文件、NAPI/CAPI/JSI、宏、常量和错误码。
- 对照前后语义：签名/布局/ABI、默认值、错误行为、同步/异步、回调次数及顺序、线程和
  生命周期、权限前提。声明没变也可能破坏调用方；内部重构也不必然影响外部契约。
- 跨仓、IPC、序列化/持久化检查生产者与消费者、旧数据/旧版本兼容、长度与版本字段。
  需要上游代码而本地缺失时明确仓库、接口和待核实语义，不能从声明假定实际行为。
- 类型/状态设计关注不变量：构造时是否有效、谁能修改、无效组合能否被表达、调用方
  是否仍可绕过约束。避免只因某语言可使用更复杂类型就要求重写。
- 若发现实际契约变更，指出需要回填的 spec AC/接口条目；内部机制改变则定位 design
  或 plan。评审者只报告，协调者按已有反馈程序更新。

用 task-scope 模板保留已查调用方和兼容结论。无法覆盖的分支写“待确认”及影响，
不要以“测试通过”替代完整性论证。候选项遵守 [发现协议](findings-and-rereview.md)。
