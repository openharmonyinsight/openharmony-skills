# 发现复核与修复复审

## 候选发现

一个条目对应一个根因，保留足够定位与验证的信息：

- 稳定 ID：如 `TASK-3-SEC-01`；后续行号变化不重编号。
- 维度、`File:Line`、相关 AC/接口及审查快照。
- 触发条件、预期与实际行为、具体影响；无可达场景时不要只写泛化风险。
- 原始证据位置、复现命令及实际结果，或源码调用路径；静态证据可以确认问题，不能伪称运行过。
- 反证/已检查的保护、缺失事实；建议修复方向及验证方式，不直接改代码。
- 验证状态与严重度分开：`confirmed` / `needs_validation` / `rejected`；Critical/High/Medium/Low
  按影响判定，待验证项只能注明潜在严重度，不能当成已确认问题。

把上述细节写在模板已有“问题/修复要求/依据”单元格或发现 ID 下的短段落。
不引入新的必需证据文件或 JSON 格式；报告保留结论及可复核依据，不记录逐步思考过程。

## 协调者复核

1. 独立读取候选对应的源码、调用链和证据，尝试证伪触发前提。作者或 reviewer 的断言
   本身不构成证据。排除已有问题但未被本 Task 引入、加重或使其可达的情况，记录去向。
2. 按根因与受影响契约去重，多个症状保留一个 ID 和全部有效位置；跨席报告引用该 ID。
   不把不同根因仅因行号接近合并。由协调者写文件，避免多席抢写或重复计数。
3. 对照原始 AC 和现有约束判断是否范围内缺陷。`rejected` 必须写反证；不能因作者否认、
   多数席没发现或修复麻烦就丢弃。保留处置，防止后续反复提出同一误报。
4. `confirmed` 且 Critical/High 未解决 → FAIL；High 风险点缺少决定性事实 → BLOCKED。
   两类均计入 `blocking_findings`，同一根因只计一次。Medium/Low 与无 High 关联的
   `needs_validation` 作为非阻塞建议/待确认。五维表与 YAML、阻塞表保持一致。

## 定向复审

先读旧报告和修复 diff，再沿受影响调用链核对：

- 对每个旧 ID 返回 `ADDRESSED` / `NOT ADDRESSED` / `待确认`，附新快照和复验依据。
  不能仅凭“已改”、测试名字或实现者的通过声明关闭发现。
- 检查修复是否引入同范围回归：错误/清理分支、调用者兼容性和安全保护。修复越过原
  范围或触及其他维度时，更新范围并回到相应现有席位，不能套用旧 PASS。
- 没有变化的维度可复用同一基线下仍有效的证据，注明复用依据；验证命令、输入、
  AC/设计约束变化时刷新受影响证据。
- 无关的新观察列入非阻塞建议，交整变更 review 跟进，不借复审无限扩大改动。
  若新发现实际引入/加重了 Critical/High 或影响当前 Task 的完成条件，仍须阻塞，不能
  因为“范围外”而放行；需要新授权时说明具体范围与原因。

每轮在原 verdict 的“复审记录”追加轮次、旧/新快照、发现 ID 处置与验证证据；保留原判断。
自动修复/复审累计最多三轮；到上限仍未解决时保持 BLOCKED，给出剩余问题、已尝试修复和
所需事实/决策。用户明确要求继续时可开启下一批，不能重置记录或自动降低严重度。
