# security：⑤安全与攻击面

先定位变更引入或改变的入口、信任边界及其可控数据，再追到权限决定、敏感操作、
资源和输出。普通 bug 只有在可达条件与安全影响成立时才报告为安全漏洞。

| 检查面 | 沿代码验证的问题 |
|--------|------------------|
| 输入/边界 | 谁控制长度、索引、偏移、计数和编码？整数溢出/截断是否先于分配与拷贝？嵌套/重复数据能否无界放大？ |
| 权限/身份 | 身份来自可信 IPC 元数据还是请求字段？权限是否覆盖每个入口，且在操作前检查？代理调用是否丢失原调用者权限约束？ |
| 敏感信息 | 日志、异常、缓存、返回值是否暴露密钥、token、个人数据或高权限状态？脱敏是否覆盖失败路径？ |
| IPC/fd | Parcel 读取是否完整校验？fd/句柄/对象是否有类型、权限、有效期和所有权检查？拒绝请求后是否仍执行副作用？ |
| 并发/生命周期 | 校验与使用之间能否变化？锁、异步回调、取消/注销、死亡通知是否导致重复释放、悬空访问或越权复用？ |
| 错误/降级 | 捕获、默认值、重试和 fallback 是否将拒绝变允许、失败变成功，或泄漏资源？失败是否能被调用方观察和处置？ |

检查 diff 中删除的保护及历史原因，必要时查看相关提交；不自动扩大为全仓安全审计。
特别核对绑定层转换后是否仍保持 native/ArkTS 的长度、类型、身份与生命周期约束。

对每个候选给出：攻击者能力与前提 → 可达入口 → 数据/控制流 → 被绕过的边界 → 具体影响。
主动找能推翻该问题的事实：上游已校验、受信任来源、锁保护、所有权保证、不可达分支。
找不到完整路径则列出缺少的事实，状态为 `needs_validation`，不能仅凭危险函数名定为漏洞。

验证优先使用已有测试与局部静态追踪。需要 PoC 时用隔离临时副本和合成数据；设备、
真实账号、联网攻击或敏感数据操作不由评审授权。不能安全验证时如实保留限制。
严重度依据实际影响与前提；不把所有吞异常、空 catch 或缺少日志统一定为 Critical。

用 task-security 模板记录每条适用检查的结论与证据，不适用写理由。
候选项遵守 [发现协议](findings-and-rereview.md)，协调者复核后才能成为已确认漏洞。
