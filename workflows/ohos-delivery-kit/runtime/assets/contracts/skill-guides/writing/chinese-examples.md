# 中文表达正反例（从交付文档归纳）

以下例子按提案、规格、设计和执行计划中的常见表达整理。
原表达有的只是过于简略或口语化，不一定有技术错误。建议写法仅改善表达，不证明源文档的实现或验证结果正确。
同类句式可以借鉴，业务条件、错误码、数值、文件名和状态必须来自当前需求，不能照搬。
示例已在本文完整给出，使用时不需要联网读取来源。

## 说明具体对象和动作

“收口、兜底、钉死”等词省略了具体动作。改写时说明统一到哪里、由谁补充处理，以及实现需要遵循什么。
内部辅助层和类结构的例子用于 design/plan，不因为出现在本表就成为 spec 的验收要求。

| 编号与语境 | 原表达（节选） | 建议表述 |
|------------|----------------|----------|
| 例 1：统一内部实现 | 统一“调用方身份获取”辅助层（每仓一个收口点） | 每个仓库使用一个统一的辅助层获取调用方身份。对外接口签名保持不变。 |
| 例 2：异常处理措施 | SyncManager 定期轮询温控等级作为兜底 | SyncManager 定期查询温控等级，在变更通知丢失时补充更新状态，避免状态不一致。 |
| 例 3：设计约束 | 类图用于钉死各组件在既有结构中的挂载点和参数传递关系 | 本次不新增类。类图说明现有组件的接入位置和参数传递关系，实现时应遵循该结构。 |
| 例 4：文件描述符管理 | FD 白名单收口（关非白名单，保留预加载 FD） | 关闭白名单之外的文件描述符，保留预加载时打开的文件描述符，以及 stdin、stdout、stderr。 |

例 2 的原文没有给轮询间隔，不能为了使描述具体而补一个数值。例 4 保留了上下文已要求保留的三种标准流，不能简写成“关闭全部 FD”。

## 区分验收要求、验证结果和保存证据

“全绿、跑通、闭环”不能替代具体判据。写清哪些测试必须通过，哪些结果已经取得，哪些仍未执行。
下表中的正常流程、回归要求属于相应任务的验证要求；文件路径和实际结果只在 plan/evidence 中维护。

| 编号与语境 | 原表达（节选） | 建议表述 |
|------------|----------------|----------|
| 例 5：任务完成条件 | 只覆盖 happy path……都不能替代 AC 闭环 | 仅验证正常流程，不能证明关联的验收标准已全部满足。还应验证其中已约定的异常和兼容场景。 |
| 例 6：回归验收要求 | 回归全绿；codegen golden / regression / bytecode 全通过；test262 零新增失败 | codegen golden、regression 和 bytecode 测试必须全部通过，预期变更项需重新生成；test262 不得新增失败用例。 |
| 例 7：验证状态说明 | Pass build / Pending runtime | 构建已通过，运行时验证尚未完成。 |
| 例 8：保存验证证据 | AC-1.1/AC-1.2 证据落盘 | 将 AC-1.1 和 AC-1.2 的验证记录保存到执行计划指定的证据文件。 |
| 例 9：验证环境受限 | 环境可用时运行 SDK 编译校验（不可用则记录证据缺口，由 API 评审流水线兜底） | 环境可用时执行 SDK 编译校验。环境不可用时，记录尚未验证的项目，交由 API 评审流水线继续验证。 |

例 5 中“还应验证”的场景必须是当前 AC 已要求的内容，不自行扩充验收范围。
例 6 的“不得新增失败”允许基线中已经存在的失败，不能改成“全部测试零失败”，也不能写成已经执行通过。
例 7 是文字说明；`Final Status` 等机器读取的字段名和 `Pass/Fail/Blocked` 等规定值仍保留原样。
例 8 只表示保存记录，不额外承诺强制刷写存储介质。例 9 没有执行结果，不能据此写“SDK 编译校验通过”。

## 保留异常语义、返回值和数据生命周期

润色时把后果说清楚，不把异常改写成成功，也不省略限制条件或生命周期。

| 编号与语境 | 原表达（节选） | 建议表述 |
|------------|----------------|----------|
| 例 10：既有异常行为 | 通过 try/catch 静默吞掉 setter 赋值异常，本特性不修改该路径 | 捕获 setter 赋值异常后忽略该异常，不再向调用方传播。本次不修改这一处理方式。 |
| 例 11：内存中的会话数据 | 不序列化、不落盘、不随应用/引擎重启保留，随 NavigationEntry 生命周期（含历史栈裁剪）自动销毁 | 数据仅保存在会话内存中，不序列化，也不写入持久化存储，应用或引擎重启后不保留。数据随 NavigationEntry 的生命周期管理，条目销毁时数据随之销毁；历史栈裁剪场景也遵循此规则。 |
| 例 12：接口失败结果 | 无 UDP 链路返回不支持 | 调用 `SendUdpMsg` 时，如果没有与 `networkId` 匹配的 UDP 通道，返回 `SOFTBUS_TRANS_FUNC_NOT_SUPPORT`，且不产生任何网络副作用。 |

例 10 只说明既有行为，不授权其他接口忽略异常。例 11 不能把“落盘”机械改为“保存文件”而丢失持久性含义。
例 12 保留了该场景约定的无通道条件、返回值和网络副作用限制；不能把它与能力位未置位时的 `SOFTBUS_FUNC_NOT_SUPPORT` 混为同一个错误码。
原文若缺少返回值或后果，只标明待确认，不猜测，也不从其他示例补入。

## 哪些表述应当保留

| 原文中的准确表述或术语 | 处理方式 |
|------------------------|----------|
| 短路表达式 | 保留。这里指编程语言的求值行为，不能统一改成“提前返回错误”。 |
| 同锁幂等 | 设计中可以保留，并说明保护对象及重复操作的结果；不能把“幂等”改成“只允许调用一次”。 |
| 数据透传 | 技术语境中可以保留；需要解释时说明数据由谁原样交给谁，不改成“成功处理数据”。 |
| 无通道时返回精确错误码，且不产生任何网络副作用 | 这种条件、结果和限制都已明确的句子可以直接保留，不为统一文风再造同义词。 |
