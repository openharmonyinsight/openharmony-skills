# API documentation subagent contract

This guide is loaded by `odk-spec` when `proposal.md` marks `API/SDK` as `是`.
Its purpose is to produce the human-friendly documentation fields that are
merged into the applicable language-specific metadata file.

## Hard rule: no fallback

API documentation must be generated by an isolated subagent. If an Agent tool
or equivalent isolated subagent execution is unavailable, `odk-spec` fails:

```text
FAIL: API documentation subagent is unavailable. Run odk-spec again in an environment that supports isolated subagents.
```

Do not generate descriptions in the main session, reuse old descriptions, copy
existing declaration comments, or leave description fields blank.

## Separation of responsibilities

The main `odk-spec` session owns the API contract skeleton:

- `kind`
- `id`
- `parentId`
- `name`
- `qualifiedName`
- `declaration`
- parameters
- return types
- error codes
- permissions
- `@since`
- `@syscap`
- platform support
- application model
- device support and differences

The subagent owns only natural-language quality:

- API definition three elements
- API usage five elements
- parameter descriptions
- return-value description
- error-code descriptions
- English and Chinese readability and semantic alignment

The subagent must not modify contract fields.

## Input

Pass files and paths, not the full main-session context:

1. API skeleton file, for example `<temporary-workspace>/api-spec-skeleton.yaml`
2. Documentation context file:
   `<temporary-workspace>/documentation-context.yaml`
3. A knowledge pack containing the API repository root `AGENTS.md` and the
   knowledge entries dynamically resolved from it for this API change
4. Up to ten relevant existing declaration files
5. The applicable metadata schema, resolved through the API repository root
   `AGENTS.md`; do not assume a repository-internal path
6. The API documentation forbidden terms file:
   `contracts/api/forbidden-terms.yaml`, resolved from this guide's plugin
   distribution; do not copy its entries into another source file
7. The API document style file:
   `contracts/api/document-style.yaml`; it owns the Chinese/ASCII spacing switch,
   documentation duplication thresholds, and the document-style ruleset version

The documentation context is the bounded source of confirmed behavioral facts.
The subagent must use it, but must not receive the full proposal, design, plan,
or implementation context.

The subagent must not receive unrelated proposal, design, plan, or
implementation context.

## Merge rules

After the subagent returns, the main session first runs
`check-api-documentation-context.py` using the relocated command in the loaded
`odk-spec` skill. Use that command's installed executable path, with these arguments;
do not reconstruct it from the business directory or a plugin-root variable:

```text
--context <temporary-workspace>/documentation-context.yaml \
  --output <temporary-workspace>/api-doc-output.yaml \
  --skeleton <temporary-workspace>/api-spec-skeleton.yaml
```

Then it:

1. Checks that the API ID set, parameter names, and errorCodes identity are
   identical to the API skeleton. For a skeleton API that has a return type,
   the output must provide a complete bilingual `returnType.description`;
   documentation-only output must not restate the machine contract field
   `returnType.text`.
2. Ignores every contract field in the subagent output.
3. Extracts only:
   - `description`
   - `parameters[].description`
   - `returnType.description`
   - `errorCodes[].description`
4. Corrects or regenerates output when the checker reports missing APIs,
   missing documentation fields, confirmed values absent from English or
   Chinese output, or forbidden documentation terms. Missing confirmed facts
   must not be silently dropped, and forbidden terms must be replaced with
   compliant wording.
5. Merges those values into the applicable language-specific metadata file.
6. Runs schema and structural validation before writing the final file.

If an API ID is missing, extra, or duplicated, `odk-spec` fails and does not
perform a partial merge.

## Quality requirements

English text must:

- use concise, direct API-documentation language
- avoid ambiguous or overly nested sentences
- use consistent terminology
- preserve all confirmed constraints and conditions

Chinese text must:

- use natural Chinese API-documentation language
- avoid translationese
- use accurate terminology
- remain semantically aligned with English

Chinese output follows the applicable rules in the OpenHarmony developer
documentation style guide:
<https://gitcode.com/openharmony/docs/tree/master/zh-cn/contribute/style-guide>.
Only apply rules relevant to API description fields; do not import requirements
for full-page document structure, navigation, images, links, or sample code.

中文写作规则：

- 中文文案必须面向中文开发者独立撰写，不得逐句翻译英文。
- 优先使用主动语态和直接陈述。主语可省略；必须写出主语时，使用“开发者”
  或“调用方”，不使用“你”。
- 客观、友好地陈述内容，避免口语化词语、行话、成语俗语和负面情绪表述。
- 描述必须具体，使用已确认的取值、范围、单位和可观测结果，不使用
  “较多”“较好”“可能”“大概”“一般”等模糊词。
- 一句话只表达一个主题，优先使用主谓宾结构。每个字段优先写一至两个自然句；
  句长尽量控制在 50 个汉字以内，同一句逗号数量不得超过 5 个。
- 不使用双重否定、反问句和过长复合句。
- API 名、参数名、类型名、枚举成员和错误码常量保留原文；行为概念使用中文。
- 同一概念在同一文件中必须使用一致的中文术语和动词。例如事件行为已确定为
  “分发”时，不得无语义理由地混用“投递”。
- 存在通用中文术语时，不得把英文概念短语直接嵌入中文句式。
- 标识符列表使用中文顿号“、”分隔。
- 中文正文使用全角标点。代码标识符、单位和取值可以保留 ASCII 字符；单位使用
  `ms`、`ns` 等符号，不使用中文单位名。
- 中英文混排时遵守 `contracts/api/document-style.yaml` 的
  `chineseEnglishSpacing` 配置；是否在中文和 ASCII 字符之间加空格，以该
  配置的当前取值为准。
- 不在 YAML 描述值中添加 Markdown 专用格式（例如反引号）；声明注释格式由
  声明文件生成规则负责。

禁用词唯一数据源：

两个规则文件均携带 `rulesetVersion` 与 `sourceOfTruth` 版本锚。最终校验会
输出当前生效的 `document-style` 与 `forbidden-terms` 规则集版本。

[forbidden-terms.yaml](../../api/forbidden-terms.yaml)

主会话必须把该文件作为 subagent 输入。该文件中的所有词不得出现在任何英文或
中文文档值中，包括 API 三要素 / 五要素、参数描述、返回值描述和错误码描述。
禁用词检查不适用于 YAML 键名、API 名、参数名、类型名、枚举成员或错误码常量
等契约标识符。机器检查与本文档使用同一份文件，不得在其它源码文件中复制该
列表。

示例：

```text
不推荐：未提供可选策略时，投递按 no competition strategy 模式执行。
推荐：  未指定竞争策略时，事件按无竞争策略分发。

不推荐：接受的事件类型为 TouchEvent MouseEvent AxisEvent。
推荐：  支持的指针事件类型包括TouchEvent、MouseEvent和AxisEvent。

不推荐：这里有个 bug。
推荐：  这里有个bug。
```

Both languages must preserve:

- default values
- constraints
- activation conditions
- error conditions
- lifecycle and concurrency restrictions
- performance restrictions

Each API must provide the three elements and five elements. If an element is
not applicable, write `N/A` in English or `不适用` in Chinese; never omit the
field.

Do not duplicate the same behavioral clause across API-level description,
parameter descriptions, and return-value descriptions. Choose one authoritative
location for each fact:

- Parameter-specific defaults, ranges, and type restrictions belong in the
  parameter description.
- API-level `defaultBehavior` describes a uniform default behavior that is
  independent of device category; if no such behavior exists, use
  `N/A` / `不适用`.
- Per-device default values and behavior differences belong once in the
  structured `deviceDifferences` fields. Do not repeat those per-device values
  or device-category branches in `defaultBehavior`, `notes`, or another prose
  field. If the only default behavior is device-specific, use `N/A` /
  `不适用`; a non-value summary such as "the system uses the device-category
  default" is allowed only when it does not duplicate `deviceDifferences`.
- Return semantics belong in `returnType.description`; do not repeat the same
  success/failure clause in API-level `effect` or `notes`.
- A type list or parameter constraint should not be copied into both the API
  description body and `@param` text.

The documentation output must be deduplicated before it is merged.

Description values are human-facing prose only. The YAML key already names the
element, so the value must not repeat that category as a label. Do not write
`Scenario: ...`, `Effect: ...`, `Notes: ...`, `使用场景：...`, or equivalent
field-name prefixes.

Documentation must not restate structured contract facts that are already
represented by metadata fields and declaration markers. In particular:

- API availability belongs only to `since` / platform `since` fields and the
  declaration `@since` marker. Do not put `Available since <version>` or
  `自 <version> 起可用` in `notes`.
- `syscap`, permissions, kit/library, platform, application-model, declaration,
  parameter-type, return-type, and error-code numeric values belong to their
  structured fields or declaration markers.
- For error-code return APIs, success/failure constants and trigger conditions
  belong to `returnType.semantic` and `errorCodes[]`. Do not enumerate them again
  in API-level `notes`; `returnType.description` should state the high-level
  result meaning without duplicating the complete error-code table.
- Use `notes` only for an additional behavioral caution, prerequisite, or
  usage restriction that is not represented by a structured field. If there is
  no such note, use `N/A` / `不适用`.

A version-dependent behavioral difference may be described in `notes` only when
it is not merely availability information and cannot be represented by the
structured `since` / platform version fields.

## Self-check before returning

The subagent must first verify every confirmed fact in
`documentation-context.yaml` is represented in the output:

- unit
- value range
- invalid-input behavior
- default behavior
- precedence
- affected and unaffected scope
- device differences when provided
- activation timing and lifecycle boundaries

The subagent must not invent additional facts.

The subagent must also verify that:

- no description value starts with an element-name label
- no description value merely restates a structured contract field, especially
  API availability already represented by `since`
- `notes` is `N/A` / `不适用` when there is no additional behavioral note
- no normalized behavioral clause is repeated between API-level description,
  parameter descriptions, and return-value descriptions
- per-device values owned by `deviceDifferences` are not duplicated in
  `description.defaultBehavior` or another documentation field
- 禁用词表中的词没有出现在任何文档值中
- 中文读起来是面向中文开发者的 API 文档，而不是英文直译
- 行为概念翻译一致，代码标识符保持原文
- 中文句子主语清楚、结构主动、长度可控
- 中文标点、标识符列表和单位符合写作规则

The subagent must also verify that a human reader can answer:

- what the API does
- when to use it
- what happens after calling it
- how it differs from similar APIs
- what happens by default
- what limits apply
- when it is effective
- what precautions are required
