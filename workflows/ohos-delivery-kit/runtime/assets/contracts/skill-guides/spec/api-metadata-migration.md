# 0.15.0 API metadata hard migration

## Scope

ODK `0.15.0` introduces a breaking API SDD contract. API changes generated by an older contract cannot continue in a newer phase. Existing API changes must either use the upgrade assistant with confirmed facts or restart from `proposal`.

## New contract

API changes now use language-specific metadata files:

- `arkts-api-spec.yaml`
- `c-api-spec.yaml`

`spec.md` contains only an API overview and fact provenance. The metadata files are the single per-API contract source.

Declaration evidence is also split by language and repository:

- `evidence/task1-arkts-api-declaration-en.diff`
- `evidence/task1-arkts-api-declaration-zh.diff`
- `evidence/task1-c-api-declaration-en.diff`
- `evidence/task1-c-api-declaration-zh.diff`

Only files for languages actually involved are required.

## Rejected legacy inputs

The following legacy artifacts are no longer accepted:

- `api-spec.yaml`
- `task1-api-declaration-en.diff`
- `task1-api-declaration-zh.diff`
- per-API Markdown specification tables in `spec.md` used as the contract source
- a design or plan created from an old API spec chain

## Machine-readable contract version chain

All API changes must use contract version `1.0.0`:

- `arkts-api-spec.yaml` / `c-api-spec.yaml`: `apiContractVersion: "1.0.0"`
- `spec.md` API contract table: `API 契约版本 | 1.0.0`
- `design.md` baseline: `API 契约版本：1.0.0`
- `execution-plan.md` input table: `API Contract Version | 1.0.0`

The phase validator checks the available chain for the selected phase. A missing or mismatched version stops design or planning rather than waiting until final validation.

## Required migration

An in-flight 0.14 Markdown API chain may use the deterministic upgrade assistant
when its proposal/spec facts are explicit and the remaining facts can be
confirmed. Load the installed `odk-upgrade-api-chain` skill and follow its
dry-run, fact-confirmation and write steps, using the relocated executable
command supplied by that skill.
The assistant writes current metadata only after all missing facts and conflicts
are resolved; it is not a compatibility layer.

For every API change that cannot be upgraded with confirmed facts:

1. Restart from `proposal`.
2. Rerun `odk-spec` to generate `arkts-api-spec.yaml` and/or `c-api-spec.yaml`.
3. Rerun `odk-design`, `odk-plan`, `odk-implement`, and `odk-validate`.
4. Regenerate language-specific declaration diff evidence.

Do not continue an old `spec.md` into a new `design.md`, and do not run a new `execution-plan.md` against an old API contract.

## Do not repair a mismatched version chain

A missing or mismatched API contract version is a blocking finding, not a field to patch. Do not manually edit `apiContractVersion`, `API 契约版本`, or `API Contract Version`. Manual edits cannot prove that the artifacts were generated by the new flow.

When validation reports a mismatch, it lists every affected artifact, the declared version, and required version `1.0.0`. Follow the required flow and regenerate the affected artifacts from `proposal`.

## Future schema direction

ODK does not provide a bidirectional YAML compatibility layer:

- A newer YAML `schemaVersion` on an older ODK skill is a blocking failure; upgrade ODK first.
- An older YAML schema on a newer ODK skill must be regenerated as current language-specific metadata; this release has no old-YAML schema migration assistant.
- Execution always consumes the current language-specific metadata contract.

The current release supports the 0.14 and `ohos-sdd/v1` Markdown-chain assistants described above. Future YAML schema migrations must declare their own assistant and migration window.

## Why this is a hard migration

The new phases consume structured metadata. Continuing from an old Markdown contract would create two conflicting contract sources and only fail during final validation. The phase gates therefore stop early: design rejects an old API chain, plan rejects an incompatible design, implementation rejects missing or invalid metadata, and validation remains the final gate.
