# 编译产品选择

先读取已有执行计划并判断验证范围。若所有 Task 均为仓库内主机测试、文档或配置检查，
且不编译目标产品、不依赖设备/模拟器，在环境表记录 `验证范围=host-only` 和实际命令，
跳过本指南中的产品/设备选择。只要任何 Task 需要目标编译或设备，本指南仍完整适用。

`build_products` 是供用户选择的产品列表，采用空格分隔的字符串，和现有配置中的
技能列表、目录列表格式一致。`build_product` 仅标注菜单默认项，**配置值不等于用户选择**。
这里的产品名是编译命令接受的名称，可以是具体产品名，也可以是抽象产品名。
编译命令与 `out/<产品名>/` 目录使用同一个名称，具体或抽象名都原样保留；不按 `all_`
前缀分类，不预设抽象名代表产品组，也不把该名称当作设备身份。
一次计划选择一个产品，选择前不生成该产品的编译命令，不自动逐个编译全部产品。

运行 using-odk 定义的配置命令，按 [配置规则](../router/configuration.md) 使用返回的 `config`；同目录用户配置按 key 覆盖默认值，不在本指南中重新读写安装目录配置。
扩展文件中的 `build_products` 替换整个列表，不与默认列表拼接。按空白拆分，保留顺序，
去除重复产品名；不要将它解析为 YAML 数组。

- 未提供 `build_products` 的旧配置：使用非空 `build_product` 作为单项列表。
- 显式配置空列表：提示用户补充产品，不能继续使用写死的备选项。
- 默认产品不在列表中：显示“当前列表无默认项”，请用户选择列表中的产品；不自动追加
  默认产品，也不悄悄选第一个。

在 plan 开始时运行配置加载器的 `--build-product-options`，使用返回的 `products`、
`default_product` 和 `menu` 展示选择。`selected_product: null` 和
`confirmation_required: true` 表示仅由配置不能得到已确认选择；不能把默认项复制成已选项。
该命令只读配置，不写计划、不执行编译。原生/中立包使用
`python3 runtime/executables/lib/odk_repository.py --build-product-options`，源码使用
`python3 scripts/lib/odk_repository.py --build-product-options`。

按实际列表生成编号菜单，标注默认项，**展示后等待用户回答**。例如：

```text
本次计划使用哪个编译产品？
1) a（配置默认项）
2) b
请回复序号、产品名，或明确回复“使用默认产品”。
```

示例菜单中的名字必须替换为实际返回值。只有用户明确输入序号、产品名，或针对
本次产品选择明确确认默认项，才获得选择。用户已为本次计划明确选定编译产品名时
直接复用，不重复提问。写过配置、开启自主模式、泛称“自动/全选推荐/继续”、没有
回答或仅存在一个候选，都不能替代产品选择。缺少明确选择时停在这里，保留待选状态，
不写环境表、不解析 `{product}`，不进入编译或实现。

列表之外的产品须让用户明确确认作为本次新增选项，随后更新计划中的列表；
不要自动修改配置文件。

将去重后的完整列表写入 `execution-plan.md` 的 `可选编译产品` 行，将最终选择写入
`编译产品` 行；在 `产品选择确认` 行记录用户实际答复的摘要，不得把“配置默认值”
写成确认依据。该表是这次计划的快照：实现阶段复用已确认选择，不因配置后来变化而
静默切换产品。已有 `编译产品` 或编译命令本身不能证明用户曾选择该产品。
旧计划缺少确认记录时，能追溯到用户针对该产品的明确答复则补入记录并沿用；否则
在首次执行编译命令之前询问一次。不要因旧计划缺少环境表而直接从默认值补全并编译。
用户要求切换时再按当前配置生成菜单并更新快照。

选择编译产品后，按本次验证需求记录 `验证范围`，不根据编译产品名选择运行环境：

- `build-only`：仅编译，可附带主机检查；`验证产品`、`验证目标确认`、设备版本两行填
  `N/A`，不选择设备、不询问 daily、不启动模拟器、不推包。
- `emulator`：单独确认具体 `验证产品` 和启动方式，记录用户实际答复到 `验证目标确认`；
  设备版本两行填 `不适用（模拟器）`（已有 QEMU 记录可保留 `不适用（QEMU）`）。
- `device`：单独确认具体 `验证产品`，记录 `验证目标确认`，再执行 device-version 指南。
  验证产品不要求出现在编译候选列表中，也不自动等于编译产品。运行时另选 hdc 设备 ID，
  核对该设备实际产品、镜像与验证目标一致；设备 ID 不是产品名。

无设备需求时不要因选了抽象产品而额外要求具体设备产品。有设备或模拟器依赖时，不能
以编译名、配置默认值或通用“继续”代替目标确认。旧计划先恢复可追溯的实际确认，无法
恢复时补问；不得根据旧 `编译产品` 自动填验证产品。

确认后运行只读命令解析器（`<executables>` 使用资源自检定位的目录，源码为 `scripts`）：

```sh
python3 <executables>/lib/odk_repository.py --resolve-product-commands --build-product <编译产品> --validation-scope <build-only|emulator|device> --validation-product <验证产品>
```

`build-only` 省略 `--validation-product`。命令不执行编译、不替代用户确认；将返回的
`commands` 写入环境表。`{product}` 与 `{build_product}` 在所有命令中始终指同一个
编译/产物目录产品名；`{validation_product}` 仅用于显式指定验证目标。
模拟器镜像与测试产物的 `out/` 路径也使用编译名，不能改用验证产品。
测试工具中需要具体设备产品的参数使用 `{validation_product}`，不能把抽象编译名
传入这些参数。例如编译 `all_phone`、在 `rk3568` 上验证时，编译命令仍用
`--product-name all_phone`，产物从 `out/all_phone/` 的实际构建结果定位；
设备版本、刷机和测试目标使用另行确认的 `rk3568`，不推断 `all_phone` 的产品成员。
build-only 不解析或继承配置的模拟器/运行时测试命令，无测试时填 `N/A`；如需主机检查，
单独记录实际命令。其他范围测试命令为空时按 Task 约定推导。

切换编译名或验证目标时分别更新对应确认，重新解析受影响命令。编译名切换后重新核对
产物与验证目标的兼容性；验证目标或实际设备变更时，旧版本准备、推包和测试证据失效。
不得以字符串替换旧产品名的方式修改所有命令，避免把编译名误写到设备命令中。

## 实现阶段验证范围预检

选择执行分支或运行 Task 命令前，核对计划已明确记录 `host-only`、`build-only`、
`device` 或 `emulator`。旧计划缺少范围或值无效时，从可追溯的用户确认恢复，无法恢复
则询问并等待确认。已确认的编译产品和现有测试命令都不能代替范围确认。补齐范围前先暂停
Task 命令。若确认范围为 `device` 或 `emulator`，再按运行时指南补齐目标、版本策略等
缺项，并在运行时命令执行前绑定实际目标。

范围补齐或变更后，先按已确认的范围更新环境表和受影响的 Task 验证命令，再执行。
对 `build-only`、`device`、`emulator` 使用上面的命令解析器；离开 `emulator` 时清除
`模拟器命令`（含旧表中的对应行）。进入 `build-only` 时，将验证产品、目标确认和设备版本
两行置为 `N/A`，移除环境表和 Task 命令中的运行时操作，保留适用的目标编译和独立主机检查。
进入 `host-only` 时按本指南开头的例外规则重写环境表和 Task 命令，只保留独立主机检查，
不调用产品命令解析器。

保留历史执行记录，将受影响的旧准备、部署和测试证据标为不再适用于新范围，并按反馈流程
补齐仍需执行的验证。若还不能明确新命令或处置原验证要求，先走反馈流程，不执行旧命令。
没有变更时继续使用已确认的计划快照。
