# 执行模式（实现阶段三选一）

基础入口 `odk-implement`、Superpowers 桥接入口 `odk-sp-implement` 和 OpenSpec 桥接入口
`odk-ops-apply` 共用同一执行模式确认流程。
模式一经确认即约束 implement → task review → review → validate 的整段链路；切换必须
显式：由开发者确认后更新该小节并留痕，不得静默切换或降级。

| 模式 | 交互 | 三席 Task Review（odk-task-review R1/R2） |
|------|------|------------------------------------------|
| 多子agent检查（默认） | 每个确认点暂停等待开发者输入 | 正常执行（现状行为） |
| 全自动 | 从选择点开始、直到 `odk-validate` 完成，可逆选项取默认值/推荐值；产品/设备等安全边界按上述规则复用既有确认或显式确认一次 | 正常执行（自动推进） |
| 逐步实现 | 与多子agent检查一致（逐项确认） | 跳过；Actual Result 记 `Task review: 不适用（逐步实现模式：免三席审查）` |

## 首个 Task 前确认

1. 列出已批准计划的 Task 清单。首次实现、旧计划缺节或只有模板默认值时，展示三种执行模式，
   等待开发者明确选择，然后把所选模式、选择时间和适用的模式说明写入计划。
2. 跨会话恢复时，复用已有的明确选择与有效留痕；需要切换时重新确认并更新记录。
3. 写入后再执行或委派首个 Task（包括 API 声明 Task）。将已确认的模式和对应 Task 完成条件
   传给桥接流程，使其在执行、评审和交接时沿用同一选择。

## 持久化格式

`execution-plan.md` 在「执行原则」之后维护以下小节（不使用表格，避免触发表格列比较）：

```markdown
## 执行模式

**所选模式：** 多子agent检查 | 全自动 | 逐步实现（三选一，实现开始时确认）
**选择时间：** <ISO 8601 时间>
**模式说明：** <全自动：默认值取值清单；逐步实现：跳过三席审查的理由；多子agent检查可省略>
```

- 旧计划没有该小节时，实现入口按本格式补建；默认推荐多子agent检查，等开发者确认后写入实际选择。
- `**所选模式：**` 的值仅接受三种模式名，可带一个括号注记（如 `多子agent检查（默认）`）；
  箭头、斜杠并列等歧义写法无效（校验器按整行严格匹配）；模式切换历史写入 `**模式说明：**`。
- 对已声明的有效模式，`选择时间` 必须唯一且填写 ISO 8601 日期与时间；全自动的默认取值记录、
  逐步实现的跳过理由也必须填写，不能保留空值或模板占位符。模式说明可在字段下逐行列出。
  缺失、重复或未填写的必需记录在 Draft 告警、归档失败；多子agent检查仍可省略模式说明。
  历史计划完全没有该小节时保留原 verdict 门禁，不据此推断它已选择全自动或免审。

## 全自动模式的默认值规则

- 可逆过程信息（分支名、API 声明仓库路径等）：按推荐规则生成，并记录为假设（assumption）
- 产品选择与验证目标：仅复用计划中已有的 `产品选择确认` / `验证目标确认`；缺失时显式询问
  一次（后续不重复问）。不得把配置默认项、单一候选或候选清单第一项当作已确认选择
  （遵循 `build-products.md`：配置值不等于用户选择）
- 设备/模拟器与版本策略：复用已确认记录；`device` 场景的目标设备选择与刷机前覆盖确认
  遵循 `device-version.md`，必须显式确认，全自动不豁免
- 未决分支按 assumption / open question 记录，不虚构“已确认”
- 三席 Task Review 照常执行（自动推进）；review/validate 阶段不重复询问已确认事项
- 会话/产物中记录「全自动模式 + 每项默认取值」，保证可追溯、可事后纠正

## 逐步实现模式的留痕与门禁

- 每个 R1/R2 Task 的 `Actual Result` 记录一行固定文案：
  `Task review: 不适用（逐步实现模式：免三席审查）`；与同一单元格内的其他证据用
  `<br>` 分隔。R0 行为不变。
- 不产出 `evidence/reviews/task-<n>/` 下任何报告；风险升级（R1→R2）提示仍照常记录，
  Task 列表 `风险等级` 单元格照常更新。
- 归档校验（`validate-artifacts-contract.py` 的 Task Review Gate）按该留痕行放行：
  留痕仅豁免三席评审报告的存在性要求；若该 Task 已有 verdict 文件，其
  `verdict: PASS` 与 `blocking_findings: 0` 结论仍然必须成立（Critical/High 阻塞不因模式豁免）。
  留痕必须位于该 Task 详情 Verification 表的 `Actual Result` 列；缺失时 Draft 告警、归档失败。
  Task 标题与既有归档解析共用规则，支持无冒号等既有写法；相邻 Task 和重复 Task 块不能提供
  本 Task 的留痕。Verification 表必须唯一，包含 `Command / Evidence`、`Expected Result`、
  `Actual Result`、`Final Status` 四列；历史说明中仅有同名 `Actual Result` 列的表不算验证记录。
- `odk-review` 的整变更评审以该留痕替代缺失的 verdict 检查；跨 Task 接口一致性与
  最终集成仍由整变更评审承担，不得因跳过 Task 评审而免检。

## 红线（三模式共同）

- 不自动合并、不自动推送、不自动创建 PR；不自动跨仓提交 design-docs
- 不可验证项仍记「待确认」；Critical/High 阻塞项仍然阻塞
- 全自动模式不豁免 `build-products.md` 与 `device-version.md` 的显式确认要求；缺少确认时
  停下询问，不得静默取默认值或第一候选
- 逐步实现模式跳过仅针对三席 Task Review；`odk-review` / `odk-validate` 的产物与
  门禁不受影响，仍正常执行
