# 变更影响范围检查

代码 Task 在规划、首次编辑和完成检查时使用本指南；审查时核对发现的路径及其处置。
重点检查行为、接口、状态、错误处理及产品配置变化可能影响的其他入口和实现。
纯文档、排版或简单配置调整不必启动语言服务；按实际涉及的文件和配置消费者核对即可。

## 先判断当前环境能做什么

首次处理相关语言时，检查当前 agent 已暴露的工具、已连接服务和仓库已有工具链。
只核对相关能力，不扫描整个用户目录或输出含凭据的配置。同一工作区可复用探测结果；
语言、工具连接或项目配置变化后再检查。

1. 优先检查当前会话可调用的 LSP、语义索引或 AST 工具，以及它实际支持的操作。
   能力以工具说明、服务返回的 capabilities 和实际查询为准，不按 agent 品牌猜测。
2. 未暴露相关工具时，检查本机或仓库依赖中已有的相关命令。例如 C/C++ 的 clangd、
   Clang，或适用语言的 ast-grep、tree-sitter、内置解析器。先确认版本和语言支持；
   不用会隐式下载依赖的命令探测，不自动安装服务或修改 agent 配置。
3. 对当前项目的相关文件做一次小范围只读查询或解析，确认工作区、构建配置和输入正确。
   给探测设置合理超时；连接失败、操作不支持或解析失败时，记录原因后使用下面的替代流程。
   本地只有语言服务可执行文件、没有可用的客户端或调用接口时，不能宣称已完成 LSP 检查。

| 实际可用能力 | 本次使用方式 |
| --- | --- |
| LSP 或语义索引可查询当前项目 | 对受影响符号执行支持的引用、调用关系、实现等查询；缺失能力由替代流程补充 |
| 仅有可用的 AST 解析或结构匹配 | 检查同类代码结构和分支，再用文本搜索、入口清单及测试补充调用关系 |
| 已安装但当前项目不可用，或没有相关工具 | 记录未执行及原因，按替代流程完成检查，不要求安装 Superpowers |

工具可用性、语言适配和查询范围分别判断。AST 结构匹配不等于语义引用解析；
`clangd --check` 的单文件诊断也不等于跨文件引用或调用层级查询。
工具不可用本身不阻塞实现，但不能把未执行的语义检查标成通过。

## 有语义能力时，补充影响范围证据

- 从本次变动的函数、接口、状态和错误处理出发，按需要查询定义、引用、上游调用、
  下游调用及其他实现。只调用服务实际支持的操作，按 API 契约处理分页或结果上限；
  结果截断、超时或索引范围不明时标明未查清部分。
- C/C++ 使用与本次已确认产品匹配的真实编译数据库或项目编译配置，核对宏、头文件、
  目标平台和生成文件。缺少这些输入时，不能用通用默认参数冒充目标产品分析；
  不为补全索引擅自编译产品、下载固件或切换配置。
- 记录分析对应的源码版本及工作区变化、语言/产品配置、索引覆盖范围和已知解析问题。
  跨文件结果依赖索引；索引尚未完成或无法确认状态时，只把结果当作部分证据。
  修改后更新相关文件或索引，再对受影响符号复查；旧结果只可用于未变化的输入。
- 同时检查符号关系之外的同类实现、功能开关、条件编译、注册表、回调和跨语言边界。
  符号引用查询不会自动关联另一段独立复制的逻辑，也不能据此排除其他产品、动态注册或仓外路径。

## 所有模式都要核对的内容

先从已有入口、接口定义、注册表、构建清单和测试中确定本次检查范围，再结合语义查询
或文本搜索追踪相关实现。按变更实际风险检查正常、异常、清理和兼容分支，避免只查修改点。
只读发现可以在当前授权仓库内扩展；新发现文件成为修改依据前，先补入 Task 的只读上下文，
需要修改时再按既有范围规则更新 `Files`，不得直接修改范围外文件。

在 Task 已有上下文、Steps 或 `Actual Result` 中简要记录：

| 入口/实现/配置路径 | 发现依据 | 处置及验证 |
| --- | --- | --- |
| 实际文件和符号或配置入口 | 查询/搜索命令、位置或已有清单 | 需要修改／共用修复已覆盖／无需修改（依据）／待确认；对应 Task 和测试 |

只记录与本次变更有关的路径，不逐文件填空表。共用修复覆盖多个入口时，说明覆盖关系。
已知入口清单与检查结果逐项核对；仍未查清的范围保留为待确认，不以“搜索无新增结果”
或“引用数为零”证明路径完整。内部路径、工具结果和运行证据留在 plan/evidence，
不写入契约未变化的 spec。

## 无语义工具时的替代流程

借鉴 Superpowers 的计划、TDD 和审查纪律，使用当前 agent 已有能力执行：

1. **计划明确范围。** 为发现的修改点和验证点安排具体文件、接口及测试。执行前核对共享
   文件或接口的 Task，记录提供方、使用方及核对结果，避免只写“跨 Task 检查通过”。
2. **搜索并读代码。** 从变动符号、行为和错误码等相关线索搜索调用点与同类实现，结合
   注册表或构建清单检查不同入口、产品分支和配置消费者；对照正常实现，必要时沿调用栈
   回溯根因。记录搜索范围和排除理由，不把文本命中数当成完整性证明。
3. **用测试验证受影响行为。** 将相关入口和异常场景落实到适当的测试；遵守既有 TDD
   及降级规则，观察合理的 Red，再验证 Green。计划列出的测试要实际执行，逐项比较
   Expected 与真实输出；只测修改后的辅助函数不足以证明所有入口都正确。
4. **对照完整改动审查。** 使用 Task 开始前的基线到当前结果的完整差异，包含相关未提交、
   未跟踪文件；多提交 Task 不能只看最后一个提交。逐项核对计划文件和影响路径：每个
   应修改点都有实际改动或有依据的替代处置。独立审查与自审沿用现有角色安排，不重复派人。

上述计划、测试及审查检查同样适用于有 LSP/AST 的情况；语义工具提供额外发现证据。
最终审查还要检查跨 Task 的接口、共享修复及周边未修改路径，不能只累加各 Task 的通过结论。

## 交接与未验证项

向执行者和审查者传递实际可用能力、相关路径、查询/搜索范围、原始结果及测试证据。
审查者按具体风险检查相关调用点和未修改实现，不开展无目标的全仓扫描，也不只信作者说明。
无法从 diff 验证、涉及未修改代码或跨 Task 的要求，要明确交给协调者逐项核实，
不能默认为通过。发现漏改或必需行为仍无法验证时，按 [反馈流程](feedback.md) 保持
对应问题和受影响完成状态未闭环；工具限制不能豁免必需验证，也不要求证明所有运行时路径。

例如，权限规则同时用于同步与异步入口时，两个入口都应有处置和适当的验证。
即使 LSP 只返回同步入口，也要结合接口/注册清单核对异步入口；其实现可能经过回调，
也可能复制了同一规则。缺少相关索引时，记录局限并继续替代检查。
