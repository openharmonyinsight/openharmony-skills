## 验证范围

**验证重点**: 用户可感知的行为和**公开接口**（public API / SDK 暴露的接口）的输入输出，而非内部实现细节。

**非验证重点**: 单元测试覆盖的内容；**内部接口**（inner / system / internal / private / @hide 标注的方法）不在本规格验证范围内，由单元测试覆盖。

## 场景

> 所有场景须锚定**本次变更的修改点流程**（由 spec.md AC 与 design.md 模块影响界定的路径），
> 而非通用套话。稳定性 / 回归场景尤其要落到"修改了哪条路径、对该路径施压或回归"，
> 避免写成与本次变更无关的通用稳定性测试。
>
> 每个场景的 Given/When 从 **spec.md AC**（接口可观测行为）派生**集成/系统验证视角**（跨模块交互、并发、重放、端到端），Then 须是可观测结果——保证能直接翻译成测试步骤与检查点。
> **不重复 spec 用户故事或 proposal 用户场景的可操作序列**——spec-for-validation 只做集成/系统验证增量。
> 场景确属系统 / 服务内部行为（生命周期、自动清理、诊断 dump）时，标"系统视角"并补上**触发它的上层用户 / 业务动作**。
>
> 写法对照：
> - **合格**：可操作用户动作 + 可观测 Then；或"系统视角" + 标注上层触发。
> - **不合格**：只有接口入参与返回码，却没有可操作用户动作。
>
> 撰写前先自检：是否涉及**特性裁剪 / feature-flag / 配置开关**？若是，须为"开关前后的行为差异"
>（如某通路不再触发、降级路径启用）单独列出场景——这类差异最易漏写。
