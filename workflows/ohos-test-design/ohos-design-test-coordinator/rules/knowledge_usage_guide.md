# 知识库/经验库使用指南

## 1. 核心架构

三层知识层级目录架构，每个domain下有三个独立的知识层级目录（层级结构可独立定义，末级目录存放层级名.md，各层级目录下有index.md作为通用知识）：

| 目录名 | 适用阶段 | 内容性质 | Phase读取路径 |
|--------|---------|---------|--------------|
| domain-knowledge | Phase1 | 特性名称与规格信息 | domain/{domain}/domain-knowledge/**/*.md |
| test-experience | Phase2 | 应该测什么？ | domain/{domain}/test-experience/**/*.md |
| case-refinement | Phase4 | 步骤有什么特殊要求？ | domain/{domain}/case-refinement/**/*.md |

---

## 2. 层级发现与读取流程

### 2.1 统一流程（各阶段）

```
步骤1：选择知识层级目录（Phase1→domain-knowledge, Phase2→test-experience, Phase4→case-refinement）
步骤2：glob扫描（领域: domain/{domain}/{knowledge_layer}/**/*.md + 通用: general/{knowledge_layer}/**/*.md）
步骤3：沿层级从深到浅读取层级名.md（优先级: 子层级 > 父层级 > index.md）
步骤4：语义匹配（关键词 vs 条目字段——Phase1:"特性名称", Phase2:"涉及特征", Phase4:"动作因子"）
  - MCP模式：调用MCP工具返回score；本地模式：详见2.2节；阈值：≥0.6保留，<0.6跳过
```

### 2.2 本地语义判断规则

**核心逻辑**：综合score = 关键词重叠度（0-0.5） + 语义相似度（0-0.5）。score≥0.6→matched，<0.6→not_matched。

**领域特性关联（强制执行）**：需求关键词含领域特性名称，且条目匹配字段以该特性名称为前缀时，score取max(综合score, 0.6)自动达标。例：关键词含"驱动应用"，条目涉及特征"驱动应用-更新"→score=max(原score, 0.6)→matched。

**采纳机制（Phase2强制执行）**：

所有经验条目通过语义匹配"涉及特征"字段进行匹配（score≥0.6→matched）。匹配成功后，采纳条目中"需要测试"验证点，按标记做二次判定：

| 验证点标记 | 采纳方式 | 说明 |
|---------|---------|------|
| 无标记 | 直接采纳 | 未标注[必测]/[选测]的验证点全部直接采纳 |
| [必测] | 直接采纳 | 核心功能必须验证，无需二次判定 |
| [选测] | 语义匹配（score≥0.6） | 扩展场景按需验证，根据语义匹配决定采纳 |

- 语义匹配判断：关键词匹配需关键词在spec中出现；相关性判断不需关键词在spec中出现（如spec未提"覆盖安装"但工程常识判断相关）
- **二次判定逻辑**：先匹配"涉及特征"（条目级别），再对"需要测试"中的[选测]验证点做语义匹配（验证点级别）；[必测]和无标记验证点无需二次判定
- **采纳前TP参照系检查（Phase2强制执行）**：验证点通过上述二次判定后，进入第三步——与当前US已生成的AC/BR测试点验证逻辑比对。验证逻辑等价（验证目标语义一致）或子集包含（经验验证点⊆已有TP验证点）→跳过采纳，来源标注"经验库/{条目ID}已由{TP-ID}覆盖"；父集包含（经验验证点⊇已有TP）→补充差异部分到已有TP，不新建。此步骤由AI语义判断，不依赖文本相似度

**交付推断来源**：Phase1根据语义识别变更内容标注测试对象，从DK条目提取已交付功能（详见§11交付推断规则）。

**匹配示例**：
- "安装-签名校验" vs "安装-签名校验完整性" → 重叠(2/3)+同功能同场景 → score≈0.78→matched
- "驱动应用" vs "驱动应用-更新" → 领域特性关联 → score=max(0.35,0.6)=0.6→matched

### 2.3 关键词提取规则

| 类型 | 示例 | 说明 |
|------|------|------|
| ✅ 测试对象 | 安装功能、按钮点击响应 | phase1输出的功能特性 |
| ✅ 业务场景 | 接口有可选参数、有共享状态 | phase1识别的业务场景 |
| ✅ 代码特征 | 多用户场景、并发场景 | phase1识别的代码特征 |
| ✅ 非功能需求 | 性能、稳定性、安全性 | §2.5全局非功能性需求 |
| ❌ 前置条件 | userId参数、前置依赖 | 测试前置条件 |
| ❌ 内部信息 | 回调丢失、OOM崩溃 | 内部问题现象 |
| ❌ 测试手段 | TM-001、接口返回成功 | 测试手段描述 |
| ❌ 跟需求不相关 | 系统内部实现细节 | 脱离需求本身 |

### 2.4 各阶段Agent分工

**规划Agent（Phase2）**：基于Phase1交付推断结果进行经验库匹配
- Read knowledge_match.md §1.1交付推断结果表 → 提取测试对象主单元列表和回归对象领域列表
- 针对测试对象主单元：匹配对应主单元的测试经验，关联US字段标注主单元ID
- 以表格汇总到knowledge_match.md §2 + 生成分批计划（仅写入类主单元和独立查询类主单元生成batch_id，有前置依赖的查询类主单元不生成独立batch）+ 返回摘要

**协调器**：确认knowledge_match.md已更新 + 并行spawn执行Agent（≤4）+ 注入knowledge_match.md路径 + 一个测试对象主单元对应一个batch_id

**执行Agent**：Read knowledge_match.md → 定位§2测试经验匹配结果表格 → 按主单元ID筛选关联US → 提取完整经验内容 → 采纳匹配到的经验补充测试点（无标记：全部直接采纳；[必测]：直接采纳；[选测]：语义匹配score≥0.6采纳）→ 来源标注"经验库/{条目ID}"

## 3. 调用方式

| 方式 | 层级获取 | 精确查找 | 匹配计算 |
|------|---------|---------|---------|
| MCP | knowledge-service_get_hierarchy_tree_simple | knowledge-service_search_knowledge | MCP返回score |
| 本地 | Read config.yaml → glob扫描 | Read层级名.md → 语义匹配 | AI计算score |

**可用性判断**：MCP可用→mcp；MCP不可用但本地有文件→local；均不可用→none

**none模式行为**：规划Agent跳过经验库匹配步骤，仅执行分批规划和前置摘要提取（Phase2），追加空表格头到knowledge_match.md对应章节（§2/§3），返回摘要匹配条目数标注0条。

### MCP模式工具调用语法

**层级获取**：
```
mcp_knowledge-service_get_hierarchy_tree_simple(domain="{domain}")
```

**知识检索**：
```
mcp_knowledge-service_search_knowledge(query="{关键词}", domain="{domain}", layer="{knowledge_layer}", min_score=0.3, top_k=10, include_common=true)
```

**layer参数取值**：
| 阶段 | layer参数值 | 说明 |
|------|-----------|------|
| Phase1 | domain_knowledge | 领域知识 |
| Phase2 | test_experience | 测试经验 |
| Phase4 | case_refinement | 用例细化 |

**关键词传入逻辑**：
- Phase1：从spec标题、AC描述、功能规则中提取关键词（特性名称），组合为query传入
- Phase2：从knowledge_match.md§1.1交付推断结果提取测试对象主单元名称，组合为query传入
- Phase4：从test_point_design.md提取测试点场景关键词（动作因子），组合为query传入
- 关键词提取规则详见 §2.3，多个关键词用空格组合传入query参数

**min_score参数说明**：min_score是传入MCP工具的过滤参数（默认0.3，可自定义调整），MCP服务端据此过滤返回结果，匹配度由MCP返回的score决定。

### 本地经验库模式

```
Read config.yaml → glob domain/{领域}/{knowledge_layer}/**/*.md + general/{knowledge_layer}/**/*.md → 沿层级路径从深到浅读取层级名.md → AI语义匹配 → 输出knowledge_match.md对应章节
```

**knowledge_layer取值**：domain-knowledge（Phase1）/ test-experience（Phase2）/ case-refinement（Phase4）

**本地语义匹配**：综合score = 关键词重叠度（0-0.5）+ 语义相似度（0-0.5），score≥0.6→matched，<0.6→not_matched。领域特性关联（关键词含领域特性名称且条目匹配字段以该特性名称为前缀时）score取max(综合score, 0.6)自动达标。详见 §2.2。

## 4. 层级隔离规则

**强制执行**：各阶段仅读取对应知识层级目录，禁止跨层读取：

| 阶段 | 允许读取 | 禁止读取 |
|------|---------|---------|
| Phase1 | domain-knowledge/**/*.md | test-experience、case-refinement |
| Phase2 | test-experience/**/*.md | domain-knowledge、case-refinement |
| Phase4 | case-refinement/**/*.md | domain-knowledge、test-experience |

---

## 5. 优先级规则

**知识优先级**：需求指定 > 子层级条目 > 父层级通用经验(逐级向上) > 通用经验 > 默认(脚本/AI)

**层级检索优先级示例**（BundleManager，Phase2 test-experience/application/driver-app）：
1. driver-app.md → 2. application.md → 3. index.md（领域通用）→ 4. general/test-experience/（通用经验）

**来源优先级**：MCP > 本地

**冲突处理**：经验库与需求文档冲突时，以需求文档为准，标注"与需求文档冲突，已忽略"

**经验库双重定位原则**：
1. **补充测试场景**：针对测试对象补充更多场景（如覆盖安装）
2. **辅助理解规格**：帮助理解需求文档已描述的场景规格和约束
- ❌ 不能把经验库的其他测试对象强行加入当前US（US-1只涉及安装，不能把"卸载功能"作为测试对象）
- ✅ 可以把经验库的补充场景加入当前测试对象（US-1测试对象是"安装功能"，可补充"覆盖安装"场景）

## 6. knowledge_match.md格式

**三段式表格结构**：

```markdown
# 知识库匹配结果
> 生成时间：YYYY-MM-DD | 领域：{domain} | 模式：mcp/local/none

## 1. 领域知识匹配结果（Phase1）

### 1.1 交付推断结果
| 类型 | 主单元ID/领域 | 名称 | 判定依据 |
|------|--------------|------|---------|

### 1.2 领域知识条目匹配详情
| 条目ID | 标题 | 来源 | 匹配状态 | 匹配度 | 涉及特征 | 内容摘要 |

## 2. 测试经验匹配结果（Phase2）
| 条目ID | 标题 | 来源 | 匹配状态 | 匹配度 | 涉及特征 | 推荐测试技术 | 关联US | 采纳方式 | 完整内容 |

## 3. 用例细化匹配结果（Phase4）
| 条目ID | 标题 | 来源 | 匹配状态 | 匹配度 | 动作因子 | 关联US | 采纳方式 | 完整内容 |

## 4. 统计信息
- 领域知识：总条目X条，匹配X条，覆盖率X%
- 交付推断：测试对象主单元X个，回归对象Y个
- 测试经验：总条目X条，匹配X条，覆盖率X%
- 用例细化：总条目X条，匹配X条，覆盖率X%
```
**§1.1交付推断结果列说明**：

- 类型：测试对象/回归对象
- 主单元ID/领域：测试对象填写主单元ID（US-1、TR-001等），回归对象填写领域名称（ArkUI、BundleManager等）
- 名称：测试对象填写主单元名称，回归对象填写领域功能名称
- 判定依据：测试对象填写spec变更标记（"新增XXX特性"、"变更YYY行为"），回归对象填写DK条目匹配结果

**§1.2条目匹配详情列说明**：

- 不再标注"交付推断"列（交付推断结果独立输出到§1.1）

**匹配状态**：matched（≥0.6）/ not_matched（<0.6）

**各阶段读取**：Phase1定位"##1"→创建§1.1交付推断结果表+§1.2条目匹配详情表；Phase2定位"##2"提取完整内容+关联US+采纳方式（语义匹配涉及特征→无标记全部直接采纳、[必测]直接采纳、[选测]语义匹配score≥0.6）；Phase4定位"##3"提取完整内容+关联US+采纳方式

**追加方式**：Phase1创建骨架+领域知识表格（仅摘要）；Phase2追加测试经验表格（含关联US+采纳方式+完整内容）；Phase4追加细化表格（含关联US+采纳方式+完整内容）

**关联US字段（Phase2特殊规则）**：
- 测试对象主单元：填写具体主单元ID（如"US-1", "US-2"），从小到大排序逗号分隔
- Phase1不含此字段，Phase2/Phase4必须包含

## 11. 交付推断规则（Phase1强制执行）

区分测试对象与回归对象：
- **测试对象**：spec中明确标注为变更内容的主单元，需要重点测试、深度覆盖
- **回归对象**：领域知识（DK）中已交付的功能（领域级别），辅助理解需求

领域知识中的DK条目默认表示已交付特性。写入领域知识的内容 = 已交付过 = 回归对象。

### 语义识别变更内容（强制执行）

通过语义分析判断主单元是否包含变更内容：

**变更标记识别**：
- spec标题含"新增"、"变更"、"修改"、"优化"、"扩展"等关键词
- AC标注"新增特性"、"变更行为"、"新增输出"等
- 功能规则含"新增功能"、"变更机制"等描述
- 业务规则含"新增规则"、"变更约束"等

**判定逻辑**：
- 主单元含变更标记 → 测试对象（该主单元整体为测试对象）
- 主单元无变更标记 → 根据业务逻辑判断是否涉及已有功能变更

**示例**：US-1标题"新增NativeModule加载失败loadErrInfo精确错误信息"
- US-1含"新增"关键词 → **测试对象**（重点测试变更内容）

### 回归对象提取（从领域知识库）

从领域知识库（DK）条目提取已交付功能作为回归对象：

**提取方式**：
- DK条目匹配成功 → 提取条目对应的领域/功能作为回归对象
- 多个DK条目匹配同一领域 → 合并为一个回归对象（领域级别）
- 无DK条目 → 不生成回归对象（仅测试对象）

**回归对象用途**：辅助理解需求规格、提供业务背景

**示例**：匹配到DK-ABY-001、DK-ABY-002、DK-ABY-003（均属于Ability领域）
- 回归对象：Ability领域（生命周期管理、NativeModule加载机制等）→ 辅助理解

### 交付推断输出

交付推断结果写入knowledge_match.md§1.1"交付推断结果"（§6格式定义）：

**§1.1交付推断结果表格式**：

| 类型 | 主单元ID/领域 | 名称 | 判定依据 |
|------|--------------|------|---------|
| 测试对象 | US-1 | [US名称] | spec标注"新增XXX特性" |
| 测试对象 | US-2 | [US名称] | spec标注"变更YYY行为" |
| 回归对象 | ArkUI | 生命周期管理 | DK-ARK-001匹配成功 |
| 回归对象 | BundleManager | 安装卸载 | DK-BMS-INS-001等匹配成功 |

交付推断同时标注在requirement_analysis.md§1需求概述（变更范围概要和主单元索引表）。
