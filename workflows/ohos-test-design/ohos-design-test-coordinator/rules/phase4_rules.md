# 阶段4：测试用例细化规则

本文档包含Phase4测试用例细化的详细执行规则，供AI Agent参考使用。

---

## NEVER（执行约束）

### 流程执行类
- NEVER 跳过或快速执行phase4——不得简化流程，必须完整执行，失败需尝试修复（2次）
- NEVER 输出不完整的测试用例——必须完整输出（符合汇总表用例数）

### 内容规范类
- NEVER 使用省略的语句代替实际用例——必须列出所有用例，不得使用"..."、"等等"等省略表述
- NEVER 测试步骤不采用黑盒可执行方式——测试步骤应采用场景操作、命令触发、用户交互等黑盒可执行方式描述
- NEVER 预期结果不采用外部可观测方式——预期结果应采用场景变化、可观测响应、日志检查等外部可观测方式描述
- NEVER 直接引用测试点内容——预置条件、测试步骤、预期结果必须展开为具体可执行操作（如"设置接口枚举值→细化为具体的枚举值"）
- NEVER 同时存在多个测试对象时不具体区分——存在多个测试对象时，用例细化需体现对应的测试对象，再细化展开步骤与结果
- NEVER 将测试步骤和预期结果写入前置条件——前置条件不得重复出现测试步骤和预期结果

### 重复与覆盖类
- NEVER 为已标注重复关系的被测场景生成重复用例——来源列标注相同场景ID的被测场景仅生成1个用例
- NEVER 为来源标注"适用US-X异常场景"的测试点生成用例——这些测试点已在被适用的主单元中生成用例，当前主单元跳过
- NEVER 同一测试点默认生成1个用例——功能结果、日志、访问等验证维度优先合并到同一用例的不同步骤中。若需生成多个用例，必须有明确的差异化维度（如执行方式不同、输入值不同、路径类型不同等），用例名称标注差异化维度，各用例验证目标不得重叠
- NEVER 生成验证维度重叠的用例——同一触发场景（相同预置条件+相同操作）下，不同用例的验证目标不得重叠，功能结果/日志/访问验证应合并到同一用例的不同步骤中，不得拆分为独立用例

### ID与格式类
- NEVER 测试步骤不与预期结果一一对应——测试步骤必须对应可独立验证的预期结果
- NEVER 用例名称意图不清晰——用例名称必须包含"测试对象+操作步骤+验证目标"（比如"xx接口-设置xx属性-验证xx观测点"）
- NEVER 用例名称带编号前缀——用例名称不得包含数字编号前缀
- NEVER 在用例细化时改变阶段2确定的执行方式——执行方式在测试点阶段锁定
- NEVER 在面向执行者的内容中使用内部追溯ID——用例名称、预置条件、测试步骤、预期结果必须使用自然语言描述

### 执行模式类
- NEVER 单批超出AI输出能力——每批用例数必须控制在动态batch_size内
- NEVER 中途出错或失败静默跳过——任一批次失败必须明确告警并记录后继续执行其他批次

## 知识库/经验库补充测试步骤规则（三层知识层级目录架构）

#### 阶段继承与层级隔离

**Phase4 Read knowledge_match.md → 读"用例细化匹配结果"表格 → 测试步骤补充**。

knowledge_match.md由Phase1生成（领域知识）+ Phase2规划Agent追加（测试经验）+ Phase4规划Agent追加（用例细化），包含三段独立表格。Phase4仅读取"用例细化匹配结果"表格中的case-refinement目录条目，禁止读取"领域知识匹配结果"或"测试经验匹配结果"表格。

> 统一流程（层级发现glob、沿层级从深到浅Read、语义匹配动作因子score≥0.6、MCP/本地模式工具调用语法）详见 `rules/knowledge_usage_guide.md` §2-3。knowledge_match.md格式详见 §6。以下仅描述Phase4专属逻辑。

#### Phase4规划Agent匹配执行步骤

```
步骤1：Read test_point_design.md → 提取测试点关键词
步骤2：按统一流程匹配case-refinement目录（知识层级=case-refinement，匹配字段=动作因子）
步骤3：语义匹配成功后采纳，记录完整内容 + 关联US（从小到大排序）
步骤4：输出匹配结果追加到knowledge_match.md §3（表格形式汇总，格式见knowledge_usage_guide.md §6）
步骤5：生成分批计划（一个US对应一个batch_id）
```

#### 追加格式（强制执行）

在knowledge_match.md中追加以下章节（如已存在则更新表格）：

```markdown
## 3. 用例细化匹配结果

| 条目ID | 标题 | 来源 | 匹配状态 | 匹配度 | 动作因子 | 关联US | 完整内容 |
|--------|------|------|---------|--------|---------|--------|---------|
| CR-BMS-APP-DRV-001 | 驱动应用安装细化 | local | matched（直接采纳） | 1.0 | 驱动应用安装验证 | US-01,US-03 | **特殊步骤要求**: 安装前验证签名完整性、安装后验证目录权限...<br>**预期结果细化**: 验证日志中签名校验成功记录、验证进程状态... |
```

**追加方式**：
- Read现有knowledge_match.md
- 定位"## 3. 用例细化匹配结果"章节（如不存在则创建）
- 更新表格内容（追加新匹配条目，包含完整内容和关联US）
- Write更新后的knowledge_match.md

**经验库为空时的追加格式**：
```markdown
## 3. 用例细化匹配结果

> 经验库为空，无匹配条目

| 条目ID | 标题 | 来源 | 匹配状态 | 匹配度 | 动作因子 | 关联US | 采纳方式 | 完整内容 |
|--------|------|------|---------|--------|---------|--------|---------|---------|
```

**采纳规则（强制执行）**：
- 语义匹配"动作因子"成功后（score≥0.6）采纳条目
- 记录完整细化内容（特殊步骤要求、预期结果细化等），不只是摘要
- 关联US字段：根据经验条目涉及的测试对象/业务场景，关联到对应的主单元（从小到大排序）

#### Phase4字段用途（仅读case-refinement目录条目）

| 字段 | Phase4用途 |
|------|-----------|
| 动作因子 | 匹配触发条件 |
| 特殊步骤要求 | 测试步骤补充，细化预置条件和操作步骤 |
| 预期结果细化 | 预期结果补充，增加外部可观测验证点 |

#### 来源标注格式

**详见** `rules/knowledge_usage_guide.md`

### 继承示例

从 knowledge_match.md 提取"用例细化匹配结果"表格中的条目，参考特殊步骤要求和预期结果细化字段补充测试步骤。

**冲突处理**：经验库与需求文档冲突时，以需求文档为主，标注"与需求文档冲突，已忽略"

## 执行规则

### 多轮并行处理机制（协调器执行）

协调器根据批次总数执行多轮并行spawn，每轮≤parallel_limit（4）个Agent。

**并行上限**：
- parallel_limit = 4（SKILL.md约束）
- 每轮最多spawn 4个执行Agent

**轮次计算**：
```
轮次数 = ceil(batch_count / parallel_limit)
例：batch_count=5，parallel_limit=4 → 轮次数=2（第1轮4个，第2轮1个）
例：batch_count=8，parallel_limit=4 → 轮次数=2（每轮4个）
例：batch_count=10，parallel_limit=4 → 轮次数=3（第1轮4个，第2轮4个，第3轮2个）
```

**轮次执行流程**：
```
第1轮：
  - spawn Agent处理batch_1~batch_4
  - 每个Agent注入：knowledge_match.md路径 + 分配的测试点范围
  - 等待第1轮所有Agent完成
  - 收集第1轮批次文件路径

第2轮：
  - spawn Agent处理batch_5~batch_8
  - 每个Agent注入：knowledge_match.md路径 + 分配的测试点范围
  - 等待第2轮所有Agent完成
  - 收集第2轮批次文件路径

（以此类推，直到所有批次处理完成）

所有轮次完成后：
  - 调用脚本merge_batch_mds合并所有批次文件
  - 输出test_cases.md
```

**每轮Agent分配规则**：

| 分配项 | 说明 |
|--------|------|
| **批次数量** | 每轮≤parallel_limit（4）个Agent |
| **注入文件** | knowledge_match.md路径（已更新） |
| **分配参数** | 测试点范围（从batches数组提取） |
| **等待机制** | 当前轮次所有Agent完成后再启动下一轮 |
| **批次文件收集** | 协调器收集所有轮次的批次文件后统一合并 |

**规划Agent返回格式**：
```
批次规划完成：
| batch_id | tp_range | estimated_cases |
|----------|----------|-----------------|
| batch_US01_1  | TP-US01-001~TP-US01-015 | 25 |
| batch_US02_1  | TP-US02-001~TP-US02-010 | 18 |
批次总数：X个
预计用例总数：X个
经验库匹配完成：已追加到knowledge_match.md
```

**注意**：
- 规划Agent不再声明执行方式，协调器统一按多轮并行处理
- 执行方式由协调器根据批次总数自动计算轮次
- 执行Agent不关心轮次逻辑，仅负责生成测试用例

### 执行Agent编号规则（强制执行）

**用例ID格式**：
- 用例ID格式：`TC-{主单元编号}-{序号}`（去掉连字符，如US-01→US01）
- 用例标题格式：`### TC-{主单元编号}-{序号}-{用例名称}`
- 示例：US-01 → `TC-US01-001-安装验证`, `TC-US01-002-卸载验证`
- 序号格式：3位数字，每个主单元独立编号，从001开始
- 合并后脚本统一重编号为 `TC-001~TC-N`
- 禁止使用不一致格式（如 TC-batch1, TC-batch_US_02）

**核心要点**：
- 每批次生成临时编号，合并时统一重编号
- 不输出汇总表/统计信息（脚本统一生成）

### TP-ADD测试点处理规则（强制执行）

**识别方式**：扫描test_point_design.md，提取TP-ADD-*测试点（对抗评估补充）。

**批次规划**：
- TP-ADD测试点单独成批：`batch_ADD_1.md`
- 用例编号格式：`TC-ADD-{序号}`（如TC-ADD-001）
- 来源标注：`对抗模型`或`对抗模型：关键场景遗漏（TP-USXX-XXX深度补充）`

**执行流程**：
```
步骤1：扫描test_point_design.md末尾的TP-ADD-*测试点
步骤2：统计TP-ADD测试点数量
步骤3：创建batch_ADD_1批次（或按数量拆分多批）
步骤4：生成测试用例，关联测试点为TP-ADD-*
```

**示例**：
```markdown
### TC-ADD-001-权限校验绕过深度验证

**测试类型：** 安全测试
**测试技术：** 边界值分析
**执行方式：** XTS
**用例级别：** P1
**来源：** 对抗模型：关键场景遗漏（TP-US01-008深度补充）
**关联测试点：** TP-ADD-001
```

## 用例生成规则

### 测试步骤与数据合一规则

步骤描述中直接包含具体数据，不单独列出"测试数据"列或JSON块。无效测试用例的步骤中必须使用无效数据。

### 按执行方式分流的描述风格

| 执行方式 | 步骤风格 | 预期结果风格 |
|---------|---------|------------|
| XTS | 调用接口/设置属性/触发事件 | 验证返回值/属性值/回调结果 |
| 黑盒自动化 | 页面操作/控件交互 | 界面显示验证 |
| API性能自动化 | 调用接口+量化采集 | 性能指标达标 |
| 手工 | 人工操作/环境切换 | 人工观察验证 |

### 验证完整性原则

所有用例的预期结果必须验证到外部可观测效果，不得仅依赖"接口返回成功"作为唯一预期结果。存在可外观测生效效果时，预期结果必须包含外部可观测证据（进程状态、系统日志、UI变化、持久化数据）。

### 白盒用例描述规范（XTS时强制执行）

用例的标题、预置条件、测试步骤、预期结果全部使用白盒风格，禁止出现Demo控件操作。

**用例标题格式**：
- 接口测试：`TC-{主单元编号}-{序号}-[接口名]-[入参描述]-[预期]`
- 组件属性测试：`TC-{主单元编号}-{序号}-[组件名]-[属性名]-[值]-[预期]`
- 组件事件测试：`TC-{主单元编号}-{序号}-[组件名]-[事件名]-[触发条件]-[预期]`

**预置条件格式**：
- 接口/枚举测试：`导入 {模块路径} 模块`
- 组件属性测试：`创建 {组件名} 组件实例；组件已挂载到页面`
- 组件事件测试：`创建 {组件名} 组件实例；注册 {事件名} 事件回调`

### Demo关联规则（非XTS且demo_design.md存在时）

- 预置条件：`Demo 应用已安装并启动，导航至 [页面名称] 页面`
- 操作步骤格式：`在{区域}的「{控件标签}」{控件类型中文名}(id:{控件ID})中{动作}`
- 区域推断：select/input→输入区；btn→操作区；result→结果区；log→日志区
- 控件类型中文映射：select→下拉框；input→输入框；btn→按钮

### 继承规则（直接继承自测试点）

测试类型、测试技术、用例级别、执行方式、**来源**：直接继承关联测试点对应字段，不做二次判定。

**来源**：两段结构 `spec: {规格来源} ｜ 经验库: TE-..,CR-..`（对抗补旧时追加 `｜ 对抗: {说明}` 段）。用例来源 = 继承测试点来源（spec+经验库TE）+ 追加本阶段匹配的 CR 到经验库段 + 对抗补旧时追加对抗段。知识库 DK 仅 phase1 标注，不继承。

**测试技术选择优先级**：需求指定 > 领域经验（经验库领域条目推荐测试技术） > 通用经验（经验库通用条目推荐测试技术） > 默认（脚本/Agent按场景判断）

## 输出格式规范（强制执行）

**必填字段**：测试类型、测试技术、执行方式、用例级别、来源、关联测试点、预置条件、测试步骤表格

**步骤表格**：步骤 | 操作（含数据） | 预期结果

**格式要点**：
- 字段格式：`**字段名：** 值`（冒号后有空格）
- 每个用例后使用 `---` 分隔线
- 不输出汇总表/统计信息（脚本统一生成）

```markdown
**输出模板**：

### TC-US01-001-安装验证

**测试类型：** 功能测试/稳定性测试/安全测试/性能测试/兼容性测试/资料测试

**测试技术：** 等价类划分/边界值分析/错误推测法/因子组合/判定表/路径覆盖/状态转换/...

**执行方式：** 黑盒自动化/XTS/API性能自动化/手工

**用例级别：** P0/P1/P2/P3

**来源：** spec: {规格来源} ｜ 经验库: TE-..,CR-..（继承关联测试点来源并追加 phase4 的 CR；对抗补旧时追加 `｜ 对抗: {说明}` 段，无则整段省略）

**关联测试点：** TP-US01-001

**预置条件：**

- Demo应用已安装并启动
- ......

**测试步骤：**

| 步骤 | 操作（含数据） | 预期结果 |
| --- | ------------ | -------- |
| 1 | 在前端页面调用LanguageModel.create()方法 | Promise进入pending状态 |
| ... | ...... | ...... |

```
