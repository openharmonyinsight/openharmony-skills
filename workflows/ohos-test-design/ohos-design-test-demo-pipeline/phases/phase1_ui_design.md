# 阶段 1：Demo UI 设计

## 输入
- 测试点设计报告：`{输出目录}/test_point_design.md`
- 需求分析报告：`{输出目录}/requirement_analysis.md`（可选）
- 领域配置文件：`{技能目录}/reference/domains.yaml`
- API 参考目录：`{技能目录}/reference/api-reference/{选定领域}/`

## 输出
- `{输出目录}/demo_design.md`

## 执行逻辑

1. **【强制阻塞】领域选择**：此步骤必须完成并记录结果后方可继续，无论是协调器调用还是独立调用
   - **如果运行时上下文中已提供领域名称**（协调器调用时由上游传入）：直接使用该领域名称，跳过询问，并运行 `bash reference/api-reference/install.sh {领域名称}`（或等价完整性校验）——通过→完整模式；未安装/校验失败→降级模式，见步骤 5
   - **如果运行时上下文中未提供领域名称**（独立调用）：读取 `reference/domains.yaml`，使用 AskUserQuestion 询问用户选择领域，关键词匹配用户输入与各领域 keywords（不区分大小写），命中后运行 `install.sh {领域}` 校验（未通过则进入降级模式）
   - **禁止**在未获得领域的情况下自行推断领域
2. 读取测试点设计报告，提取所有测试点（ID、描述、技术类型、优先级、对应场景ID）
   2a. **检测测试点组织方式**：
   - 扫描测试点的"对应场景ID"列或"依据"列，检查是否包含 SPEC 引用（如 SPEC-XXX、SPEC-XXX-SNN）
   - **存在 SPEC 引用** → 标记分组维度为"按SPEC"，并建立 `{测试点ID → SPEC ID}` 映射
   - **不存在 SPEC 引用** → 标记分组维度为"按API"
3. 读取需求分析报告，提取 API 信息和系统能力；若分组维度为"按SPEC"，同时提取各 SPEC 的输入约束、参数配置和 SPEC 间依赖关系
4. **API 提取**：从测试点和需求中提取涉及的 API 名称、参数、错误码
5. **API 验证**：验证提取的 API 是否存在于选定领域的 API 参考中。**模式判定**：运行 `bash reference/api-reference/install.sh {领域}`（或等价完整性校验，校验 index.json schema 与所有 `modules[].files[].file` 引用存在且为合法 JSON）——通过→完整模式（执行 5a–5d 的 index 查找）；未安装或校验失败→降级模式（跳过 5a–5d，所有 API 标注 "⚠️ 无 API 参考"，写入 demo_design.md，返回摘要写入 `api_reference=degraded`，由门禁决定是否继续，不宣称可独立运行）。**仅凭 index.json 存在不得进入完整模式**

    **【禁止】使用 Grep/Glob 搜索 api-reference 目录下的 .json 文件。必须严格按以下步骤通过 index.json 索引查找：**

    **步骤 5a（强制首步）**：使用 Read 工具读取 `{技能目录}/reference/api-reference/{领域}/index.json`
    - 该文件结构为：`modules[] → files[] → { name, type, file }`
    - 只需读取此一个文件即可获得所有 API 的定位信息

    **步骤 5b（解析索引）**：从 index.json 中提取查找表
    - 遍历所有 `modules[].files[]` 条目
    - 构建查找表：`{ files[].name → files[].file }`
    - 例如：`{ "domStorageAccess" → "attributes-component-web.json", "WebCookie" → "WebCookie.json" }`

    **步骤 5c（匹配 API）**：对步骤 4 提取的每个 API 名称，在查找表中匹配
    - **找到匹配** → 记录 `{API名称: 对应的file值}` 映射（如 `enableWebAVSession → attributes-component-web.json`）
    - **未找到匹配** → 在 demo_design.md 的 API 清单中标注 "⚠️ 未验证"，并输出警告

    **步骤 5d（验证结果）**：确认所有 API 均已完成查找，将映射写入 demo_design.md API 清单的"JSON文件"列
6. **操作模式提取**：分析测试点的操作步骤，归纳为有限个操作模式（见下方"操作模式定义"）
7. **页面分组**：根据步骤 2a 棇定的分组维度，执行对应策略

    **策略 A（分组维度=按SPEC时）**：
    a. **按 SPEC 初始分桶**：同一 SPEC 的所有测试点归入同一页面初始桶
    b. **SPEC 依赖分析与合并**：
       - 读取需求分析报告中各 SPEC 的输入约束，分析 SPEC 间的配置依赖关系
       - **依赖判定条件**（满足任一即视为有依赖）：
         - SPEC-B 的前置条件/预置步骤中需要设置 SPEC-A 的配置项（如开关状态、模式选择）
         - SPEC-B 的输入参数中包含 SPEC-A 的输出/状态作为条件
         - SPEC-A 和 SPEC-B 共享同一个 API 配置控件（如 Toggle 开关），且该控件的状态影响两者的行为
       - **有依赖关系的 SPEC 合并到同一页面**
       - 合并后的页面须包含所有被合并 SPEC 的完整配置区 + 操作区 + 结果区
    c. **独立可测试性验证**：合并完成后，逐页面检查每个页面是否能独立完成所有测试操作（无需切换到其他页面设置前置条件）
       - 不满足 → 将缺失的前置配置控件补充到该页面，或将相关 SPEC 进一步合并
    d. **小页面合并**：不足 3 个测试点的 SPEC 合并至最相近页面（功能相近或 API 相同）
    e. **大页面拆分**：超过 20 个控件的页面按独立测试场景拆分（非按开关/内容拆分）
       - 拆分时每个子页面自备完整的 SPEC 配置 + 对应测试控件，确保子页面内可独立完成测试
    f. **API 配置控件约束**：API 配置控件（开关/Toggle/Select）必须与依赖该配置的测试操作在同一页面，禁止拆分到不同页面

    **策略 B（分组维度=按API时）**：
    - 同一 API 的所有测试点归入同一页面
    - 功能强相关的 API 归入同一页面
    - 不足 3 个测试点的模块合并至最相近页面
    - 超过 20 个控件的页面按独立测试场景拆分（非按开关/内容拆分）
    - API 配置控件（开关/Toggle/Select）必须与依赖该配置的测试操作在同一页面，禁止拆分到不同页面
    - 按测试场景拆分时，每个场景页面自备完整的开关配置 + 对应测试控件，确保页面内可独立完成测试
8. **控件设计**：为每个页面设计控件（Button/TextInput/Select/Toggle/Text/List）
9. **模式化映射**：按操作模式批量生成映射（见下方"映射生成策略"），不逐条手写
10. 输出 demo_design.md

## 并行生成策略（测试点 > 80 时启用）

使用 Agent 工具并行生成各页面详细设计：
- 每个 Agent 负责一个页面的设计（控件清单 + 区域描述 + 模式化映射）
- Agent prompt 必须包含：该页面的测试点列表、控件 ID 命名规范、区域描述格式、操作模式定义
- 主线程合并各 Agent 输出，生成全局映射总表和导航结构

## 操作模式定义

操作模式是测试点的操作步骤抽象。同一页面的测试点通常遵循相同模式，仅在输入值和预期结果上不同。

**模式定义格式：**
```
模式ID: PM-XXX
名称: [操作模式名称]
适用测试点: [测试点ID范围]
固定控件序列: [控件ID 列表]
操作步骤模板:
  1. 在 [{控件ID}] 中选择/输入 {参数名}
  2. 在 [{控件ID}] 中输入 {参数名}
  3. 点击 [{控件ID}]
  4. 查看 [{控件ID}] 显示结果
差异字段: {参数名} — 取值见映射表
```

**常见模式示例：**
| 模式ID | 名称 | 固定步骤数 | 差异字段 |
|--------|------|-----------|---------|
| PM-001 | setValue 标准设值 | 4 | eventType, xpath, value, 预期结果 |
| PM-002 | selectOption 按索引选中 | 4 | xpath, index, 预期结果 |
| PM-003 | selectOption 按 value 选中 | 4 | xpath, value, 预期结果 |
| PM-004 | 错误场景触发 | 3 | eventType/xpath/value(含无效值), 预期错误码 |
| PM-005 | 回退/通道测试 | 3 | 开关状态, xpath, value, 预期结果 |
| PM-006 | 并发/批量测试 | 2 | 次数, 预期结果 |

## 映射生成策略（模式化 + 合并）

**替换逐条映射，采用"模式-差异值"表格：**

每个操作模式输出一个合并映射表：
```markdown
#### 模式 PM-001：setValue 标准设值
**操作步骤：** 选择 eventType → 输入 xpath → 输入 value → 点击执行 → 查看结果
**涉及控件：** select_XXX_event_type, input_XXX_xpath, input_XXX_value, btn_XXX_execute, result_XXX_01, status_XXX_01

| 测试点ID | eventType | xpath | value | 预期返回码 | 预期状态 |
|---------|-----------|-------|-------|-----------|---------|
| EC-001 | setValue:date | [有效xpath] | 2026-04-14 | 0 | PASS |
| EC-014 | setValue:date | [有效xpath] | abc | -4 | FAIL |
```

**合并规则：**
- 操作步骤相同的测试点合并到同一个模式表
- 仅差异字段（输入值、预期结果）作为列
- 同一模式表内测试点按 ID 排序

## 控件 ID 命名规范（强制执行）
```
{type}_{page_seq}_{semantic_name}
type: btn | input | textarea | toggle | select | result | status | log
page_seq: 3 位零填充页面序号
例: btn_001_execute, input_001_date_value, result_001_01
```

## 自检清单（输出前逐条验证）

1. API 查找走的是 index.json 索引（Read index.json → 解析 files[] → 匹配 name），**未使用 Grep/Glob 搜索 api-reference 目录下所有 .json 文件**
2. 每个测试点至少出现在某个模式化映射表的一行中（100% 覆盖）
3. 所有控件 ID 全局唯一
4. 所有控件 ID 符合 `{type}_{page_seq}_{semantic_name}` 命名规范
5. 每个页面控件数在 8-20 之间（特殊情况允许标注例外）
6. 每个页面包含输入区、操作区、结果区、日志区
7. 涉及 API 的页面包含该 API 所有必填参数的输入控件
8. 涉及系统权限的 API/能力在系统能力清单中标注所需权限
9. 模式化映射表中的测试点 ID 与 test_point_design.md 一致
10. 所有页面在路由表中有对应条目
11. 全局映射总表中的操作模式覆盖所有页面的模式化映射
12. API 配置类控件（开关/Toggle）与依赖其状态的测试操作在同一页面内，未被拆分到不同页面
13. **按SPEC分组时的独立可测试性**：存在配置依赖的 SPEC 已合并到同一页面；每个页面包含其所有测试操作所需的前置配置控件，可独立完成测试，无需切换到其他页面设置前置条件

## 确认机制

**协调器调用**：完成后返回摘要，跳过确认。
**独立调用**：完成后显示摘要（Demo 页面/控件/操作模式/覆盖率），使用 AskUserQuestion 询问用户确认。
- **确认完成** → 进入下一阶段
- **输入优化建议** → 增量修正、重新自检、再次确认，循环直到确认完成
- 增量优化规则：仅修改用户指出的具体问题，不擅自扩展范围；新增 ID 顺延编号
